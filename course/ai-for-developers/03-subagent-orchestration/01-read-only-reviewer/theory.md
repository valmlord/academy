# Read-only ревьюер: запрет, который исполняет харнесс

## Проблема

Коллега взял из документации Claude Code пример `code-reviewer`. Там он подписан как "A read-only
subagent that reviews code without modifying it", а в списке инструментов стоит
`tools: Read, Grep, Glob, Bash`. В промпт коллега дописал "никогда не меняй файлы". На первом же
ревью агент "заодно поправил опечатку" командой `sed -i`.

Коллега написал строгую копию, где в списке только чтение. Claude Code продолжил вызывать старого
ревьюера, а строгая копия так ни разу и не загрузилась. И модель у ревьюера оказалась не та, что
нужна команде.

Это три разные ошибки. Запрет записан в промпте, а не в списке инструментов. Загрузился не тот файл.
Модель зависит от нескольких настроек сразу, и коллега проверил не все. Ниже про Claude Code по
документации на 2026-11-03.

## Идея: запрет живёт в списке инструментов

Промпт просит, харнесс исполняет. Если инструмента нет в списке, агент не может его вызвать, что
бы ни было написано в промпте. Best practices Claude Code говорит про ревьюера прямо: дайте ему
"only `tools: Read, Grep, Glob`", и тогда "that limit is enforced by Claude Code rather than
requested in a prompt". В Agent SDK у набора `Read`, `Grep`, `Glob` стоит описание "Can examine code
but not modify or execute".

Bash в этот набор не входит, потому что выполняет команды оболочки. А команда оболочки умеет писать
файлы: `sed -i`, `>`. Поэтому пример с Bash остаётся read-only только на словах.

Не путайте "только чтение" со столбцом "Permission required: No" в справочнике инструментов. Этот
столбец показывает только одно: спрашивает ли инструмент разрешение в режиме Manual для путей внутри
рабочей папки. "No" стоит и у
`Agent`, `SendMessage` и `TaskStop`, а они запускают других агентов, пишут им сообщения или
останавливают их.

У других инструментов модель другая. В Codex субагент наследует от родителя песочницу и правила
одобрения: "Subagents inherit the parent turn's current sandbox and approval settings ... A custom
agent file can't replace those settings." И дальше: "Custom agent instructions can ask an agent to
avoid edits, but they don't create a separate read-only sandbox." Там read-only это свойство
сессии-родителя, а не файла агента.

## Как это работает

### Какой файл загружается

Определения лежат в `.claude/agents/`, и Claude Code обходит эту папку рекурсивно, с подпапками.
Агента определяет только поле `name`, а имя файла и путь к нему роли не играют.

Пять случаев, когда файл пропускается молча, без сообщения в сессии (причина видна только в
debug-логе):

- нет `name` (файл считается документацией);
- открывающий `---` стоит не на первой строке (тоже документация);
- `name` начинается с `-`, содержит `:` или длиннее 256 символов;
- есть `name`, но нет `description`;
- YAML не разбирается.

Если два файла в одном дереве `.claude/agents/` объявляют одинаковый `name`, Claude Code загружает
только один, "chosen by filesystem read order rather than a documented precedence". Документированного
порядка нет, поэтому дубликат убирают, а не угадывают победителя.

Поле с неизвестным именем Claude Code игнорирует без ошибки. Опечатка `tool:` вместо `tools:` не
сломает файл, она просто снимет ограничение.

### Какие инструменты получит агент

- `tools` это allowlist. Если поля нет, агент наследует все инструменты, доступные субагентам.
- `disallowedTools` это denylist. Если заданы оба поля, сначала применяется `disallowedTools`, потом
  `tools`. Агент только с `disallowedTools: Write, Edit` по документации "keeps Bash, MCP tools, and
  the rest of its pool". А агент с `tools: Read, Grep, Glob, Bash` по документации не может
  использовать MCP-инструменты.
- Если ни одна запись в `tools` не соответствует инструменту, Claude Code "usually refuses to launch"
  агента.
- `memory` даёт агенту постоянную папку, и для неё "Read, Write, and Edit tools are automatically
  enabled".

Через четыре инструмента агент дотягивается до других агентов и навыков:

- `Agent` запускает субагента (старое имя `Task` работает как синоним с v2.1.63, `Task(...)` тоже);
- `Skill` вызывает навык;
- `SendMessage` пишет другому агенту или другой сессии Claude Code;
- `TaskStop` останавливает фоновую задачу или фонового агента.

Чтобы ревьюер не запускал субагентов и не вызывал навыки, документация советует не включать `Agent`
и `Skill` в `tools` (или добавить их в `disallowedTools`).

Поиск на Linux. На macOS, Linux и WSL Claude Code не включает Glob и Grep в набор инструментов по
умолчанию: Claude ищет через `find` и `grep` в Bash. Для субагента документация называет условие, при
котором они возвращаются: он перечисляет Glob или Grep в поле `tools` и не перечисляет там Bash.
Отсюда наш вывод (дословно в документации его нет): в обычной сессии пример ревьюера с
`Read, Grep, Glob, Bash` на Linux получит Read и Bash, но не Glob и Grep.

Ещё три поля расширяют агента:

- `mcpServers` подключает MCP-серверы, и агент получает их инструменты;
- `hooks` задаёт хуки только для этого агента, например команду перед вызовом инструмента;
- `permissionMode` меняет, что идёт без вопроса. В `acceptEdits` это чтение, правки файлов и частые
  файловые команды (`mkdir`, `touch`, `mv`, `cp` и т. п.), в `auto` "Everything, with background safety
  checks", в `bypassPermissions` "Everything".

Ревьюеру, который только читает, ни одно из них не нужно.

### Какая модель запустится

Claude Code выбирает модель субагента в таком порядке:

1. `model`, который Claude передал в вызове (только алиас: `sonnet`, `opus`, `haiku`, `fable`);
2. поле `model` в определении, где `inherit` значит модель основной сессии;
3. переменная `CLAUDE_CODE_SUBAGENT_MODEL`;
4. модель основной сессии.

Здесь есть ловушка. Алиас семейства в вызове или в определении указывает на модель основной сессии,
если она из того же семейства. Тогда агент работает на точной модели основной сессии, а не на
версии, на которую указывает алиас. (Второй такой случай касается только `opus` у провайдеров кроме
Anthropic API, когда Claude Code не может определить семейство модели сессии.) В переменной
`CLAUDE_CODE_SUBAGENT_MODEL` алиас "always resolves to the version the alias points to". Значение
`inherit` в переменной равносильно тому, что её нет. На Anthropic API `opus`, `sonnet` и `haiku`
указывают на Opus 5.5, Sonnet 5.5 и Haiku 5.5.

`CLAUDE_CODE_SUBAGENT_MODEL_FORCE` меняет картину. Пока она включена, Claude Code игнорирует поле
`model` в определениях, а Claude не может передать модель в вызове. Если заданы обе переменные,
субагенты работают на модели из `CLAUDE_CODE_SUBAGENT_MODEL`. Если задана только `..._FORCE`, они
работают на модели основной сессии (кроме встроенного Explore). Форк и навык, запущенный в субагенте
с `model: inherit`, и при включённой переменной остаются на модели основной сессии. Действует она на
все субагенты, не только на ревьюера. Включают её как любой переключатель: `1`, `true`, `yes`, `on`,
а выключают `0`, `false`, `no`, `off`, в любом регистре.

Пример. Основная сессия на Opus 5, Anthropic API, Claude модель в вызове не передаёт.

| Определение | `env` в настройках | На чём работает агент |
|---|---|---|
| `model: opus` | ничего | Opus 5: алиас своего семейства берёт модель сессии |
| поля `model` нет | `CLAUDE_CODE_SUBAGENT_MODEL: opus` | Opus 5.5: алиас в переменной указывает на версию |
| `model: claude-opus-5-5` | `CLAUDE_CODE_SUBAGENT_MODEL: haiku` и `..._FORCE: "on"` | Haiku 5.5: поле `model` игнорируется |

## Свежий взгляд

Обычный субагент "starts with a fresh, isolated context window". Он не видит вашего разговора,
Claude пишет ему сообщение с задачей. Поэтому ревьюер не видел, как автор рассуждал.

Форк устроен иначе: это субагент, который "inherits the entire conversation so far". Он видит тот же
разговор, тот же системный промпт и ту же модель, поэтому свежим взглядом не является. Режим форков
включён по умолчанию с v2.1.302. Это деталь версии, она может поменяться.

Сам по себе субагент не умнее основной сессии. Best practices: по умолчанию это "the same model (or a
smaller one) on the same task". Это разбирали в модуле 00 (урок 4) и модуле 01 (урок 7).

## Когда второй агент оправдан

Best practices называет четыре случая:

- независимые части работы идут одновременно;
- длинный вывод вроде полного прогона тестов не попадает в основной разговор;
- нужен ревьюер, который не видел, как писался код;
- задаче нужно меньше инструментов, чем у основной сессии.

Статья в блоге claude.com о мультиагентных системах (2026-01-23) советует делить работу по контексту ("context-centric"), а
не по типу работы. В его эксперименте агенты по ролям разработки (планировщик, исполнитель,
тестировщик, ревьюер) "spent more tokens on coordination than on actual work". Название должности
агента не причина его заводить. Наш ревьюер оправдан двумя пунктами из этого списка: свежим взглядом
и урезанными инструментами.

Флаг `claude --agent <name>` запускает всю сессию от лица агента, с его инструментами и моделью. В
пайплайне этого модуля роли вызываются из скрипта через `claude -p`, и `--agent` мы там не используем.
Почему, разберём в уроке 2.

## Частые ошибки

- "Только чтение" написано в промпте, а Bash стоит в `tools`.
- Поля `tools` нет совсем, или есть только `disallowedTools`.
- Исправленная копия, которая молча пропускается, или второй файл с тем же `name`.
- Алиас семейства основной сессии в `model` в расчёте на новую версию.
- Забытый `..._FORCE` в `env`, который меняет модель всем агентам проекта.
- `memory` "на всякий случай": вместе с ней приходят Write и Edit.

## Что делать в практике

Вы получите `invoice-service` с определениями агентов, которые писал коллега, настройками проекта и
брифом команды. Нужно найти, какое определение ревьюера на самом деле загружается, какие у него
инструменты и на какой модели он запустится, и привести это к требованиям. Кодер при этом должен
остаться рабочим.
