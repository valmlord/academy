# Журнал передач: где сломался стык

## Проблема

Эта история из другого проекта, не из рабочей папки урока; запись, которую вы будете читать, снята с
другого прогона. В сервисе платежей прогон ревью изменения в `payouts/settle.py` закончился спокойно.
Synthesizer написал "все три раздела проверены", summarizer "замечаний нет, тесты проходят". Через
день выяснилось, что выплаты теряют строки с комиссией, а тест на это падал уже в день ревью.

Разработчик открыл запись прогона. Прямо перед словами ревьюера тестов "все тесты проходят" стоял
запуск `python3 -m unittest` с выводом `OK`. Вывод напрашивался: ревьюер тесты прогнал, просто тест
плохой. Но этот запуск сделал другой субагент, который работал параллельно и уже успел откатить свою
правку. Ревьюер тестов ничего не запускал.

Итоговый текст каждого агента выглядел правдоподобно. Сломался стык между агентами, и найти его можно
только по записи передач. Стык в этом уроке это граница между агентами: что агенту разрешено по его
роли, что он получает на вход, что сдаёт в отчёте и что с этим отчётом делает получатель. Читать её надо по дереву агентов, а не по порядку строк.

## Идея: каждая передача записана и приписана агенту

В мультиагентном прогоне ошибку делает один агент на одном шаге, а видна она обычно в конце, у
другого агента. Восстановить виновника потом трудно даже моделям. Zhang и др. собрали набор Who&When:
журналы сбоев 127 мультиагентных систем, в которых размечены виновный агент и решающий шаг ошибки.
Лучший из их автоматических методов находит агента в 53,5% случаев, а шаг в 14,2% (arXiv:2505.00212
v3, 2025-06-02; ICML 2025, PMLR 267). Даже o1 и DeepSeek R1, по словам авторов, до практической
пригодности не дотягивают.

Вывод для пайплайна: не надеяться разобраться потом, а писать журнал каждой передачи (урок 3) и
приписывать события агентам по данным, а не на глаз. Когда оркестратор ваш скрипт, журнал пишет он.
Когда оркестратор сам Claude, журнал уже есть: это поток `stream-json`.

## Дерево в `stream-json`

Страница headless, раздел "Follow subagent messages": сообщения субагентов приходят в поток как
сообщения `assistant` и `user`, и их поле `parent_tool_use_id` говорит, к какому запуску относится
каждое. У сообщений основного разговора там `null`. Значение это id блока `tool_use`, которым Agent
запустил субагента. Вложенный субагент несёт id того вызова Agent, который запустил его самого, "so you
can rebuild the full nesting tree by following those IDs".

Что попадает в поток:

- первое сообщение субагента, работающего на переднем плане, это сообщение `user` с его промптом;
- дальше по умолчанию только его блоки `tool_use` и `tool_result`;
- с `--forward-subagent-text` (Claude Code v2.1.211+) или `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT` ещё текст
  и thinking, на любой глубине вложенности.

По умолчанию субагент может запускать своих субагентов на глубину до трёх уровней ниже основного
разговора; `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` меняет предел (sub-agents).

Три детали из страницы о субагентах в Agent SDK:

- инструмент называется `"Agent"` в блоках `tool_use`, но `"Task"` в списке инструментов `system:init`.
  До v2.1.63 и в `tool_use` он назывался `"Task"`;
- вызов Agent без `subagent_type` получает встроенного субагента `general-purpose`: "When Claude calls
  the Agent tool without a `subagent_type`, it gets the built-in `general-purpose` subagent". Если его в
  сессии нет (например, с `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1`), вызов падает с
  `subagent_type is required`;
- форк, субагент с копией всего разговора, Claude запускает явным типом: "From Claude Code v2.1.302,
  Claude can start forks in your application with nothing configured, by calling the Agent tool with
  `subagent_type: "fork"`". На странице о субагентах: "Fork mode is on by default from Claude Code
  v2.1.302". Документация запускает форк только этим явным типом, а про вызов без типа говорит одно:
  он получает `general-purpose`. В записи этого урока форков нет.

Субагент по умолчанию запускается в фоне: результат Agent приходит со `status: "async_launched"`, а
отчёт позже. Если Claude ждёт субагента, вызов блокируется, и отчёт приходит в `tool_result` этого
вызова.

### Небольшой пример

Четыре строки, по одному блоку содержимого в строке. Лишние поля убраны, и часть строк тоже: строки
`user` с промптами субагентов и результат `Read`.

```json
{"type":"assistant","parent_tool_use_id":null,"message":{"content":[{"type":"tool_use","id":"tu_A","name":"Agent","input":{"subagent_type":"planner","prompt":"..."}}]}}
{"type":"assistant","parent_tool_use_id":"tu_A","message":{"content":[{"type":"tool_use","id":"tu_B","name":"Agent","input":{"prompt":"..."}}]}}
{"type":"assistant","parent_tool_use_id":"tu_B","message":{"content":[{"type":"tool_use","id":"tu_C","name":"Read","input":{"file_path":"docs/api.md"}}]}}
{"type":"user","parent_tool_use_id":null,"message":{"content":[{"type":"tool_result","tool_use_id":"tu_A","content":"..."}]}}
```

- `tu_A` сделал `main`: у строки `parent_tool_use_id` равен `null`. Этот вызов запустил `planner`.
- `tu_B` сделал `planner`: строка указывает на `tu_A`. В вызове нет `subagent_type`, значит, он
  запустил `general-purpose`.
- `tu_C` сделал `general-purpose`, запущенный из `planner`: путь `main/planner/general-purpose`.
- Последняя строка это отчёт `planner`, вернувшийся к `main`. Она в контексте `main`, поэтому там
  `null`, а `tool_use_id` говорит, на какой вызов это ответ.

Порядок строк агента не определяет. Два субагента, запущенные одним ходом, работают одновременно, и их
строки перемешаны. Правило "это сделал последний запущенный агент" ломается на первом же таком
месте, а правило "смотрю только на ближайшего родителя" ломается на вложенности.

Поддерево агента это все вызовы под тем Agent `tool_use`, который его запустил, вместе с вызовами его
вложенных субагентов.

## Записанный прогон

Эту запись снял не ваш Python-пайплайн, а один вызов `claude -p`, где оркестратором был сам Claude и
раздавал работу субагентам из `--agents`. Правила вызова из уроков 2-5 относятся к вызову роли
из скрипта. Среди них правило C10 из урока 2: в вызове роли только флаги, которым учит урок, и
`--agents` в этом списке нет. Здесь видно, зачем они нужны: определения в `--agents` оказались
шире контрактов, и харнесс пропустил то, что запрещал контракт.

Строка запуска и контракты ролей лежат в `trace/README.md`. Файловая форма `--agents` с `--print`
требует Claude Code v2.1.281+ (CLI reference). Это контекст записи, а не правило курса.

## Пять поломок стыка

Категории курса узкие: каждую решает одна наблюдаемая строка записи. Точные правила в задании, здесь
смысл.

- **`role-breach`**: агент вызвал инструмент, которого нет в его контракте. Харнесс мог это
  разрешить, если определение шире контракта. В терминах этого модуля это близко к режиму MAST
  FM-1.2 "Disobey role specification" (о MAST ниже).
- **`context-leak`**: передача несёт то, что контракт получателя запрещает: рассуждения, стенограмму,
  отчёт другого раздела. Свежий взгляд ревьюера (урок 3) пропадает именно так.
- **`uncited-claim`**: находка ушла от агента без проверяемой цитаты, и её подхватил следующий. Это
  то, что в уроке 5 останавливает проверка на стыке.
- **`ignored-failure`**: оркестратор получил ошибку или не получил вывода и пошёл дальше так, будто шаг
  удался.
- **`unverified-pass`**: агент сообщает "проверено", а проверки в его поддереве нет (урок 5, ярлык
  верификатора). В уроке 6 модуля о spec-driven development была похожая категория
  `claim-without-evidence`: после правки нет ни одного запуска. Здесь иначе: запуск в записи есть, но в
  поддереве другого агента. Отличить одно от другого можно только по дереву.

MAST (Cemri и др., "Why Do Multi-Agent LLM Systems Fail?", arXiv:2503.13657 v3, 2025-10-26; NeurIPS
2025, spotlight-постер) даёт таксономию из 14 режимов отказа в трёх группах и набор MAST-Data из 1600+
размеченных трасс семи фреймворков. В терминах этого модуля `uncited-claim` ближе всего к FM-3.3
"Incorrect verification", а `unverified-pass` к FM-3.2 "No or incomplete verification", обе из группы
"Task Verification". Это сопоставление курса, а не авторов: режимы MAST шире, и их ставит разметчик по
всей трассе, а не правило по одной строке.

## Не только stream-json

У Claude Code есть трассировка OpenTelemetry, но она помечена как beta (monitoring-usage, раздел
"Traces (beta)"). Её включают `CLAUDE_CODE_ENABLE_TELEMETRY=1` и
`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` плюс `OTEL_TRACES_EXPORTER`. Спаны субагента вложены в спан
инструмента Agent родителя, а промпты и содержимое инструментов по умолчанию скрыты. В этом уроке
она не нужна: всё дерево есть в `parent_tool_use_id`.

## Частые ошибки

- Приписывать строку последнему запущенному агенту или ближайшему вызову Agent выше по файлу.
- Останавливаться на одном уровне и не видеть, что вызов сделал субагент субагента.
- Искать `"Task"` в `tool_use`: в текущих версиях там `"Agent"`.
- Считать, что вызов без `subagent_type` никого не запустил.
- Видеть зелёный прогон рядом с "тесты проходят" и не проверять, в чьём он поддереве.
- Ставить находку на строку, где проблема проявилась позже, а не на строку, которую называет правило
  якоря.

## Что делать в практике

Сначала вы напишете `attribute()`: она по `parent_tool_use_id` приписывает каждый `tool_use` агенту,
включая вложенные вызовы. Её проверяют на случайных трассах, которых вы не видели. Потом с её помощью
прочитаете запись прогона ревью и найдёте стыки, где сломалась передача, по пяти категориям и правилу
выбора из задания.
