- `trace/trace_tree.py`: сигнатура `attribute(events: list[dict[str, object]]) -> dict[str, str]`,
  тело пока бросает `NotImplementedError`;
- `findings.json`: ваш отчёт, сейчас `[]`.

Файлы проекта, на которые ссылаются находки в записи, лежат в рабочей папке: по ним можно проверить
цитату. Они лежат в состоянии после изменения из `run/change.diff`, и цитату сверяют именно с ними, в
том виде, в каком они в рабочей папке.

## Что сделать

1. Реализуйте `attribute()` (требования T1, T2).
2. Прочитайте `trace/README.md`, потом запись, зная для каждого вызова, какой агент его сделал.
3. Найдите стыки, где сломалась передача, и запишите их в `findings.json` по правилам ниже.

## Требования к `attribute()`

`events` это строки записи, каждая разобрана как JSON-объект, в порядке файла. Сообщения субагента
никогда не идут раньше вызова Agent, который его запустил.

- **T1.** `attribute` возвращает словарь, где ключ это id каждого блока `tool_use` в событиях, а
  значение это путь агента, который сделал этот вызов: `main` для основного разговора,
  `main/<тип>` для субагента, запущенного из `main`, `main/<тип1>/<тип2>` для субагента этого
  субагента и так далее. `<тип>` это `subagent_type` из вызова Agent, который запустил агента. Два
  экземпляра одного типа под одним родителем дают один и тот же путь.
- **T2.** Вызов Agent без `subagent_type` запускает `general-purpose`: в каждой трассе, на которой
  проверяется функция, этот субагент в сессии есть.

## Категории и правило выбора

Для каждого места, которое вызывает подозрение, задавайте вопросы по порядку. Первый ответ "да" даёт
категорию.

Термины:

- **передача**: вход вызова Agent (`tool_use`) или `tool_result`, который возвращает отчёт агента его
  родителю. Строка `user` с промптом, которой субагент начинает работу, передачей не считается: она
  повторяет вход вызова Agent, а передача это строка самого вызова;
- **находка**: утверждение о коде, которое обязано ссылаться на файл, строку и цитату. Цитата
  проверяемая, как в уроке 5: файл существует, строка в его диапазоне, цитата с этой строки. Файл и
  строку берут из рабочей папки как есть, то есть в состоянии после изменения;
- **поддерево агента**: все вызовы под тем Agent `tool_use`, который его запустил, включая вызовы его
  вложенных субагентов.

Вопросы:

1. Агент вызвал инструмент, которого нет в его контракте? Тогда `role-breach`.
2. Передача несёт то, что контракт запрещает: рассуждения, стенограмму, отчёт другого раздела? Тогда
   `context-leak`.
3. Находка уходит от агента, который её сделал, в его отчёте без проверяемой цитаты, и следующий агент
   её использует? Тогда `uncited-claim`.
4. Первый вызов инструмента (`tool_use`) `main` после результата с ошибкой или без вывода считает этот
   шаг успешным? Тогда `ignored-failure`.
5. Отчёт агента сообщает как свой результат, что тесты или проверка прошли, а в его собственном
   поддереве до отчёта нет вызова, который эту проверку выполняет? Тогда `unverified-pass`.

Если на все пять вопросов ответ "нет", это не находка.

## Правило якоря: на какую строку указывать

| Категория | Строка |
|---|---|
| `role-breach` | строка `tool_use` запрещённого вызова |
| `context-leak` | строка передачи: Agent `tool_use` или `tool_result` |
| `uncited-claim` | строка `tool_result` с отчётом агента, который сделал находку |
| `ignored-failure` | строка первого `tool_use` `main` после ошибки |
| `unverified-pass` | строка `tool_result` с отчётом |

У каждого спрятанного места ровно одна принимаемая строка.

## Формат `findings.json`

JSON-массив объектов:

```json
[
  {"file": "trace/review-run.ndjson", "line": 1, "category": "role-breach", "why": "одна фраза"}
]
```

`file` путь от корня рабочей папки, буква в букву: `trace/review-run.ndjson`. `line` целое число,
`category` одна из пяти категорий, `why` ваше объяснение (его читает ментор, автоматически оно не
оценивается). Пример выше показывает только формат.

Отчёт с другим путём или с категорией не из списка пяти ни с чем не совпадает, а отправка при этом
засчитывается как попытка.

## Готово, когда

1. `attribute()` проходит `trace-attribution`.
2. `findings.json` это JSON-массив объектов в формате выше.
3. В нём не больше 9 отчётов.
4. Не больше 1 отчёта попало на место, которое похоже на поломку, но ею не является.
5. Найдено не меньше 6 из 8 спрятанных мест, каждое с верной категорией.
6. Оценённых отправок `findings.json` не больше 3; отправка с ошибкой формата не считается.

## Как проверяется

**`trace-attribution`** (команда в рабочей папке; требования T1, T2).

- Проверка вызывает вашу `attribute` на 50 случайных трассах, которых вы не видели и которые создаются
  заново при каждом запуске. В каждом запуске среди них не меньше 10 трасс с вложенностью 2 и глубже,
  10 с вложенностью 3, 10 с перемешанными сообщениями соседних субагентов, 10 с параллельными
  вызовами Agent из одного хода, 5 с вызовом Agent без `subagent_type` и 10, где у вложенного
  субагента есть строка после первой строки соседа, запущенного позже него.
- Трассы устроены как запись: первая строка `system`/`init`, последняя `result`, один блок
  содержимого в строке, первая строка субагента это `user` с его промптом, в `tool_use` всегда
  `Agent`. Id и имена типов случайные.
- Функция работает в отдельном процессе `python3 -I -B` на копии рабочей папки (без `.git` и
  `__pycache__`). Первыми в `sys.path` стоят `trace/` и корень копии, стандартные модули импортированы
  раньше вашего. Каждая трасса передаётся заново разобранным списком. Что функция печатает, не
  показывается.
- Возвращённый словарь сравнивается с ожидаемым целиком: пропущенный id, лишний ключ или неверный путь
  дают провал. Если неверный путь отличается от ожидаемого только сегментом агента, запущенного
  вызовом Agent без типа, это T2. Любое другое расхождение, пропущенный id или лишний ключ это T1.
- Сообщение при провале: по строке на каждое невыполненное требование, вида
  `не выполнено: T1: <требование> (<ситуации>)`. Ситуации перечислены через "; ", их пять: "в трассе с
  вложенным вызовом", "при перемешанных сообщениях соседей", "при параллельных вызовах Agent из одного
  хода", "в трассе без вложенных и параллельных вызовов", "в трассе с вызовом Agent без типа" (у T2
  всегда последняя). Трасса, id и значения не печатаются.
- Если модуль не импортируется, функция бросает исключение, возвращает не словарь или словарь, который
  нельзя записать в JSON, или процесс с функцией завершается без результата, сообщение одно: T1, а в
  скобках причина. Для исключения называется только его класс.
- На все 50 трасс у функции 30 секунд; если не уложилась, сообщение T1 с причиной "не уложились в
  30 с". Вся проверка ограничена 60 секундами.
- Число попыток не ограничено; после 5 неудачных интерфейс предложит ментора.

**`trace-hunt`** (bug-hunt): ваш `findings.json` сравнивается с ключом.

- Отчёт совпадает со спрятанным местом, когда совпадают `file` и `category`, а `line` равна его
  строке. Один отчёт засчитывается не больше чем одному месту, и каждое место засчитывается один раз.
- Нужно найти не меньше 6 мест.
- Не больше 9 отчётов в файле.
- Не больше 1 отчёта на месте, похожем на поломку, в любой категории.
- Отчёт на строке, которая не совпала ни с чем, только расходует один из 9 отчётов.
- Ошибки формата (не массив, нет поля, `line` не целое) называются с индексом и полем. Такая
  отправка не считается попыткой.
- При провале показывается только "не пройдено", без числа найденных и без указания, какие отчёты
  совпали.

## Как работать (совет, не проверяется)

- Начните с `attribute()`: без дерева запись не прочитать.
- Выпишите контракты из `trace/README.md` в таблицу: роль, инструменты, вход, отчёт.
- Проведите каждую подозрительную строку через пять вопросов по порядку и проверьте якорь.
- Для каждой находки назовите себе похожее место, которое правил не нарушает, и скажите, чем они
  отличаются. Если не можете, это, скорее всего, не находка.
- Если не уверены между двумя строками, не ставьте отчёт на обе.

## Попытки и подсказки

- `trace-attribution`: попытки не ограничены. Ментор обсуждает только требования, которые уже назвало
  сообщение проверки.
- `trace-hunt`: не больше 3 оценённых отправок. Ключ и пояснения открываются после прохождения или
  после 3-й неудачи, и тогда проверка закрывается как "не пройдено" с разбором у ментора. Разбор после
  закрытия идёт на другом, ещё не виденном фрагменте.
- Ментор между отправками задаёт вопросы и подсказывает направление, но не говорит, какой отчёт верен
  или неверен.
