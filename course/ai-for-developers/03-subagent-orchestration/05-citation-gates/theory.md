# Цитаты и перекрёстные проверки на стыках

## Проблема

Fan-out ревью из урока 4 прошёл без единого сбоя. Ревьюер безопасности вернул находку:

```json
{"id": "F-3a91", "file": "src/invoices/export.py", "line": 412,
 "quote": "rows = db.execute(f\"SELECT * FROM invoices WHERE id = {invoice_id}\")",
 "claim": "SQL-инъекция через invoice_id", "severity": "high"}
```

Схема ответа её приняла: все поля на месте, `line` целое число. Synthesizer объединил её с похожей
находкой другого раздела, и в отчёте появилось "критично: SQL-инъекция в export.py:412". Разработчик
открыл файл. В нём 300 строк, а такой строки нет ни в одном файле проекта.

Каждая роль выполнила свой контракт, но не было проверки на стыке. Схема проверяет форму ответа, а не
то, что строка 412 существует. Диапазоны, как договорились в уроке 2, проверяет детерминированный код
на стыке. Этот урок о таком коде и о том, где он стоит.

## Идея: место, которое проверяет код

В исследовательской системе Anthropic (Hadfield и др., 2025) система в конце "passes all findings to
a CitationAgent, which processes the documents and research report to identify specific locations for
citations". У каждого утверждения должно быть место в источнике.

В этом модуле место находки это файл, строка и цитата с этой строки (урок 2). Проверить его можно без
модели, обычным кодом:

1. файл есть в снимке, то есть в том дереве файлов, которое видел ревьюер;
2. строка с таким номером в файле есть;
3. цитата действительно стоит на этой строке.

Итоговую находку synthesizer проверяют иначе. Она должна сводиться к принятым исходным: каждый её
`source_ids` указывает на находку, которая прошла проверку, а её место совпадает с местом одной из них.
Иначе synthesizer её придумал или собрал из отклонённой.

Правило курса: находка без проверяемой цитаты **не проверена, а не опровергнута**. Она может быть и
верной, просто ревьюер ошибся в номере строки. Поэтому дальше как факт она не идёт, но и не исчезает
молча: проверка записывает её в журнал вместе с нарушенным правилом, и человек может посмотреть сам.

### Небольшой пример

Как считать строки, в задании сказано точно. Коротко: текст делится по `\n`, последний пустой кусок
отбрасывается.

```python
def lines_of(text: str) -> list[str]:
    pieces = text.split("\n")
    if pieces[-1] == "":
        pieces.pop()
    return pieces

print(len(lines_of("")))       # 0: в пустом файле строк нет
print(len(lines_of("\n")))     # 1: одна пустая строка
print(len(lines_of("a\n\nb"))) # 3
```

Снимок с файлом `src/fees.py`:

```text
1  def late_fee(days: int) -> int:
2      if days <= 0:
3          return 0
```

| Находка | Вердикт |
|---|---|
| `src/fees.py`, строка 2, цитата `if days <= 0:` | проходит |
| `src/fees.py`, строка 3, цитата `if days <= 0:` | нет: цитата с соседней строки |
| `src/fees.py`, строка 7 | нет: в файле 3 строки |
| `./src/fees.py`, строка 2 | нет: путь записан не так, как в снимке |
| `src/fees.py`, `"line": true` | нет: в Python `isinstance(True, int)` истинно, но номер строки это не `bool` |

Цитата сравнивается как подстрока, а не как регулярное выражение: в коде полно `(`, `*` и `.`.

## Почему на каждом стыке

Допустим, проверка стоит только перед отчётом. Плохая находка ревьюера дошла до synthesizer, и он её
уже использовал: объединил с другой, поднял серьёзность, переписал формулировку. Убрать её в конце
можно, а её влияние на объединённый вывод уже не убрать. Поэтому проверка стоит на каждом стыке, где
находки переходят от роли к роли или в отчёт.

Что говорят исследования.

**MAST** (Cemri и др., "Why Do Multi-Agent LLM Systems Fail?", arXiv:2503.13657 v3, 2025-10-26):
"Insight 3. Multi-Level Verification is Needed. Current verifier implementations are often
insufficient; sole reliance on final-stage, low-level checks is inadequate." Там же: "Systems with
explicit verifiers like MetaGPT and ChatDev generally show fewer total failures", и "the presence of a
verifier is not a silver bullet". Это наблюдение по разметке трасс, а не эксперимент. Прирост +15,6%
от проверки цели задачи в ChatDev (по приложению H это смена топологии: процесс кончается, только когда
агент CTO подтвердит ревью) измерен на 32 задачах ProgramDev-v0, и авторы пишут, что их вмешательства
"do not constitute substantial improvements". Где ставить проверку, MAST не сравнивает: он говорит, что
одной низкоуровневой проверки в конце мало.

**Hallucination Snowball** (Singh, Pawar, arXiv:2608.14588 v1, препринт) сравнивает именно место. По
аннотации, проверки на каждой границе между агентами оставляют до конца намного меньше галлюцинаций,
чем проверка только в конце, а проверка только в конце почти ничего не даёт против полного отсутствия
проверок. Оговорки:

- это препринт, а не рецензируемая статья;
- один финансовый пайплайн из четырёх агентов на FinanceBench, 346 искусственно внесённых ошибок;
- "accepted at the FAGEN Workshop" написали сами авторы, сайт воркшопа списка принятых работ не даёт и
  говорит: "This is a non-archival venue";
- номер 2608 не сходится с датой подачи на странице, 22 июня 2026.

**Hallucination Cascade** (Jamshidi и др., arXiv:2606.07937 v1, препринт) в цепочках из трёх агентов
нашёл "net attenuation": к концу цепочки галлюцинаций стало меньше, а фактическая точность немного
снизилась. **From Spark to Fire** (Xie и др.,
arXiv:2603.04474 v2, препринт) показывает обратное на своих атаках: одна внесённая ошибка "leads to
widespread failure".

Работы изучали разные постановки, поэтому противоречия меньше, чем кажется. Вывод курса, а не авторов:
проверка по правилам на каждом стыке это дешёвая страховка, она ловит то, что дальше заметить труднее,
но выигрыш от неё на ваших задачах никто не мерил.

## Ярлык верификатора: `unverified-pass`

Пост в блоге claude.com о мультиагентных системах (2026-01-23): "The most significant failure mode for
verification subagents is marking outputs as passing without thorough testing." И дальше: "The
verifier runs one or two tests, observes them pass, and declares success." Это один источник одного
вендора.

Отсюда категория `unverified-pass`: агент передаёт дальше "проверено", а проверки в его работе нет.
Похожая `claim-without-evidence` из модуля о spec-driven development касалась одного агента; случай,
когда запуск есть, но в работе другого агента, разберём в уроке 6. Проверка на стыке не верит слову
"проверено": она проверяет место сама.

## Где исполняется проверка

### В вашем пайплайне

Роли у вас это отдельные процессы `claude -p`, а не субагенты. Каждый стык проходит через ваш
`run.py`, поэтому и проверка это функция в нём, между вызовами. Она работает одинаково в любом режиме
разрешений и в любой папке.

### Когда оркестратор сам Claude

Если субагентов запускает Claude, стык внутри одной сессии, и мест для проверки несколько (hooks
reference):

- **`SubagentStop` в настройках** (`.claude/settings.json`). Хук получает `agent_id`, `agent_type`,
  `agent_transcript_path`, `stop_hook_active` (`true`, когда Claude уже продолжает работу из-за
  stop-хука) и `last_assistant_message`, где "the text content of the subagent's final response".
  `decision: "block"` с `reason` "keeps the subagent running and delivers `reason` to the subagent as
  its next instruction"; exit 2 доставляет stderr так же. Для родителя
  там же другой путь: "To inject context into the parent session after a subagent returns, use a
  `PostToolUse` hook on the `Agent` tool instead."
- **Внутренние агенты.** `SubagentStop` срабатывает и для служебных агентов Claude Code, например
  подсказок промпта и `/btw`. У них `agent_type` это имя агента самой сессии или пустая строка. Matcher
  с именами типов пустую строку не ловит. Ловят её хук без matcher, matcher `""` или `"*"` и регулярное
  выражение, которое совпадает с пустой строкой.
- **Лимит.** После восьми продолжений подряд от Stop-хуков Claude Code отменяет следующий блок и
  завершает ход; счётчик сбрасывается, когда Claude вызывает инструмент. Число задаёт
  `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` (Stop и SubagentStop, по умолчанию 8, `0` снимает лимит). Хук
  просит переделать, но не гарантирует, что непроверенное не уйдёт дальше.
- **`PostToolUse` на `Agent`.** "When a foreground Agent call completes, your PostToolUse hook receives
  the subagent's result" в `tool_response`. У фонового субагента там `status: "async_launched"` и
  данные запуска, без отчёта.
- **Хук во frontmatter субагента проекта.** Под `claude -p` в папке, которой не доверяли, он "Not
  used" (permissions, таблица "What runs before you trust a folder"); хуки из файлов настроек там
  "Used". Интерактивно такие хуки работают только после диалога доверия к папке.
- **Режим auto.** С v2.1.271 субагенты, которых Agent запускает локально (кроме форков), в auto
  получают инструмент `SubagentHandback` и отдают отчёт через него (tools reference). Тогда
  `last_assistant_message` "is not the delivered report": отчёт лежит в `tool_input.message` вызова `SubagentHandback`, и его видит хук `PreToolUse` или `PostToolUse` с
  matcher `SubagentHandback`. В результате Agent вместо отчёта короткая заметка о передаче (hooks
  reference).
- **Скрипт, читающий `stream-json`.** Если `claude -p` запущен с
  `--output-format stream-json --verbose`, в потоке есть сообщения основного разговора (у них
  `parent_tool_use_id` равен `null`, headless). Страница agent loop: `UserMessage` "emitted after
  each tool execution with the tool result content sent back to Claude", а "A subagent returns only
  its final response". Значит, `tool_result` вызова Agent на переднем плане это строка потока с
  отчётом субагента. С `--output-format json` скрипт получает только итоговое сообщение `result`
  (урок 2).

В этом уроке вы пишете проверку для своего пайплайна. Хук `SubagentStop` разбираем, но не строим:
роли пайплайна не субагенты, а хук во frontmatter под `-p` не сработал бы.

## Частые ошибки

- Одна проверка перед отчётом, когда synthesizer уже съел плохую находку.
- Проверять формат регулярным выражением, а не то, что строка есть в файле.
- Искать цитату через `re.search`: метасимволы ломают поиск.
- Пропускать `True` как номер строки.
- Нормализовать путь (`./a`, `a//b`) вместо того, чтобы отклонить.
- Отбрасывать находку молча, без журнала.
- Хук `SubagentStop` с matcher `"*"`, который не отличает служебных агентов с пустым `agent_type`.
- Читать `last_assistant_message` в режиме auto.

## Что делать в практике

Вы напишете `pipeline/gate.py`: две функции проверяют находки ревьюеров и итоговые находки synthesizer
по правилам из задания. Потом поставите их в `run.py` на каждый стык, где находки переходят дальше, и
запишете каждое отклонение в журнал. Под конец квиз.
