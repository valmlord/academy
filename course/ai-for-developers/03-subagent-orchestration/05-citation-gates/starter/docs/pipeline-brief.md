# Бриф пайплайна ревью: роли, формы вывода, сбои

Пайплайн invoice-service вызывает три роли по очереди: кодер вносит изменение, ревьюер ищет в нём
проблемы, summarizer пишет человеку короткий итог. Каждая роль отвечает одним JSON-объектом, и
следующий этап читает его без догадок. Этот бриф фиксирует формы вывода один раз; контракты ролей и
схемы в `pipeline/contracts/` должны им соответствовать.

## Формы вывода

### Кодер

Объект с двумя полями, оба обязательны:

- `diff_path` (строка): путь к файлу с diff внесённого изменения;
- `summary` (строка): что изменено, в двух-трёх предложениях.

### Ревьюер

Объект с одним обязательным полем `findings`: массив находок (может быть пустым). Каждая находка
это объект, все шесть полей обязательны:

- `id` (строка): идентификатор находки, например `F-3a9c01d2e4`;
- `file` (строка): путь к файлу от корня проекта;
- `line` (целое число): номер строки;
- `quote` (строка): дословный текст этой строки;
- `claim` (строка): что не так, одним предложением;
- `severity` (строка): одно из `high`, `medium`, `low`.

"Место" находки это `file` + `line` + `quote`: по ним следующий этап находит строку, не перечитывая
весь проект.

### Summarizer

Объект с двумя полями, оба обязательны:

- `summary` (строка): итог для человека;
- `finding_ids` (массив строк): `id` находок, на которых итог основан.

## Примеры пригодного вывода

Кодер:

```json
{"diff_path": "runs/2026-11-03-late-fee/coder.diff", "summary": "Пеня теперь округляется до целых центов вниз; добавлен тест на границу 30 дней."}
```

Ревьюер, две находки:

```json
{"findings": [
  {"id": "F-3a9c01d2e4", "file": "src/invoices/late_fee.py", "line": 18, "quote": "    days = (today - due).days + 1", "claim": "Лишний день: счёт, оплаченный в срок, получает пеню за один день.", "severity": "high"},
  {"id": "F-77b0e5c912", "file": "tests/test_late_fee.py", "line": 41, "quote": "    def test_fee_after_due_date(self):", "claim": "Нет теста на оплату ровно в день срока.", "severity": "medium"}
]}
```

Ревьюер, проблем не найдено:

```json
{"findings": []}
```

Summarizer:

```json
{"summary": "Изменение пени содержит ошибку на один день; нужен тест на оплату в день срока.", "finding_ids": ["F-3a9c01d2e4", "F-77b0e5c912"]}
```

## Вывод, который следующий этап использовать не может

Такой вывод схема роли должна отклонять:

- нет обязательного поля (у объекта роли или у находки);
- у поля другой тип, чем указан выше: например, `summary` числом, `finding_ids` строкой вместо массива,
  находка строкой вместо объекта;
- `line` не целое число: `"18"` (строка), `18.5`, `true`;
- `severity` не из трёх значений: например, `"critical"`;
- `findings` не массив: например, объект `{}` или строка.

Примеры:

```json
{"summary": "Пеня исправлена."}
```

(кодер без `diff_path`)

```json
{"findings": [{"id": "F-3a9c01d2e4", "file": "src/invoices/late_fee.py", "line": "18", "quote": "    days = (today - due).days + 1", "claim": "Лишний день.", "severity": "high"}]}
```

(`line` строкой)

```json
{"findings": [{"id": "F-3a9c01d2e4", "file": "src/invoices/late_fee.py", "line": 18, "quote": "    days = (today - due).days + 1", "claim": "Лишний день.", "severity": "critical"}]}
```

(`severity` вне перечня)

```json
{"summary": "Есть ошибка в пене.", "finding_ids": "F-3a9c01d2e4"}
```

(`finding_ids` строкой)

Диапазоны (номер строки не больше длины файла, цитата совпадает с файлом) схема не проверяет: это
работа проверки на стыке, к ней курс вернётся позже.

## Сбои вызова и их виды

`call_role` возвращает объект только при успешном ответе со структурным выводом. Любой другой исход
даёт `RoleCallError` с одним из трёх видов (`kind`):

| Что вернул `claude -p` | Код выхода | Вид |
|---|---|---|
| `subtype: "success"` и есть `structured_output` | 0 | ответ (не ошибка) |
| `subtype: "success"`, но `structured_output` нет, а в `result` текст, похожий на JSON | 0 | `no-structured-output` |
| `subtype: "error_max_structured_output_retries"` | не 0 | `no-structured-output` |
| `subtype: "error_max_budget_usd"` | не 0 | `budget` |
| `subtype: "error_max_turns"` | не 0 | `failed` |
| `subtype: "error_during_execution"` | не 0 | `failed` |
| ошибка аутентификации: `subtype: "success"`, `is_error: true`, в `result` текст `Failed to authenticate: ...` | не 0 | `failed` |
| сообщения `result` нет вовсе (CLI отказался запускаться) | не 0 | `failed` |

`result` у `RoleCallError` это разобранное сообщение `result`, если вызов его напечатал, иначе `None`.

## Пайплайн: прогон, журнал передач, отчёт

`pipeline/run.py --task FILE --acceptance FILE --run-dir DIR` вызывает роли по очереди: кодер, ревьюер,
summarizer, каждую один раз. Получить ответ роли с сообщением `result` можно функцией
`call_role_with_result` из `pipeline/claude_call.py`: она возвращает пару (проверенный объект, сообщение
`result`), а при сбое поднимает тот же `RoleCallError`, что и `call_role`.

Что получает каждая роль:

- кодер: задачу;
- ревьюер: изменение (diff из файла `diff_path` кодера, путь от корня проекта) и критерии приёмки,
  текстом или путём к файлу; пояснений кодера (`summary`, текст `result`) ревьюер не получает;
- summarizer: все находки ревьюера (`id`, `file`, `line`, `quote`, `claim`, а также `severity`, по которой
  его контракт решает, можно ли принимать), текстом или путём к файлу, и ничего из пояснений кодера и
  ревьюера. Текст, который несёт вызов (stdin, позиционный промпт, значения системного промпта), не
  больше 16 КБ; длинный контракт передаётся файлом.

Первый упавший вызов останавливает пайплайн: дальше ни одного вызова, код выхода 1, отчёта нет.

Все файлы прогона лежат в каталоге прогона (`--run-dir`), и пока идёт вызов, тоже. В проекте остаётся
только изменение кодера.
Имена файлов в каталоге прогона: латинские буквы, цифры, `_`, `-`, `.`.

### Журнал передач: `<каталог прогона>/handoffs.jsonl`

Одна строка JSON на каждый сделанный вызов, упавшие тоже, в порядке вызовов:

| Поле | Значение |
|---|---|
| `role` | `coder`, `reviewer` или `summarizer` |
| `model` | модель, переданная в вызов, или ключ `modelUsage` из сообщения `result` |
| `session_id` | `session_id` сообщения `result`, как вернул вызов; `null`, если сообщения нет |
| `subtype` | `subtype` сообщения `result`, как вернул вызов; `null`, если сообщения нет |
| `total_cost_usd` | `total_cost_usd` сообщения `result`; `0`, если сообщения нет |
| `prompt_bytes` | размер промпта в байтах UTF-8 (не в символах): stdin плюс позиционный промпт, без системного промпта |
| `status` | `ok`, если роль вернула проверенный объект, иначе `failed` |

У упавшего вызова сообщение `result` берётся из `RoleCallError.result`. Другие поля можно добавлять.

### Отчёт: `<каталог прогона>/report.json`

Пишется только когда все три роли ответили:

- `summary`: `summary` роли summarizer;
- `finding_ids`: `finding_ids` роли summarizer;
- `total_cost_usd`: сумма `total_cost_usd` всех сделанных вызовов, числом JSON, без округления.

## Fan-out: три раздела ревью и synthesizer

С этого места пайплайн вызывает роли так: кодер, затем три ревьюера разделов одновременно (`security`,
`performance`, `tests`), затем synthesizer, затем summarizer. Роль `reviewer` из урока 3 в этом пайплайне
не вызывается: её работу делят три раздела. Её контракт и схема остаются в `pipeline/contracts/` как
образец.

### Формы вывода разделов и synthesizer

Ревьюер раздела (`security`, `performance`, `tests`) отвечает как ревьюер урока 3: объект с одним
обязательным полем `findings`, массивом находок (может быть пустым). У находки раздела семь обязательных
полей: шесть полей находки ревьюера и `section` (строка), равное разделу этого ревьюера. Находка с
`section` другого раздела для следующего этапа непригодна, и схема раздела её отклоняет.

Synthesizer отвечает объектом с одним обязательным полем `findings`: массивом итоговых находок (может быть
пустым). У итоговой находки семь обязательных полей: `id`, `file`, `line`, `quote`, `claim`, `severity`,
как у находки ревьюера, и `source_ids` (массив строк): `id` исходных находок разделов, из которых она
собрана. Две находки разных разделов об одной строке synthesizer может свести в одну, тогда в `source_ids`
оба `id`. Раздел итоговой находки виден по её `source_ids`.

Примеры пригодного вывода:

```json
{"findings": [{"id": "F-3a9c01d2e4", "file": "src/invoices/late_fee.py", "line": 18, "quote": "    days = (today - due).days + 1", "claim": "Лишний день: счёт, оплаченный в срок, получает пеню.", "severity": "high", "section": "tests"}]}
```

(раздел `tests`)

```json
{"findings": [{"id": "F-90d1c2b3a4", "file": "src/invoices/late_fee.py", "line": 18, "quote": "    days = (today - due).days + 1", "claim": "Пеня начисляется за день оплаты.", "severity": "high", "source_ids": ["F-3a9c01d2e4", "F-5be07a1c33"]}]}
```

(synthesizer, одна итоговая находка из двух исходных)

Непригодный вывод, кроме перечисленного выше для всех ролей:

- у находки раздела нет `section`, или в нём другой раздел;
- у итоговой находки нет `source_ids`, или это не массив строк.

Пустой `source_ids` тоже непригоден, но схема в подмножестве курса этого не выразит: такую находку
отклонит проверка на стыке (урок 5).

Схемы всех ролей попарно различаются. Схемы трёх разделов различаются тем, какой `section` они принимают.

### Что получает каждая роль

- Раздел: изменение (diff из `diff_path` кодера), текстом или путём к файлу; критерии приёмки можно
  передать так же. Ни ответа другого раздела, ни пояснений кодера (`summary`, текст `result`).
- Synthesizer: каждую находку каждого раздела, который ответил, с полями `id`, `file`, `line`, `quote`,
  `claim`, `section`, текстом или путём к файлу, и ничего из рассказов ролей (текст `result` любой роли,
  `summary` кодера). `severity` находок передать можно и полезно: из них synthesizer выводит `severity`
  итоговой находки. Это поле не рассказ роли, а значение из её структурного вывода. Текст, который несёт
  вызов (stdin, позиционный промпт, значения системного промпта), не больше 16 КБ.
- Summarizer: итоговые находки synthesizer (`id`, `file`, `line`, `quote`, `claim`, а также `severity`, по
  которой его контракт решает, можно ли принимать), текстом или путём к файлу, и ничего из рассказов ролей.
  Тот же предел 16 КБ.

### Порядок, сбои, код выхода

- Каждая роль вызывается не больше одного раза за прогон, упавший вызов не повторяется.
- Три раздела вызываются одновременно: все три запущены раньше, чем закончился любой из них.
- Synthesizer вызывается после того, как закончились все три раздела, если хоть один из них ответил, даже
  когда находок нет. Summarizer вызывается после synthesizer.
- Упал кодер: дальше ни одного вызова, код выхода 1, отчёта нет.
- Упал один или два раздела: остальные доводят работу, пайплайн идёт дальше, упавшие разделы попадают в
  `unreviewed`.
- Упали все три раздела: synthesizer и summarizer не вызываются, код выхода 1, отчёта нет.
- Упал synthesizer или summarizer: дальше ни одного вызова, код выхода 1, отчёта нет.
- Когда отчёт записан, код выхода 0.

### Журнал передач

Как в уроке 3, по строке на каждый сделанный вызов, на каждый вызов раздела тоже, упавшие тоже. Строки
вызовов, которые шли одновременно, могут стоять в любом порядке. В `role` имя роли: `coder`, `security`,
`performance`, `tests`, `synthesizer` или `summarizer`.

### Отчёт

К полям урока 3 (`summary` и `finding_ids` роли summarizer, `total_cost_usd`) добавляются:

- `unreviewed`: массив имён разделов, вызов которых упал; пустой, если ответили все три;
- `status`: `incomplete`, если `unreviewed` не пуст; иначе `findings`, если у synthesizer есть итоговые
  находки, и `clean`, если их нет.

`total_cost_usd` это сумма по всем сделанным вызовам, упавшие разделы тоже.

## Проверка на стыках

Находки переходят дальше на двух стыках: от разделов к synthesizer и от synthesizer к summarizer (и в отчёт).
На каждом стыке `pipeline/gate.py` проверяет место находки по правилам G1-G4 задания урока 5. Снимок, против
которого проверяется место, это корень проекта: `file` в находке записан от него.

Каждая отклонённая находка записывается строкой JSON в `<каталог прогона>/gate.jsonl`:

| Поле | Значение |
|---|---|
| `id` | `id` отклонённой находки |
| `joint` | роль, к которой находка попала бы следующей: `synthesizer` для находки раздела, `summarizer` для итоговой |
| `rule` | правило, которое находка нарушает: `G1`, `G2`, `G3` или `G4` |

Другие поля можно добавлять. Отклонённая находка дальше не идёт: ни в промпт, ни в файл, на который промпт
ссылается, ни в `finding_ids` отчёта. `accepted` для `check_synthesis` это находки разделов, которые прошли
первый стык. `status` отчёта считается по итоговым находкам, которые прошли второй стык. Если второй стык
не пропустил ни одной, summarizer всё равно вызывается, с пустым списком находок, а `status` отчёта `clean`.
