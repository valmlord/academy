# Задание: развёртывание в Docker и изменение требования

Время: около 90 минут (около 80 из них практика):

- теория 10;
- Dockerfile для API и страницы 20;
- `compose.yaml` с проверкой здоровья (и подкоманда сервера для неё) 20;
- README 10, `AGENTS.md` 10;
- видимое изменение `GET /bookings/{bookingId}` через вашего агента 20.

Время своего запуска `docker compose up --build` (сборка образов) сюда не входит.

## Что в рабочей папке

Эталонное состояние урока 7: всё из уроков 1-6, набор тестов API в `backend/apitest/` и `make ci`
с проверкой дрейфа. Нового нет: ни `compose.yaml`, ни Dockerfile, ни `AGENTS.md`. Сервер стартера
без `CALENDAR_NOW` берёт время своего запуска и дальше его не двигает. Для учебного развёртывания
этого хватает, но настоящему сервису нужно текущее время на каждый запрос.

## Что сделать

1. **Подкоманда проверки здоровья.** Например `server healthcheck`: спрашивает свой
   `GET /event-types` на `127.0.0.1:$PORT` и завершается с кодом 0 только на 200. Её работу ни одна
   проверка не запускает; статическая проверка смотрит только, что compose вызывает сам сервер.
2. **Dockerfile для `api` и для `web`**, многостадийные: стадия сборки с инструментами, последняя
   стадия только с программой, не от root, с закреплённым базовым образом. В образе `api` должна быть
   база часовых поясов.
3. **`compose.yaml` в корне репозитория:** сервисы `api` и `web`, `web` зависит от `api`, у `web`
   `CALENDAR_API_URL=http://api:8080`, наружу открыт только `web`, у `api` проверка здоровья, никаких
   переменных тестов.
4. **Свой запуск.** На своей машине выполните `docker compose up --build`, создайте расписание и вид
   встречи через `/api/` страницы, откройте страницу. Вставьте вывод в `docs/deploy-run.md`.
5. **README**: раздел о развёртывании. **`AGENTS.md`**: порядок работы в репозитории и признак
   "готово".
6. **Видимое изменение через агента.** Новое требование: `GET /bookings/{bookingId}` возвращает 200
   и бронирование с текущим статусом (как в последнем ответе сервера о нём: 201 или отмена), а для
   неизвестного `id` 404 `not_found`. Дайте задачу своему агенту и проследите, что он идёт по
   `AGENTS.md`: требование в `docs/spec.md`, операция в `contract/`, `make gen` и коммит клиента,
   сервер, тест в наборе API, `make ci` проходит.
7. **Скрытое изменение** делаете не вы. Ваша часть: репозиторий, в котором агент справится сам.

## Правила `docker-static`

Образы не собираются и не запускаются: проверка только читает файлы. Ни один ваш процесс не
запускается.

**Файлы.**

- `compose.yaml` в корне репозитория.
- Рядом с ним нет других входов `docker compose up`: файлов переопределения
  `compose.override.yaml`, `compose.override.yml`, `docker-compose.override.yaml`,
  `docker-compose.override.yml` (compose сам добавляет такой файл к `compose.yaml`), второго файла
  compose `compose.yml`, `docker-compose.yml`, `docker-compose.yaml` и файла `.env` (compose
  читает его сам, а `COMPOSE_FILE` в нём меняет набор файлов compose). Символические ссылки с
  этими именами тоже не принимаются. Проверка читает только `compose.yaml`.
- Dockerfile каждого из `api` и `web` берётся из его `build`: строка с путём к контексту, тогда
  `<контекст>/Dockerfile`; или словарь с `context` и необязательным `dockerfile` (путь относительно
  контекста).
- Пути `context` и `dockerfile` относительные, только из букв, цифр и `.` `_` `/` `-`: без `~`,
  `:`, `@`, URL, абсолютного пути и `..` наружу. Путь с `github.com/` в начале compose читает как
  адрес Git-репозитория, он тоже не принимается. Путь не выходит из репозитория и через
  символическую ссылку.
- Каждый файл обычный (не символическая ссылка), не больше 256 КБ и в UTF-8.

**Как читается Dockerfile.**

- Директивы `syntax`, `escape` (только `\` или `` ` ``) и `check`, только в начале файла, каждая не
  больше одного раза. Имя директивы в любом регистре, пробелы вокруг `=` можно. `#` директивы в
  первой колонке: директива с отступом не принимается (BuildKit читает её как директиву, а
  `syntax` ищет только без отступа).
- `syntax` выбирает образ, который читает весь Dockerfile. Принимается только `docker/dockerfile`
  с тегом `1`, `1.N` или `1.N.M` и (или) дайджестом sha256, как у базовых образов, например
  `# syntax=docker/dockerfile:1`. Строка `#!` в начале файла не принимается: BuildKit её
  пропускает и ищет `syntax` дальше.
- Из пробельных и управляющих символов только пробел, табуляция и перевод строки (`\n` или
  `\r\n`). Перевод строки одним `\r`, перевод страницы, неразрывный пробел, NUL не принимаются:
  проверка и BuildKit могли бы по-разному разбить на них строки.
- Строки комментариев, в том числе внутри продолжения строки.
- Продолжение строки: символ escape последний в строке, после него только пробелы и табуляция.
  Два escape подряд в конце (`\\`) не продолжение. Продолжение склеивается без пробела, как в
  BuildKit. Пустая строка или строка из пробелов внутри продолжения не принимается: BuildKit её
  пропускает и продолжает ту же инструкцию.
- Heredoc после `RUN`, `COPY`, `ADD`: тело пропускается. `<<` принимается только отдельным словом
  `<<ИМЯ`, `<<-ИМЯ`, `<<'ИМЯ'` или `<<"ИМЯ"` (имя из букв, цифр и `_`, перед `<<` можно номер
  дескриптора, `3<<EOF`), и в такой строке нет `\`, `$` и `[`. Любое другое `<<` не принимается:
  `"<<EOF"`, `x<<EOF`, `<< EOF`, `<<"A B"`, `<<` в других инструкциях, в том числе в `ONBUILD`.
  На таких строках BuildKit может иначе решить, где тело heredoc.
- Ровно 18 инструкций в любом регистре: ADD, ARG, CMD, COPY, ENTRYPOINT, ENV, EXPOSE, FROM,
  HEALTHCHECK, LABEL, MAINTAINER, ONBUILD, RUN, SHELL, STOPSIGNAL, USER, VOLUME, WORKDIR.
- До первого `FROM` только `ARG`, в формах вроде `ARG A=1 B="x"`.

**FROM.** Форма `FROM [--platform=<платформа>] <образ> [AS <имя>]`. `AS` в любом регистре. Имя
стадии приводится к нижнему регистру, должно подходить под `[a-z][a-z0-9-_.]*` и не повторяться.
Курс принимает только эти формы:

| Форма | Вердикт |
|---|---|
| F1 `scratch`, ровно строчными (`SCRATCH` это не scratch, и правила имени образа он не проходит) | принимается |
| F2 имя более ранней стадии, ровно как его хранит BuildKit, строчными | принимается |
| F3 `имя:тег`, тег не `latest` | принимается |
| F4 `имя@sha256:<64 строчные шестнадцатеричные цифры>` | принимается |
| F5 `имя:тег@sha256:<64 цифры>`, тег не `latest` | принимается |
| F6 F3-F5 с адресом реестра `хост[:порт]` и частями пути, например `gcr.io/distroless/static-debian13:nonroot`. Первая часть считается реестром, только если в ней есть `.` или `:` или это `localhost`. Части пути: строчные буквы, цифры и разделители `.`, `_`, `__`, `-` | принимается |
| F7 `--platform=<значение>` перед любой из форм, в том числе `--platform=$BUILDPLATFORM` | принимается |
| F8 `$NAME` или `${NAME}` в образе, где `ARG NAME=...` объявлен до первого `FROM` со значением по умолчанию, а после подстановки получается F3-F6 (имя стадии или `scratch` за `ARG` не принимается) | принимается |
| R1 образ без тега и без дайджеста (это `latest`) | отклоняется |
| R2 тег `latest`, в том числе вместе с дайджестом | отклоняется |
| R3 `ARG` без значения по умолчанию; формы с модификатором `${NAME:-x}`, `${NAME:+x}` и другие | отклоняется |
| R4 любой флаг `FROM`, кроме `--platform=...` | отклоняется |
| R5 имя, которое совпадает с именем стадии только без учёта регистра, например `FROM Build` после `AS build` | отклоняется |
| R6 дайджест не sha256, например `@sha512:...`. Курс принимает только дайджест sha256 | отклоняется |

**USER.**

- Один аргумент `пользователь[:группа]`, каждая часть это имя `[A-Za-z_][A-Za-z0-9_.-]*` или
  число. Переменные не принимаются.
- Цепочка последней стадии: она сама и стадии, от которых она строится по имени (F2). Действует
  **последний** `USER` по этой цепочке (от самой ранней стадии к последней). Он должен быть, и его
  пользователь не `root` и не 0. Число сравнивается как число, поэтому `USER 00` и `USER 000:0`
  это тоже root. `USER root` после `USER nonroot` проваливает проверку, а `USER` в стадии вне
  цепочки не считается.
- В стадиях, от которых строится последняя стадия, нет `ONBUILD`: BuildKit выполняет его в
  стадии, которая строится от неё, и его результат попадает в последнюю стадию.
- В цепочке последней стадии нет `ENV` и `ARG` с `CALENDAR_NOW` и `CALENDAR_BOOKING_DELAY_MS`.
- Правила для обоих Dockerfile, `api` и `web`.
- Без `USER` последняя стадия не проходит, даже на образе `...:nonroot`: статическая проверка не
  видит пользователя по умолчанию в образе. Пишите `USER` явно, например `USER nonroot:nonroot`
  или `USER 65532:65532`.

**Как читается `compose.yaml`.** Проверка понимает только часть YAML:

- без табуляций и других управляющих символов, кроме перевода строки (`\n` или `\r\n`);
  комментарий `#` в начале строки или после пробела;
- один документ (`---` в начале можно);
- только блочные словари и списки, в том числе список на отступе родительского ключа и элементы
  `- ключ: значение`;
- не принимаются: `[` `{` (однострочные списки и словари), `&` `*` (якоря и ссылки), `<<`
  (слияние), `|` `>` (блочные строки), `!` (теги), а также `%`, `@`, `` ` `` в начале значения;
- повторённый ключ не принимается;
- значения без кавычек, которые YAML 1.1 читает как логические, не принимаются: y, Y, yes, Yes,
  YES, n, N, no, No, NO, true, True, TRUE, false, False, FALSE, on, On, ON, off, Off, OFF;
- значения без кавычек, которые YAML 1.1 читает как число в шестидесятеричной записи (после
  каждого `:` число 0-59), не принимаются: `22:22` и `3000:30` отклоняются, а `3000:3000`
  принимается. Порты надёжнее всегда брать в кавычки: `- "3000:3000"`;
- `$` в любом значении не принимается, в кавычках тоже: подстановку переменных проверка не
  раскрывает;
- кавычки: двойные по правилам JSON, одинарные с `''` внутри.

**Правила compose.**

- В корне файла только ключи `services` и `volumes`: `include`, `networks`, `x-...` и другие не
  принимаются.
- `volumes` в корне это словарь именованных томов без настроек: `data:` без значения. `driver` и
  `driver_opts` могут подключить каталог хоста.
- Есть сервисы `api` и `web`, каждый словарь, и других сервисов нет.
- Ключи сервиса только из списка курса: у `api` `build`, `environment`, `healthcheck`, `volumes`,
  `restart`; у `web` `build`, `environment`, `depends_on`, `ports`, `healthcheck`, `restart`.
  Поэтому не принимаются, например, `user` (пользователя задаёт `USER` в Dockerfile), `image`
  (образ собирается из `build`), `extends`, `command`, `entrypoint`, `privileged`, `cap_add`,
  `network_mode`, `pid`, `expose`, `profiles`, а у `web` и `volumes`.
- `build` словарём: только `context`, `dockerfile`, `args`, `target`.
  - `build.args` не задаёт `ARG`, объявленный до первого `FROM`: такой `ARG` выбирает базовый
    образ, а проверка читает `FROM` по значению по умолчанию. `ARG` внутри стадии задавать можно.
  - `build.args` не задаёт имён с `BUILDKIT_`: они настраивают сам BuildKit, а `BUILDKIT_SYNTAX`
    подменяет программу, которая читает Dockerfile.
  - `build.target`, если есть, равен имени последней стадии из её `AS` без учёта регистра, как
    сравнивает BuildKit: проверка читает базовый образ и `USER` последней стадии.
- `volumes` у `api` это список строк `ИМЯ:/путь`, можно с `:ro` или `:rw`, где `ИМЯ` объявлено в
  корневом `volumes`. Путь хоста (bind), относительный путь и длинная форма словарём не
  принимаются.
- В `healthcheck` только `test`, `interval`, `timeout`, `retries`, `start_period`,
  `start_interval` (без `disable`).
- Ни у одного сервиса нет `env_file`.
- Ни у одного сервиса нет `CALENDAR_NOW` и `CALENDAR_BOOKING_DELAY_MS` в `environment` (списком
  `- ИМЯ=значение` или словарём).
- `ports` есть только у `web`.
- У `web`: в `environment` `CALENDAR_API_URL` ровно `http://api:8080`; `depends_on` называет `api`
  (списком или словарём); `ports` непустой список.
- У `api` `healthcheck.test` это блочный список строк, не меньше 3 элементов: первый `CMD`, второй
  равен исполняемому файлу последней стадии образа `api`, дальше подкоманда (третий и следующие
  элементы проверка не читает). Исполняемый файл это
  первый элемент последнего `ENTRYPOINT` по цепочке последней стадии, а если `ENTRYPOINT` нет, то
  последнего `CMD`. Он должен быть в форме exec (JSON-массив), иначе проверка не знает путь к
  серверу. Например `ENTRYPOINT ["/app/server"]` и в compose `- CMD`, `- /app/server`,
  `- healthcheck`, каждый на своей строке. Однострочную форму из справки compose
  (`["CMD", ...]`) проверка не принимает, а оболочки, `curl` и `wget` в образе distroless нет.

## Готово, когда

### Проверка `docker-static`

Все правила выше выполнены. У стартера: "нет файла compose.yaml в корне репозитория".

### Проверка `visible-change-applied`

Четыре части по очереди, в каждой не больше 15 строк, потом "и ещё N расхождений":

1. **Контракт.** `contract-matches` урока 2 тем же кодом, но против обязательного контракта с новой
   операцией: `GET /bookings/{bookingId}`, параметр пути `bookingId` (строка), ответ 200 `Booking`,
   ответ 404 problem+json (`not_found`).
2. **Пробы `api-bookings-conformance` урока 5** без изменений, тем же кодом.
3. **Пробы `booking-integrity` урока 5** без изменений, тем же кодом.
4. **`GET /bookings/{bookingId}` на вашем сервере.** `make -s build` (180 секунд) в свежей копии,
   `bin/server` с `CALENDAR_NOW` как в уроке 4, `CALENDAR_BOOKING_DELAY_MS=0` и свежим
   `CALENDAR_DATA_DIR`. Через `POST`: расписание в одном из 8 поясов, 08:00-18:00 каждый день; вид
   встречи 30 минут, шаг 30, без буферов и уведомления, окно 30 суток; 3 бронирования на разные дни
   через 2-19 дней, второе отменено. Потом:
   - `GET` подтверждённого: 200, тело по схеме нового контракта и равно ответу 201 (даты как
     моменты);
   - `GET` отменённого: 200, тело равно ответу на отмену (`status` `cancelled`);
   - неизвестный `id`: 404 `not_found`;
   - `id` вида встречи вместо бронирования: 404 `not_found`;
   - `POST /bookings/{id}`: 405, в `Allow` есть `GET`;
   - отмена третьего, потом его `GET`: 200, тело равно ответу на эту отмену.

Ответы проверяются так же, как в уроке 4: схема контракта, problem+json, `status` в теле равен
статусу ответа.

### Проверка `visible-change-gate`

Гейт урока 7 с теми же правилами, порядком, ограничением 60 секунд на прогон, дрейфом (3a)-(3g),
K1-K7 и сообщениями. Отличия:

- сервер проверки работает по контракту с `GET /bookings/{bookingId}`;
- прогонов против сервера 25: 5 против правильного и 20 против сервера с ошибкой, это 18 ошибок
  урока 7 и ещё две:

  | Ошибка | Требование |
  |---|---|
  | `GET /bookings/{bookingId}` отвечает 200 на неизвестный `id` (с телом бронирования под этим `id`) вместо 404 `not_found` | новое требование о `GET /bookings/{bookingId}` |
  | `GET /bookings/{bookingId}` показывает отменённое бронирование подтверждённым (только эта операция) | то же |

У стартера обе новые ошибки проходят: в его наборе нет теста на эту операцию.

### Проверка `hidden-change`

- Агент получает требование, которого нет в этом задании, и выполняет его в свежей копии вашей
  рабочей папки, без вас. Он получает только текст требования: как здесь работать, он узнает из
  репозитория (`AGENTS.md`). Ограничения: 3600 секунд и 8 долларов на попытку.
- Потом проверочный скрипт по шагам, гейт только если всё до него прошло:
  1. контракт: `contract-matches` против обязательного контракта новой версии;
  2. пробы `api-bookings-conformance`, `booking-integrity` и `GET /bookings/{bookingId}` (ответы
     по схеме новой версии);
  3. пробы нового требования в 4 поясах, один из них на дату перевода часов;
  4. в `docs/spec.md` есть строка требования вида `- **REQ-NN** WHEN ... THE SYSTEM SHALL ...`, в
     которой названо то, что изменение добавляет в контракт (проверяется только форма);
  5. `client-in-sync` урока 6;
  6. гейт урока 7 над новой версией: 5 прогонов против правильного сервера и 23 против сервера с
     ошибкой (20 из `visible-change-gate` и 3 ошибки нового требования).
- Каждый запуск скрипта берёт новое случайное зерно, из него всё случайное в пробах и в гейте.
  Последняя строка вывода всегда `seed N`: по нему ментор повторит запуск. Попытка это один запуск
  агента и один запуск скрипта, без автоматического повтора.
- Пока платформа не запускает такие проверки (#39), эта показана как ожидающая. Засчитывается ли
  время скрипта в 3600 секунд, решит #39.

### Рубрика `deploy-rubric`

Ментор оценивает `compose.yaml`, `**/Dockerfile`, `README.md`, `AGENTS.md`, `docs/deploy-run.md` и
`backend/**/*.go` по 5 критериям, 0-2 балла каждый. Нужно не меньше 70% суммы, и ни один критерий
не может получить 0. То, что уже проверила `docker-static`, ментор заново не оценивает.

1. README воспроизводит `docker compose up`: команда, что за сервисы и какой порт открыт, как

## Окружение проверки

`docker-static` только читает файлы. Остальные проверки как в уроках 5 и 7: снимок рабочей папки
(обычные файлы, `.git` входит, `__pycache__` нет, символические ссылки только внутрь), свежая копия
на каждую сборку и каждый прогон, окружение урока 7 (`PATH`, пустые `HOME`, `TMPDIR`, `XDG_*`,
`NUXT_TELEMETRY_DISABLED=1`, случайный `TZ` не UTC, переменные Go, больше ничего), сети нет.

## Как работать (совет, не проверяется)

- Подкоманду проверки здоровья проверьте без Docker: `make -s build`,
  `HOST=127.0.0.1 PORT=8080 bin/server &`, потом `PORT=8080 bin/server healthcheck; echo $?`.
- У себя: `docker compose up --build`, во втором терминале `docker compose ps` (у `api` должно быть
  `healthy`), потом запросы через `http://localhost:<порт web>/api/...`. Команды и вывод вставьте в
  `docs/deploy-run.md`.
- Видимое изменение дайте агенту одной фразой требования, без подсказок по файлам. Если он
  пропустил шаг, поправьте `AGENTS.md`, а не результат: скрытое изменение агент будет делать по
  нему же.
- Перед сдачей: `make ci` без адреса и с адресом своего сервера, как в уроке 7.
