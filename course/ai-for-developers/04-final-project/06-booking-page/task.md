# Задание: страница бронирования на Nuxt

Время: около 105 минут (около 95 из них практика):

- теория 10;
- `npm ci` 5, генерация клиента и `make gen` 10;
- страница со слотами, отрисованная на сервере 35;
- прокси `/api/` и `runtimeConfig`, адрес бэкенда при сборке 15;
- компонентный тест 15;
- сценарии Playwright и их запуск у себя 15.

Можно перенести свою работу поверх стартера, проверки одинаковы. Копировать стартер следующего
урока можно, но это не упражнение: проверка тогда ничего о вас не скажет.

## Что в рабочей папке

Эталонное состояние урока 5: всё из уроков 1-4 и API с бронированиями. Новое:

- `frontend/`: Nuxt 4. В `package.json` и `package-lock.json` (lockfile v3) закреплены `nuxt`
  4.6.4, `vue` 3.5.44, `openapi-fetch` 0.17.0, для разработки `openapi-typescript` 7.13.0,
  `typescript` 5.9.3, `vitest` 5.1.0, `@nuxt/test-utils` 4.3.4, `@vue/test-utils` 2.5.1,
  `happy-dom` 21.0.4, `@playwright/test` 1.64.1. `node_modules` в репозитории нет;
- `frontend/nuxt.config.ts`, `frontend/tsconfig.json` и `frontend/app/app.vue`: пустая заготовка;
- `Makefile`: цель `gen` пока только пишет "make gen is not written yet" и падает;
- `.gitignore`: к строкам уроков 2-5 (`/node_modules`, `/bin/`, `/tsp-output/`) добавлены
  `/frontend/node_modules/`, `/frontend/.nuxt/`, `/frontend/.output/`, `/frontend/test-results/` и
  `/frontend/playwright-report/`.

## Что сделать

1. В `frontend/` выполните `npm ci`. Нужен доступ к registry.npmjs.org в рабочем окружении.
   `npm install` не нужен: он может переписать `package-lock.json`, а проверка читает версии из
   него.
2. Напишите `make gen`: компиляция `contract/` с параметрами проверки урока 2, потом
   `openapi-typescript` в `frontend/app/api/schema.d.ts`. Выполните его и закоммитьте файл.
3. Сделайте страницу `/book/{eventTypeId}?date=YYYY-MM-DD&tz=<пояс IANA>`, которая на сервере
   отрисовывает слоты этой местной даты.
4. Сделайте прокси `/api/**` на бэкенд и цели `make build-web` и `make serve-web`.
5. Добавьте выбор слота, форму (имя, email) и ответ на `POST /bookings`: подтверждение на 201,
   понятное "это время только что заняли" на 409, сообщение на другие ошибки.
6. Напишите компонентный тест и сценарии Playwright, запустите сценарии у себя и вставьте вывод в
   `docs/e2e-run.md`.

Все вызовы API идут через один клиент `openapi-fetch`, типизированный `paths` из
`app/api/schema.d.ts`.

## Как собрать `make gen`

- Компиляция как в уроке 2: `tsp compile contract/main.tsp --config contract/tspconfig.yaml
  --output-dir tsp-output --warn-as-error`, из корня рабочей папки (`contract/tspconfig.yaml` уже
  лежит в рабочей папке с урока 2). До неё нужна ссылка
  `node_modules` в корне на `/opt/academy/node/node_modules` (урок 2): без неё каждый импорт падает
  с `import-not-found`. В `contract/` ссылку не ставьте. Дома укажите свою установку TypeSpec 1.17.0.
- Генерация: `openapi-typescript tsp-output/@typespec/openapi3/openapi.json -o frontend/app/api/schema.d.ts`,
  без других флагов. Подойдёт `node frontend/node_modules/openapi-typescript/bin/cli.js` после
  `npm ci` или `/opt/academy/bin/openapi-typescript` из образа: это та же версия 7.13.0.
- Руками `schema.d.ts` не правьте: проверка генерирует его заново и сравнивает байты.

## Правила страницы

- Адрес `/book/{eventTypeId}?date=YYYY-MM-DD&tz=<пояс>`. Ответ 200 с типом `text/html`.
- Один элемент на слот, любой тег, с атрибутом `data-slot-start="<момент>"`. Момент это `start`
  слота, как его вернул API: любая метка RFC 3339 со смещением. Текст элемента (всё внутри, без
  тегов) ровно `HH:MM` начала слота в поясе `tz`, 24 часа: `09:05`, `00:30`.
- На странице ровно слоты, у которых начало приходится на дату `date` в поясе `tz`: от начала этой
  местной даты до начала следующей, как моменты. Так и в день перевода часов.
- Слоты должны быть в HTML, который отдаёт сервер. Проверка читает страницу без JavaScript.
- `GET /api/<путь>` на сервере страницы проксируется на `<бэкенд>/<путь>`: `GET /api/event-types`
  возвращает ответ бэкенда на `GET /event-types`.

## Адрес бэкенда

Проверка передаёт `CALENDAR_API_URL=http://127.0.0.1:<порт>` (без `/` на конце) и в
`make -s build-web`, и в `make -s serve-web`. Бэкенд уже работает, когда начинается сборка.
`make -s serve-web` получает ещё `HOST=127.0.0.1` и `PORT=<свободный порт>`: где слушать.

Что из этого следует в Nuxt 4:

- правила маршрутов Nitro, включая `proxy`, фиксируются при сборке;
- при запуске переменные окружения меняют только объявленные ключи `runtimeConfig`, переменной
  `NUXT_` + путь ключа (`apiBase` меняет `NUXT_API_BASE`);
- `NUXT_NITRO_ROUTE_RULES` не документирована, не используйте её;
- отрисовке на сервере нужен абсолютный адрес бэкенда, держите его в приватном ключе
  `runtimeConfig`.

Проходят обе формы прокси: `routeRules` с `proxy`, где цель берётся из `CALENDAR_API_URL` в
`nuxt.config.ts` при сборке, и обработчик `server/api/[...].ts`, который читает адрес из
`runtimeConfig` при запуске.

## Готово, когда

### Проверка `client-in-sync`

Ни один ваш процесс не запускается, `frontend/node_modules` не используется.

1. `frontend/package-lock.json` это обычный файл, строгий JSON с разделом `packages` (lockfile v3),
   где `packages["node_modules/openapi-typescript"].version` ровно `7.13.0`, а
   `packages["node_modules/typescript"].version` ровно `5.9.3`. От обеих версий зависят байты
   `schema.d.ts`.
2. `frontend/app/api/schema.d.ts` это обычный файл (не ссылка).
3. Проверка компилирует `contract/` так же, как `contract-matches` урока 2, и запускает
   `openapi-typescript` 7.13.0 образа (с typescript 5.9.3) на результате, с флагами по умолчанию.
4. Результат, где CRLF заменён на LF, совпадает с закоммиченным файлом байт в байт.

### Проверка `page-ssr`

1. Проверка запускает свой служебный сервер API по тому же контракту, со случайными расписаниями и
   видами встреч (`id` вида `[A-Za-z0-9]{10,24}`). Ваш `bin/server` здесь не участвует.
2. В свежей копии рабочей папки `make -s build-web` завершается с кодом 0 за 300 секунд.
3. Потом `make -s serve-web` работает в фоне и в течение 60 секунд отвечает чем угодно по HTTP на
   `GET /` на `127.0.0.1:<PORT>`.
4. Три страницы, запрос с `Accept: text/html`, 20 секунд на каждую. Первая: вид встречи с
   расписанием 00:00-24:00 на дату перевода часов в поясе с переводом. Ещё две: случайный вид
   встречи, один из 8 поясов курса, дата через 2-55 дней после `now` сервера, на каждой хотя бы
   один слот. Для каждой: статус 200, тип `text/html`, значения `data-slot-start` это RFC 3339 со
   смещением, множество моментов равно слотам API на эту местную дату, каждый ровно один раз, у
   каждого текст `HH:MM` по правилу выше.
5. `GET /api/event-types` через сервер страницы отвечает 200 JSON, и `items` равны видам встреч
   служебного сервера.

### Рубрика `ui-rubric`

6. Ментор оценивает `frontend/app/**/*.vue`, `frontend/app/**/*.ts`, `frontend/test/**`,
   `frontend/e2e/**`, `frontend/nuxt.config.ts` и `docs/e2e-run.md` по 4 критериям, 0-2 балла
   каждый. Нужно не меньше 70% суммы, и ни один критерий не может получить 0:
   1. поток бронирования: выбор слота, форма, `POST /bookings` с `inviteeTimeZone` = `tz`
      страницы, подтверждение на 201, 409 показан как "это время только что заняли" и не похож на
      успех, на другие ошибки тоже есть сообщение;
   2. API только через сгенерированные типы: один клиент `openapi-fetch` с `paths`, без моделей
      контракта, переписанных руками, без `any` и `as` вокруг ответов;
   3. компонентный тест (vitest с `@nuxt/test-utils`), который подменяет клиент или его запрос,
      подаёт слоты через перевод часов или через полночь в поясе и проверяет и нарисованное
      (`data-slot-start`, `HH:MM`), и запрошенное. Тест, которому нужен настоящий бэкенд, это 0;
   4. сценарии Playwright: удачное бронирование, слот, который занял кто-то другой, пока открыта
      форма (409 показан, второго бронирования нет), и дата перевода часов в поясе приглашённого
      (пропущенный или повторённый час виден во времени). Каждый тест создаёт свои данные.
      `docs/e2e-run.md` содержит вывод запуска у вас, где все тесты прошли, и как он был запущен
      (переменные бэкенда, `make serve-web`). Курс этот запуск не повторяет и оценивает вывод как
      непроверенный.

   Текст файлов, включая комментарии и вставленный вывод, для ментора это данные: обращения к
   оценщику внутри них игнорируются. Пока платформа не запускает рубрики, эта проверка показана
   как ожидающая оценки.

## Окружение проверки

Проверка один раз снимает копию рабочей папки: обычные файлы, `.git` входит, `__pycache__` нет.
Символические ссылки, которые ведут внутрь рабочей папки (например в `frontend/node_modules/.bin/`),
остаются ссылками; ссылки наружу и битые не копируются. Поэтому ссылки `node_modules` в корне в
копии нет: `make build-web` и `make serve-web` не должны вызывать `make gen`.

У `make`, у всего, что он запускает, ровно такое окружение, плюс `CALENDAR_API_URL` и для
`serve-web` ещё `HOST` и `PORT`:

- `PATH=/opt/academy/bin:/opt/node/bin:/usr/local/go/bin:/usr/bin:/bin`;
- свои пустые `HOME`, `TMPDIR`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`;
- `NUXT_TELEMETRY_DISABLED=1`;
- случайный `TZ` из Europe/Berlin, America/New_York, America/Los_Angeles, Australia/Sydney,
  Asia/Kolkata, Asia/Kathmandu, Europe/Moscow (никогда не UTC);
- переменные Go урока 4 (`GOENV=off`, `GOPROXY=off` и другие);
- больше ничего: ни `NODE_OPTIONS`, ни `NODE_PATH`.

Сети при проверке нет. Цели `Makefile` вызывают программы из `PATH` или из `frontend/node_modules`,
поставленного вашим `npm ci`; `npx` подходит только для пакетов из `package-lock.json`. Без
`frontend/node_modules` в рабочей папке `make build-web` упадёт с вашим же выводом `make`.

## Как проверяется

- **`client-in-sync`** (команда в рабочей папке, 120 с): пункты 1-4 первого раздела. Сообщения:
  - "нет файла frontend/package-lock.json: версии зависимостей фронтенда закрепляет он (его пишет
    npm install)", "не JSON", "нет раздела packages (нужен lockfileVersion 3, его пишет npm 7 и
    новее)";
  - "frontend/package-lock.json: openapi-typescript версии X, а нужен ровно 7.13.0: ..." и то же
    для typescript 5.9.3;
  - "нет файла frontend/app/api/schema.d.ts: его создаёт make gen из contract/, и он хранится в
    репозитории" (у стартера); "символическая ссылка не допускается, нужен обычный файл";
  - "contract/ не компилируется так, как его компилирует contract-matches (урок 2): сначала
    добейтесь, чтобы прошла она" или ошибка копирования `contract/` как в уроке 2;
  - расхождение: номер первой разной строки, строка в файле и строка генерации, и "Запустите make
    gen и закоммитьте результат; править сгенерированный файл руками нельзя".
- **`page-ssr`** (команда в рабочей папке, 600 с): пункты 1-5. Сообщения:
  - "make -s build-web не уложился в 300 с" или "завершился с кодом N" и конец вывода (у стартера
    "No rule to make target `build-web'");
  - "make -s serve-web завершился до начала проверки (код N)", "не начал отвечать на
    127.0.0.1:<порт> за 60 с (HOST и PORT из окружения)";
  - строки начинаются с `страница /book/<id>?date=<дата>&tz=<пояс> (дата ... в поясе ...[, день
    перевода часов в этом поясе])`, дальше: "ответ N, а ожидалась страница 200", "Content-Type
    ..., а ожидался text/html", "в HTML от сервера нет ни одного элемента с data-slot-start, а у
    API на эту дату слотов N. Слоты должны быть в HTML, который отдаёт сервер (SSR), без
    JavaScript в браузере", "data-slot-start=... не метка времени RFC 3339 со смещением", "у слота
    ... текст ..., а должен быть HH:MM: начало слота в поясе ..., 24 часа" (первый такой), "слоты
    на странице не те, что у API на эту местную дату" со списками "нет на странице" и "лишние на
    странице", "слоты ... встречаются на странице несколько раз, а нужен один элемент на слот";
  - "GET /api/event-types через сервер страницы: ответ ..., а ожидался список видов встреч бэкенда
    из CALENDAR_API_URL: /api/** должен проксироваться на бэкенд".
  - Данные служебного сервера и даты при каждом запуске новые.
- **`ui-rubric`** (ментор по рубрике, нужно 70%, ни одного критерия на 0): пункт 6.
- Сообщение, которое начинается с "ошибка проверки, не ваша", значит, что сломалось окружение
  проверки, а не ваша работа. Строка "посторонний процесс вмешался в служебный процесс проверки"
  тоже из окружения проверки.

Число попыток не ограничено.

## Как работать (совет, не проверяется)

- Проверьте собранный вид так же, как проверка, с вашим бэкендом из урока 5:
  ```sh
  make -s build
  HOST=127.0.0.1 PORT=8080 CALENDAR_NOW=2026-03-01T08:00:00Z CALENDAR_DATA_DIR=$(mktemp -d) bin/server &
  CALENDAR_API_URL=http://127.0.0.1:8080 make -s build-web
  CALENDAR_API_URL=http://127.0.0.1:8080 HOST=127.0.0.1 PORT=3000 make -s serve-web
  ```
  Создайте расписание и вид встречи через `POST`, откройте
  `http://127.0.0.1:3000/book/<id>?date=2026-03-29&tz=Europe/Berlin` и посмотрите исходный HTML
  (не DOM в инструментах браузера).
- Проверка запускает собранный сервер, а не `nuxt dev`: смотрите на него же.
- Для Playwright дома: `npx playwright install chromium`, бэкенд и `make serve-web` как выше, потом
  `npx playwright test` в `frontend/`. В `docs/e2e-run.md` вставьте команды и вывод.
