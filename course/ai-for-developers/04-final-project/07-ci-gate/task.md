# Задание: тесты API и единая команда make ci

Время: около 125 минут (около 115 из них практика):

- теория 10;
- набор тестов API 95:
  - стенд: адрес из `CALENDAR_API_URL` или свой сервер, переменные передаются дальше 15;
  - проигрывание случаев урока 3 через HTTP 25;
  - тесты проверки тел и ошибок 15;
  - бронирования, ключ идемпотентности и параллельные запросы 25;
  - цикл "запустить проверку, поправить" по сообщениям `ci-gate` 15;
- цель `make ci` 10, проверка дрейфа 10.

Можно перенести свою работу поверх стартера, проверки одинаковы. Копировать стартер следующего
урока можно, но это не упражнение: проверка тогда ничего о вас не скажет.

## Что в рабочей папке

Эталонное состояние урока 6: всё из уроков 1-5 и страница бронирования на Nuxt с компонентным
тестом и сценариями Playwright. В `Makefile` уже есть `build`, `gen`, `build-web`, `serve-web` и
`test-web`. Новое: цель `ci`, которая пока только пишет "make ci: nothing is checked yet" и
завершается с кодом 0. Тестов API нет.

## Что сделать

1. **Набор тестов API.** Любой язык, который есть в `PATH` проверки: Go (`go test`), Node (vitest из
   `frontend/node_modules`) или Python 3 без сторонних пакетов. `curl` в образе нет. Набор говорит с
   сервером только по HTTP:
   - если задана `CALENDAR_API_URL`, он проверяет сервер по этому адресу и свой сервер не
     запускает;
   - иначе он сам запускает `bin/server` (его собирает `make build`) с `HOST`, `PORT`,
     `CALENDAR_NOW`, `CALENDAR_BOOKING_DELAY_MS` и `CALENDAR_DATA_DIR` и ждёт готовности;
   - `CALENDAR_NOW` и `CALENDAR_BOOKING_DELAY_MS` он берёт из окружения в обоих случаях.
2. **Случаи урока 3 через HTTP.** Набор проигрывает файлы `testdata/slots/*.json`: создаёт
   расписание, виды встреч и бронирования через `POST` (отменённое бронирование отменяет сразу после
   создания), сравнивает `GET .../slots` с `expected` и отменяет бронирования случая.
3. **Тесты на остальное поведение контракта:** ошибки и их коды, проверка тел, бронирования и
   конфликты, отмена, ключ идемпотентности, параллельные запросы.
4. **`make ci`.** Одна команда для всего, что должно оставаться зелёным: `go vet`, модульные тесты,
   случаи движка через `bin/slots` или пакет движка, набор тестов API, vitest, компиляция
   контракта, перегенерация клиента и проверка дрейфа. Шаг дрейфа перегенерирует клиент из
   `contract/` и сравнивает результат по содержимому с `frontend/app/api/schema.d.ts` в рабочей
   папке: `make gen` и потом `git diff --exit-code`, или генерация во временный каталог и сравнение
   файлов. Проверка проверяет это требование на семи случаях дрейфа (3a)-(3g) ниже. Внутрь
   `make ci` она не смотрит: видит только код завершения на известных ей серверах и правках. Поэтому
   она не отличит от ожидаемого способа такой, где `make gen` записывает контрольную сумму или копию
   контракта и клиента, а шаг дрейфа сравнивает с ней: он тоже падает на всех семи случаях и
   проверку проходит. Ожидаемый способ всё равно первый.

## Что получает `make ci`

У `make -s ci`, у всего, что он запускает, ровно окружение проверки (ниже) и ещё:

- `CALENDAR_NOW=2026-03-01T08:00:00Z` во всех прогонах;
- `CALENDAR_BOOKING_DELAY_MS`: одно число из 150-250 на запуск проверки, одно и то же во всех её
  прогонах. Задержка включена в каждом прогоне, с ошибкой в сервере и без: сервер проверки спит
  столько после успешной проверки слота и до записи, как ваш в уроке 5;
- `CALENDAR_API_URL=http://127.0.0.1:<порт>`, без `/` на конце, только в 23 прогонах против
  сервера проверки (пункт 2 ниже).

Больше ничего.

## Сервер проверки

В пункте 2 ниже проверка запускает свой сервер по контракту урока 2. Для каждого прогона это новый
процесс, пустой (ни расписаний, ни видов встреч), с тем же `CALENDAR_NOW` и той же задержкой.

- Метки времени в ответах с `Z` и без долей секунды, так что их можно сравнивать и строкой.
  `createdAt` это настоящее время UTC с точностью до секунды, а не `CALENDAR_NOW`.
- Тело ошибки `{type: "about:blank", title, status, code, detail}`, `detail` бывает не всегда,
  `status` равен статусу ответа.
- Путь не из контракта: 404 `text/plain` с телом `404 page not found`. Метод не из контракта: 405
  `text/plain` с `Allow`. Как в уроке 4, у них проверяется только статус (и `Allow`).
- Операцию, которую добавляет проверка дрейфа (ниже), сервер не реализует, и тесты не должны её
  требовать.

**Что меняется от прогона к прогону.** Перед каждым из 23 прогонов один и тот же генератор заново
выбирает эти значения. Он не знает, есть ли в сервере ошибка, поэтому по ним нельзя отличить
сервер с ошибкой от правильного. Набор, который от них не зависит, ничего не теряет:

| | Что | Варианты |
|---|---|---|
| K1 | `id` | строчный UUID v4; 26 символов из `0-9A-HJKMNP-TV-Z`; две случайные строчные буквы на вид объекта, `_` и 16 шестнадцатеричных цифр; десятичный счётчик от случайного числа 1-999999, +1 на каждый `id` |
| K2 | `title` ошибки | один из 3 текстов на каждый `code` |
| K3 | `detail` ошибки | нет или один из 3 текстов на каждый `code` |
| K4 | параметр типа у `application/json` и `application/problem+json` | нет, `; charset=utf-8`, `; charset=UTF-8` |
| K5 | порядок заголовков | случайная перестановка `Content-Type`, `Content-Length`, `Date`, `Allow`, `Connection` |
| K6 | `Allow` | `GET`, `HEAD`, `POST` в случайном порядке; `HEAD` на путях с `GET` есть или нет (если нет, `HEAD` там получает 405) |
| K7 | задержка ответа | на прогон 0, 10 или 30 мс, плюс 0-10 мс на каждый ответ, всего не больше 40 мс |

Порт сервер получает от системы. Задержка K7 меньше половины самой короткой задержки шва (75 мс),
так что правила урока 5 со временем ответа остаются верными.

**Ошибки в сервере.** 5 прогонов из 23 идут против правильного сервера, 18 против сервера с одной
ошибкой. Ошибки движка действуют везде, где сервер считает слоты: в `GET .../slots` и в проверках
`POST /bookings` (доступность и конфликт).

## Случаи вне рекомендации урока 3

Случай с `now`, отличным от `2026-03-01T08:00:00Z`, или с бронированием, которое при этом `now` в
порядке списка нельзя создать через `POST /bookings`, остаётся случаем только для движка:

- `make ci` по-прежнему прогоняет его через движок (`bin/slots` или пакет `internal/slots`);
- набор тестов API пропускает его через HTTP и пишет, какой случай и почему.

Ошибки движка в проверке подаются только через HTTP. Если ошибку ловили только такие случаи, она
пройдёт `make ci`, и сообщение назовёт её поведение и требование. Тогда перепишите случай по
рекомендации урока 3 или добавьте тест API на это поведение.

## Дрейф

Семь прогонов без `CALENDAR_API_URL`, в случайном порядке. Каждый случай записывается в копию
рабочей папки до её единственного коммита `workspace as submitted` (как, ниже). Отдельного
коммита со случаем нет: сообщение коммита в каждом прогоне одно и то же, `HEAD~1` не существует, и
по истории git не видно, какие файлы изменены.

- **(3a) правка клиента руками.** Из `frontend/app/api/schema.d.ts` удаляется одна случайная
  строка со свойством внутри `export interface components` (строка вида `name: ...;` или
  `"name"?: ...;`), контракт не меняется. `make ci` должен упасть.
- **(3b) контракт без перегенерации.** В конец `contract/main.tsp` дописывается новая операция,
  `schema.d.ts` не меняется. `make ci` должен упасть.
- **(3c) контракт и перегенерация.** Та же по виду правка, потом ваш `make -s gen` (60 секунд),
  затем коммит и `make -s ci`. Он должен пройти.
- **(3d) перегенерация и ручная правка вместе.** Правка контракта как в (3b), ваш `make -s gen`,
  потом внутри `components` в `schema.d.ts` строка со свойством одного объекта копируется в другой
  объект, где свойства с таким именем нет. Строка только добавляется, и её имя в клиенте уже есть.
  `make ci` должен упасть.
- **(3e) клиент от прежней версии контракта.** Правка контракта, ваш `make -s gen`, потом в конец
  `contract/main.tsp` дописывается ещё одна такая операция, уже без перегенерации. `make ci` должен
  упасть.
- **(3f) тип в клиенте руками.** В `frontend/app/api/schema.d.ts` у одного свойства внутри объекта
  в `components`, тип которого `string` или `number` (можно с `[]` или `| null` после него), тип
  меняется на месте на другой из этих двух (`status: number;` становится `status: string;`). Число
  строк и байтов, имена и операции те же, контракт не меняется. `make ci` должен упасть.
- **(3g) тип в контракте без перегенерации.** В одном из `contract/**/*.tsp` у одного поля вида
  `name: <тип>` тип меняется на месте на тип той же длины, который в клиенте даёт другой тип
  TypeScript (`string` и `uint16`/`uint32`/`uint64`, `boolean` и
  `float32`/`float64`/`integer`/`numeric`/`safeint`, `int16`/`int32`/`int64`/`uint8`/`float` на
  `bytes`, `bytes` на `int32`/`int64`). Проверка берёт поле, после замены которого контракт
  компилируется её компиляцией и OpenAPI меняется, и пробует не больше 8 полей. `schema.d.ts` не
  меняется. `make ci` должен упасть.

(3f) и (3g) не меняют число строк, байтов, операций и имён: шаг дрейфа, который сравнивает только
их, их не поймает.

Правка контракта в (3b)-(3e) (в (3e) обе операции) одна из двух форм, выбирается отдельно для
каждой операции, `<x>` это 8 случайных строчных букв, `<X>` то же с заглавной первой:

```
namespace <X> {
  model <X>Value { value: string; }
  @TypeSpec.Http.route("/<x>")
  @TypeSpec.Http.get
  op read<X>(): <X>Value;
}
```

Вторая форма: то же с `model <X>Input { value: string; }`, `@TypeSpec.Http.post` и
`op write<X>(@TypeSpec.Http.body body: <X>Input): <X>Value;`. Декораторы с полным именем, поэтому
`using` не нужен. Проверка компилирует контракт своей компиляцией (как `contract-matches` урока 2) и
берёт первую форму, после которой в OpenAPI есть путь, кончающийся на `/<x>`, с этим методом:
сначала пространство имён как написано (внутри `namespace X;` на весь файл), потом
`namespace <Имя>.<X>` для каждого имени пространства из `contract/**/*.tsp`, по порядку файлов, не
больше 10.

Что из этого следует:

- `make gen` перегенерирует `frontend/app/api/schema.d.ts` из `contract/`;
- ваш сервер операцию `/<x>` не реализует, и тесты её не требуют;
- серверный код oapi-codegen не входит в `make gen`. В oapi-codegen 2.8.2 у строгого сервера
  (strict, std-http) нет типа-заглушки Unimplemented, который можно встроить в свою структуру. Если
  `make gen` перегенерирует и его, новая операция добавит метод в интерфейс, и сборка Go в (3c)
  сломается.

## Готово, когда

### Проверка `ci-gate`

**До прогонов.** Проверка сверяет базу поясов и инструменты образа, один раз снимает копию рабочей
папки и собирает свой сервер раньше, чем запускается любой ваш процесс. Потом один раз запускает
`make -s build` в свежей копии, 180 секунд, вне ограничения 60 секунд: так первый `make ci` не
компилирует стандартную библиотеку Go с нуля. Если эта сборка упала или не уложилась, больше ничего
не запускается.

**Каждый прогон.**

- Свежая полная копия снимка, после прогона она удаляется. В начале проверки нужно не меньше 1200
  МБ свободного места, перед каждой копией не меньше 600 МБ.
- В копии новый репозиторий git: `.git` снимка удаляется, `git init -q -b main`, в
  `.git/info/exclude` записаны `node_modules/`, `.nuxt/`, `.output/`, `/bin/`, `/tsp-output/`, в
  прогонах дрейфа записывается случай, потом `git add -A` и один коммит `workspace as submitted`.
  Значит, `HEAD` в копии это рабочая папка такой, какая она есть, с незакоммиченными изменениями,
  а не ваш последний коммит. Ваш `.gitignore` действует поверх этого списка. История ваших коммитов в копии не видна.
- Все команды git проверки (git init, add и этот коммит) запускаются как ваши процессы: окружение
  проверки плюс `GIT_CONFIG_NOSYSTEM=1` и `GIT_TERMINAL_PROMPT=0`, автор `Academy grader
  <grader@academy.invalid>`, без подписи коммитов, хуки выключены (`core.hooksPath=/dev/null`,
  `commit --no-verify`).
- `make -s ci` ограничен 60 секундами. Копирование и git в это время не входят. Прогон дольше 60
  секунд считается упавшим.

**Прогоны.**

1. `make -s ci` без `CALENDAR_API_URL` завершается с кодом 0. Это нужно, но не достаточно.
2. 23 прогона с `CALENDAR_API_URL` в случайном порядке, у каждого свой новый сервер проверки:
   - 5 против правильного сервера: код 0;
   - 18 против сервера с ошибкой: код не 0 (прогон дольше 60 секунд тоже считается упавшим).
3. Семь прогонов дрейфа без `CALENDAR_API_URL`, в случайном порядке: (3a), (3b), (3d), (3e), (3f)
   и (3g) код не 0 (прогон дольше 60 секунд тоже считается упавшим, то есть дрейф пойман), (3c)
   код 0 (прогон дольше 60 секунд здесь ошибка).

Всего 31 прогон `make -s ci`: 1, 23 и 7.

Вердикт берётся только из кода завершения `make -s ci` на известном проверке сервере или правке.
Вывод ваших тестов не читается.

## Окружение проверки

Снимок рабочей папки: обычные файлы, `.git` входит, `__pycache__` нет. Символические ссылки внутрь
рабочей папки (например в `frontend/node_modules/.bin/`) остаются ссылками, ссылки наружу и битые не
копируются. Поэтому ссылки `node_modules` в корне на `/opt/academy/node/node_modules` в копии нет:
ваш `make gen` создаёт её сам (в стартере это строка `test -e node_modules || ln -s ...`).

У `make`, у всего, что он запускает, ровно такое окружение, плюс переменные выше:

- `PATH=/opt/academy/bin:/opt/node/bin:/usr/local/go/bin:/usr/bin:/bin`;
- свои пустые `HOME`, `TMPDIR`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`;
- `NUXT_TELEMETRY_DISABLED=1`;
- случайный `TZ` из Europe/Berlin, America/New_York, America/Los_Angeles, Australia/Sydney,
  Asia/Kolkata, Asia/Kathmandu, Europe/Moscow (никогда не UTC);
- `GOENV=off GOFLAGS= GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off GOWORK=off CGO_ENABLED=0 GOEXPERIMENT=`,
  свои `GOTMPDIR`, `GOPATH`, `GOMODCACHE` и один `GOCACHE` на весь запуск проверки (его делят все
  прогоны);
- больше ничего: ни `NODE_OPTIONS`, ни `NODE_PATH`.

Сети при проверке нет. Цели `Makefile` вызывают программы из `PATH` или из `frontend/node_modules`,
поставленного вашим `npm ci`; `npx` подходит только для пакетов из `package-lock.json`. Сторонние
модули Go в `vendor/`.

## Как работать (совет, не проверяется)

- Запустите набор так же, как проверка, против своего сервера по адресу:
  ```sh
  make -s build
  HOST=127.0.0.1 PORT=8080 CALENDAR_NOW=2026-03-01T08:00:00Z CALENDAR_BOOKING_DELAY_MS=200 CALENDAR_DATA_DIR=$(mktemp -d) TZ=Australia/Sydney bin/server &
  CALENDAR_NOW=2026-03-01T08:00:00Z CALENDAR_BOOKING_DELAY_MS=200 CALENDAR_API_URL=http://127.0.0.1:8080 make -s ci
  ```
  Проверка даёт каждому прогону новый пустой сервер: перезапускайте свой между прогонами.
- Потом без адреса: `CALENDAR_NOW=2026-03-01T08:00:00Z CALENDAR_BOOKING_DELAY_MS=200 make -s ci`.
- Сломайте сервер по одной строке таблицы ошибок (409 и 422, лишние поля, блокировка на время
  задержки) и убедитесь, что `make ci` падает. Потом верните.
- Шаг дрейфа (пункт 4 выше) перегенерирует клиент и сравнивает содержимое, а не признаки.
  Смотреть, что изменил последний коммит, мало: отдельного коммита с правкой в проверке нет, и в
  (3d) и (3e) `make gen` уже запускался. Считать строки или сравнивать имена тоже мало: (3f) и (3g)
  меняют один тип на месте.
- Дрейф руками: допишите форму выше в `contract/main.tsp` и закоммитьте, `make ci` должен упасть;
  потом `make gen`, коммит, `make ci` должен пройти. Затем скопируйте в `schema.d.ts` строку
  свойства в другой объект (как в (3d)), `make ci` должен упасть. Затем замените в `schema.d.ts` у
  одного свойства `string` на `number` (как в (3f)), `make ci` должен упасть. Затем отмените эти
  коммиты.
- Набор на TypeScript (vitest) в `frontend/`: `frontend/tsconfig.json` ссылается на
  `.nuxt/tsconfig.*.json`, а их создаёт только сборка Nuxt. Без неё тестовый файл падает с
  `TSCONFIG_ERROR`. Положите в папку набора свой `tsconfig.json` (например `"target": "ES2022"`,
  `"module": "ESNext"`, `"moduleResolution": "Bundler"`, `"strict": true`, `"types": ["node"]` в
  `compilerOptions`) и запускайте набор отдельным файлом настроек vitest (`environment: 'node'`,
  свой `include`), а в проект Nuxt из `frontend/vitest.config.ts`, который запускает `test-web`, его
  не включайте.
- Держите `make ci` заметно короче 60 секунд: в проверке машина медленнее, каждое удачное
  бронирование ждёт задержку 150-250 мс, а каждый ответ сервера проверки ещё до 40 мс.
