# Итоговый проект: тесты API и единая команда make ci

**Твой шаг.** В эталонном плане урока 1 у срезов 1-6 строка `Check: make ci`, а у среза 0
`Check: make gen`. Вертикальная команда наращивала бы тесты API срез за срезом, начиная со среза 1.
Здесь API и страница уже готовы, и урок собирает проверку целиком: тесты API на REQ-01..REQ-19
(номера REQ здесь и ниже из спецификации стартера, в своей нумерации они могут быть другими) и
защиту от расхождения контракта и сгенерированного клиента (T-00).

## Проблема

Набор тестов API, написанный после сервера, обычно проверяет то, что сервер уже делает:
`POST /bookings` вернул 201, `GET .../slots` вернул непустой список. Такой набор зелёный и
остаётся зелёным, когда:

- 409 и 422 перепутаны местами;
- метка времени без смещения принимается как местное время;
- два одновременных бронирования одного слота оба получают 201;
- следующий день считается прибавлением 24 часов, и в день перевода часов слоты съезжают.

Обратная беда: тест привязан к своему серверу. Он сравнивает `Content-Type` строкой, ждёт `id` из
цифр, проверяет текст `title` в ошибке или порядок методов в `Allow`. На другом сервере, который
выполняет тот же контракт, такой тест падает, и красный `make ci` перестаёт что-то значить.

Третья беда: контракт меняется, а сгенерированный клиент `schema.d.ts` нет. Или кто-то поправил
`schema.d.ts` руками. Всё собирается, потому что клиент ни с чем не сравнивается.

## Идея

1. **Тест проверяет обещание контракта, а не свою реализацию.** Набор говорит с сервером только по
   HTTP и работает против любого сервера по адресу из `CALENDAR_API_URL`. Без адреса он сам
   запускает ваш `bin/server`. Один и тот же набор можно направить на ваш сервер и на чужой.
2. **Качество набора видно на сломанных серверах.** Хороший набор падает на сервере с ошибкой и
   проходит на любом корректном. Это приём урока 3 с подложенными ошибками движка, только теперь
   ошибки во всём API, а судят ваш набор тестов.
3. **Сгенерированный файл это функция контракта.** Проверка дрейфа: сгенерировать заново и
   сравнить с тем, что лежит в репозитории. `git diff --exit-code` "exits with 1 if there were
   differences and 0 means no differences", а форма `git diff -- <путь>` показывает изменения
   "relative to the index". Значит, `make gen && git diff --exit-code -- frontend/app/api/schema.d.ts`
   падает и на ручной правке, и на контракте без перегенерации, и проходит после честного
   `make gen` с коммитом.

## Как это выглядит в Go

Набор тестов это отдельный пакет, например `backend/apitest`. Адрес сервера выбирает один
`TestMain`. Документация `testing`: TestMain нужен, когда программе тестов надо "do extra setup or
teardown before or after it executes", а "m.Run will return an exit code that may be passed to
os.Exit". Короткий пакет, который можно запустить `go test` против сервера на 8080:

```go
package apitest

import (
	"net/http"
	"os"
	"testing"
)

var baseURL = "http://127.0.0.1:8080"

func TestMain(m *testing.M) {
	if url := os.Getenv("CALENDAR_API_URL"); url != "" {
		baseURL = url
	}
	os.Exit(m.Run())
}

func TestEventTypesList(t *testing.T) {
	response, err := http.Get(baseURL + "/event-types")
	if err != nil {
		t.Fatal(err)
	}
	defer response.Body.Close()
	if response.StatusCode != http.StatusOK {
		t.Fatalf("GET /event-types: %d", response.StatusCode)
	}
}
```

В `make ci` вместо адреса по умолчанию стенд запускает `bin/server` на свободном порту с `HOST`,
`PORT`, `CALENDAR_NOW`, `CALENDAR_BOOKING_DELAY_MS` и `CALENDAR_DATA_DIR`, ждёт 200 на
`GET /event-types` и останавливает сервер после `m.Run()`. `CALENDAR_NOW` и задержку набор берёт
из окружения в обоих случаях: сервер по адресу запущен с теми же значениями.

**Случаи урока 3 через HTTP.** Каждый файл `testdata/slots/*.json` становится подтестом: стенд
создаёт расписание, вид встречи и бронирования через `POST`, сравнивает `GET .../slots` с
`expected` как моменты и отменяет бронирования случая. `t.Run` "runs f as a subtest of t called
name". Отмена удобна через `t.Cleanup`: функция вызывается "when the test (or subtest) and all
its subtests complete". Случай, который нельзя повторить через HTTP (другой `now`, бронирование,
которое не создать через `POST /bookings`), пропускается с причиной: `t.Skipf` "is equivalent to
Logf followed by SkipNow", а SkipNow "marks the test as having been skipped and stops its
execution".

Решает, можно ли повторить случай, ваш собственный движок (`internal/slots`), а не сервер под
тестом. Иначе сломанный сервер мог бы сделать случай "неповторимым", и тест молча пропустился бы.

**Сравнения, которые не зависят от реализации:**

- даты и время сравниваются как моменты, а не строками;
- `Content-Type` сравнивается без параметров и без учёта регистра: `application/json;
  charset=UTF-8` тоже JSON;
- в ошибке проверяются `status`, `code` и тип `application/problem+json`, но не тексты `title` и
  `detail`;
- `id` непрозрачный: любая строка, которую сервер вернул, годится для следующего запроса;
- `Allow` это множество методов, порядок не важен, а `HEAD` тест не трогает;
- правила по времени ответа оставляют запас: ответ сервера может задержаться на десятки
  миллисекунд без всякой ошибки.

**Параллельные запросы.** Шесть горутин одновременно бронируют один слот. Ровно один ответ 201,
остальные 409 `slot_taken`, и `GET /bookings` показывает одно бронирование. Задержка
`CALENDAR_BOOKING_DELAY_MS` делает окно гонки широким, поэтому сервер без атомарной секции
проваливает такой тест надёжно, а не через раз.

> **Go для TS-разработчика: тесты.**
> - **Пакет тестов.** Файлы `*_test.go` в `backend/apitest/`, запуск `go test ./apitest/` из
>   `backend/`. Тесту доступен `calendar/internal/slots`, как любому пакету модуля.
> - **Подтесты идут по очереди.** `t.Run` "runs f in a separate goroutine and blocks until f
>   returns or calls t.Parallel". Без `t.Parallel` тесты не мешают друг другу через общий сервер,
>   если у каждого свои даты.
> - **Кэш результатов.** "go test caches successful package test results to avoid unnecessary
>   repeated running of tests", а "The idiomatic way to disable test caching explicitly is to use
>   -count=1". Для тестов против живого сервера пишите `go test -count=1`.
> - **Не только Go.** Набор можно написать на Node (vitest из `frontend/node_modules`) или на
>   Python 3 без сторонних пакетов. `curl` в образе нет.

## Частые ошибки

- Тесты только на удачный путь: почти все подложенные ошибки проходят.
- Набор при заданном `CALENDAR_API_URL` всё равно запускает свой сервер и проверяет его.
- Тест сравнивает тексты ошибок, формат `id`, порядок заголовков или `Content-Type` строкой и
  падает на корректном сервере.
- Тесты делят даты: бронирование одного теста занимает слот другого, потому что бронирования
  конфликтуют для всех видов встреч хоста.
- Даты считаются от `time.Now()`, а не от `CALENDAR_NOW`.
- Случаи урока 3 написаны не по рекомендации: через HTTP они пропускаются, и ошибка движка, которую
  ловили только они, проходит.
- Дрейф через сравнение с сохранённой копией (`cmp schema.d.ts schema.golden`): ловит ручную правку,
  но не контракт без перегенерации.
- `make ci` что-то скачивает: при проверке сети нет.

## Что делать в практике

Сначала стенд: адрес или свой сервер. Потом проигрывание случаев урока 3, тесты ошибок и проверки
тел, бронирования, ключ идемпотентности и параллельные запросы. Потом цель `make ci` с проверкой
дрейфа. Сломайте свой сервер нарочно (поменяйте 409 и 422) и посмотрите, что набор краснеет.
Правила проверки, переменные и что меняется в ответах сервера проверки описаны в задании.
