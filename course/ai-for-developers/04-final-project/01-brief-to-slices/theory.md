# Итоговый проект: от брифа к спецификации, примерам и срезам

**Твой шаг.** Это первый урок итогового проекта, и кода в нём нет. Из брифа и интервью с заказчицей
вы делаете спецификацию с требованиями REQ, исполняемые примеры, один ADR и план вертикальных срезов.
Всё, что дальше пишется в уроках 2-8, опирается на эти файлы: контракт, движок слотов, сервер,
страница, CI и деплой. Вертикальная команда сделала бы эту работу до среза 1: план нужен раньше
первого среза.

## Проблема

Ирина пишет в брифе: однажды встреча "съехала" на час после перевода часов. Попросите агента
"сделай запись на звонки по брифу", и он напишет код, который в обычный день работает. Тесты по
такой спецификации тоже пройдут в обычный день. Ошибка проявится в одно воскресенье марта, когда в
Нью-Йорке не будет времени 02:30, и в одно воскресенье октября, когда в Берлине 02:30 наступит
дважды.

Решения о таких днях в брифе не записаны. Они разбросаны по интервью: правило для разрыва
спрятано в истории про мартовское воскресенье, правило для перерывов звучит как "работают они в обе
стороны". Спецификация, написанная по одному брифу, эти решения теряет.

## Идея: требование плюс исполняемый пример

Требование в форме WHEN...SHALL вы писали в уроке 4 модуля 01. Но фразу "читайте его по смещению,
которое действовало до перевода" можно понять неправильно и записать неправильно, и никто этого не
заметит, пока не придёт март.

Исполняемый пример снимает этот риск. В нём есть вход (расписание, вид встречи, бронирования,
текущий момент, диапазон) и ожидаемый выход (список слотов). Пример это данные, а не код. В этом
уроке у заказчицы есть модель: программа, которая по входу выдаёт слоты по её правилам. Ваш
пример либо совпадает с моделью, либо нет.

Совпадения мало. Пример "обычный вторник в UTC, окно 09:00-11:00, бронирований нет" совпадёт с
моделью, но и с реализацией, которая ошибается в любом из восьми решений ниже. Поэтому к модели прилагаются мутанты из уроков 1 и 5 модуля 01: на
каждое из восьми решений о времени есть копия модели, которая решает иначе. Например, разрыв
читает по смещению после перевода. Набор примеров хорош, когда для каждого мутанта есть пример,
на котором мутант даёт другой список, чем модель. Тогда этот пример станет тестом, который поймает
такую ошибку в вашем коде в уроке 3.

## Как это работает: что значит 02:30, которого не было

В ночь на 8 марта 2026 года в Нью-Йорке часы переводят с 02:00 сразу на 03:00. Окно Ирины "с
02:30" в этот день начинается во времени, которого нет. Ирина решила: читать такое время по
смещению до перевода. До перевода смещение -05:00, значит 02:30 это 07:30 UTC, то есть 03:30 по
новому времени. Окно сдвигается вперёд на длину разрыва.

При обратном переводе (в апреле в Сиднее, в октябре в Берлине) наоборот: 02:30 наступает дважды.
Ирина решила брать первое из двух.

Это правило не придумано для курса, оно совпадает со стандартными библиотеками:

- Python, PEP 495: у повторяющегося времени `fold=0` соответствует "the earlier" из двух прочтений;
  для времени в разрыве "the rules in effect before the transition should be used if `fold=0`".
- Temporal, параметр `disambiguation: "compatible"`: для обратного перевода "Acts like 'earlier'",
  а несуществующее время читается "using the pre-transition time zone offset".
- Java, `ZonedDateTime.of(LocalDateTime, ZoneId)`: при повторе "uses the earlier offset", при
  разрыве "the local date-time is adjusted to be later by the length of the gap".

Проверить на Python можно так (модуль `zoneinfo` в стандартной библиотеке):

```python
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

new_york = ZoneInfo("America/New_York")
in_gap = datetime(2026, 3, 8, 2, 30, tzinfo=new_york)  # fold=0 by default
print(in_gap.astimezone(timezone.utc))  # 2026-03-08 07:30:00+00:00
```

Пример в формате урока описывает именно такой день: окно в поясе расписания, дата перевода,
ожидаемые слоты со смещением. Ожидаемый ответ считать вручную не обязательно. Если `expected`
расходится с моделью, проверка покажет список модели для первого такого примера. Ваша работа в
другом: найти в интервью решение и выбрать день, на котором неправильное решение даёт другой ответ.

> **Go для TS-разработчика: время.** В уроке 3 движок слотов пишется на Go. Документация
> `time.Date` про разрыв и повтор говорит прямо: "Date returns a time that is correct in one of the
> two zones involved in the transition, but it does not guarantee which." Поэтому правило Ирины
> движок реализует сам, а не надеется на `time.Date`. Ваши примеры из этого урока станут первыми
> тестами, которые это поймают.

## Срезы: план вертикальный, уроки идут по инструментам

Срез из урока 4 модуля 01 проходит через все слои и даёт результат, который можно увидеть. В этом
проекте срез выглядит так: "приглашённый видит свободные слоты одного вида встречи в обычный день".
В нём часть контракта, правила недельного расписания в движке, `GET` слотов, список на странице и
`make ci` с первым тестом API.

Уроки 2-8 при этом идут в другом порядке: сначала весь контракт, потом по одному новому
инструменту на урок (движок на Go, HTTP на Go, страница на Nuxt, CI, Docker). Так сделано по двум
причинам. Каждой проверке нужен устойчивый шов, который можно проверять как чёрный ящик. И стек для
вас новый: урок, где один срез сразу идёт через Go, HTTP и Nuxt, превратился бы в "сделай всё
сразу". Ваш план это не нарушает: его оценивает только рубрика, и с порядком уроков его никто не
сравнивает.

ADR в этом проекте нужен на одно решение, которое интервью само называет трудным для отмены: где
хранить бронирования и как не дать двум запросам одновременно пройти проверку "свободно".

## Частые ошибки

- Спецификация по брифу без интервью: решения о времени, перерывах и ошибках потеряны.
- Требование с правилом, которое интервью отвергло: "уведомление от начала дня", "из двух 02:30
  берём второе", "исключение добавляется к недельным окнам".
- Примеры только на обычные дни: все совпадают с моделью, но ни один мутант не отличается.
- `bookingWindowDays`, который не дотягивается до выбранной даты. Модель тогда вернёт пустой
  список, мутант тоже, и пример ничего не различает. То же с `minimumNoticeMinutes`, который
  закрывает весь день, и со стартом бронирования не на сетке окна.
- Срезы по слоям: "модель данных, движок, обработчики, фронтенд, тесты".
- ADR не на то решение (формат ошибок, язык, формат идентификаторов) или с одним вариантом.

Прочитайте бриф и интервью целиком, выпишите решения Ирины и превратите каждое в требование.
Потом на каждое из восьми решений о времени подберите маленький пример: один местный день, 1-3
слота. Затем ADR и план срезов. Формат примеров, правила проверок и рекомендация для урока 7
