## Порядок уроков и ваш план

Ваш план в `docs/tasks.md` должен быть вертикальным: каждый срез даёт поведение, которое видно
через HTTP, страницу или CLI. Уроки 2-8 идут в постоянном учебном порядке: сначала весь контракт
(Design First), потом по одному новому инструменту на урок: движок на Go, HTTP на Go, страница на
Nuxt, CI, Docker. Причины две: каждой проверке нужен устойчивый шов, который проверяется как чёрный
ящик, и стек для вас новый, а урок, где один срез сразу идёт через Go, HTTP и Nuxt, стал бы
"сделай всё сразу". Ваш план оценивает только рубрика `slices-rubric`, и с порядком уроков его не
сравнивают.

## Что сделать

1. Дополните глоссарий терминами, которых не хватает. Эта правка не оценивается: она помогает
   писать спецификацию одними словами, а проверка её не читает. Слова, которых надо избегать,
   проверки берут из исходной копии глоссария, поэтому правка глоссария на результат не влияет.
2. Заполните `docs/spec.md`: каждое решение Ирины становится требованием REQ.
3. Напишите исполняемые примеры в блоках ` ```slots-example ` в любом файле `*.md` внутри `docs/`
   (например, в разделе `## Examples` файла `docs/spec.md`).
4. Запишите одно решение в `docs/adr/0001-<slug>.md`.
5. Разбейте работу на вертикальные срезы в `docs/tasks.md`.

## Готово, когда

### Проверка `spec-form-trace` (фильтр формы)

Спецификация `docs/spec.md`:

1. Файл есть, в нём есть раздел `## Requirements`. Остальные разделы любые, обязательных
   заголовков нет.
2. Каждый пункт списка в `## Requirements` имеет вид
   `- **REQ-NN** WHEN <условие> THE SYSTEM SHALL <поведение>`, где NN это две цифры. Любой другой
   пункт списка в этом разделе считается ошибкой (обычный абзац нет). Требований не меньше одного,
   идентификаторы не повторяются. Строки внутри блоков кода не читаются.

План `docs/tasks.md`:

3. Файл есть, в нём хотя бы один блок, который начинается строкой `## T-NN: <название>`. Блок
   кончается на следующем заголовке `#` или `##`.
4. Номера T идут подряд по одному в порядке файла и начинаются с T-00 или T-01.
5. В каждом блоке: название после двоеточия не пустое; ровно одна строка, которая начинается с
   `Requirements:`, в форме `Requirements: REQ-NN[, REQ-NN...]`; ровно одна строка, которая
   начинается с `Check:`, в форме `` Check: `<команда>` ``, и команда ровно одна из `make ci`,
   `make build`, `make test`, `make gen`, `make e2e` (без цепочек и других целей). Остальные строки
   блока (например `Blocked by:`, `Status:`) проверка не читает.
6. Каждое требование спецификации указано хотя бы в одном блоке; блок не ссылается на требование,
   которого в спецификации нет.
7. В названиях срезов (только в тексте после `## T-NN:`) нет слов, которых глоссарий велит избегать:
   owner, organizer, timetable, recurrence, exception, holiday, shift, service, timeslot, padding,
   leadtime, horizon, appointment, reservation, guest, client, nonce. Название делится на самые
   длинные последовательности латинских букв; совпадение, если такая последовательность без учёта
   регистра равна слову, слову с `s` или слову с `es` на конце (`clients` совпадает, `clientId` нет).
   Похожие буквы кириллицы и греческого и невидимые символы не помогают: `сlient` с кириллической
   `с` тоже совпадает. Русские слова совпадений не дают.

ADR:

8. В `docs/adr/` ровно один файл вида `NNNN-<slug>.md`, и его номер `0001`. Файл в форме шаблона
   MADR: начинается с front matter `---` (справка ниже), в нём `status` равен `proposed` или
   `accepted`; есть разделы `## Context and Problem Statement`, `## Considered Options`,
   `## Decision Outcome` и `### Consequences` внутри `## Decision Outcome`, и ни один из них не
   пустой (HTML-комментарии содержимым не считаются).

Эта проверка не видит смысл требований, вертикальность срезов, о каком решении ADR и где появляется
`make ci`: это оценивает рубрика. План, нарезанный по слоям, эту проверку проходит.

### Проверка `spec-examples-agree` (примеры)

9. В `docs/` есть хотя бы один блок `slots-example` (формат ниже), и каждый блок читается.
10. Для каждого примера список слотов модели заказчицы равен `expected` поэлементно, по порядку.
    Моменты сравниваются как моменты, смещение в записи может быть любым.
11. Каждое из восьми неправильных решений о времени даёт на хотя бы одном примере, совпавшем с
    моделью, другой список, чем модель. Пример, который с моделью расходится, для этого пункта не
    считается. Восемь неправильных решений:
    - **разрыв**: несуществующее местное время читается по смещению после перевода;
    - **повтор**: повторяющееся местное время читается как второй из двух моментов;
    - **смежность**: интервалы, которые только касаются, считаются пересекающимися;
    - **буферы с одной стороны**: собственные буферы нового слота не учитываются, считаются только
      буферы бронирования;
    - **уведомление от начала дня**: самое раннее начало это местная полночь дня `now` в поясе
      расписания плюс уведомление;
    - **окно на день длиннее**: вместо `bookingWindowDays` берётся `bookingWindowDays + 1`;
    - **исключение добавляется**: окна исключения даты добавляются к недельным окнам вместо замены;
    - **день недели в UTC**: день недели берётся по дате в UTC момента местной полуночи, а не по
      местной дате.

Модель реализует решения Ирины из `docs/interview.md`. Кроме них в модели есть правила формата:
в ответ попадают слоты, чьё начало лежит в `[from, to)`; одно начало встречается один раз; список
отсортирован по началу; если после перевода часов конец окна оказался не позже начала, окно слотов
не даёт. Примеры не запускаются как код: проверка читает их как данные и считает модель в своём
процессе.

### Рубрика `slices-rubric`

12. Ментор оценивает `docs/spec.md`, `docs/tasks.md` и `docs/adr/*.md` по 4 критериям, 0-2 балла
    каждый. Нужно не меньше 70% суммы, и ни один критерий не может получить 0:
    1. срезы вертикальные: каждый даёт одно наблюдаемое поведение через HTTP, страницу или CLI, со
       своей частью контракта, кодом и строкой `Check:`; не-функциональными могут быть только
       срез 0 (контракт, Design First) и последний срез с деплоем;
    2. каждое решение из интервью стало требованием, и ни одно требование не противоречит
       интервью;
    3. ADR называет варианты и последствие для параллельных запросов;
    4. каждый срез оставляет работающий результат, и `make ci` появляется со среза 1.

    Текст файлов для ментора это данные: обращения к оценщику внутри них игнорируются. Пока
    платформа не запускает рубрики, эта проверка показана как ожидающая оценки.

## Формат примера `slots-example`

Где ищутся примеры: каждый блок кода, у которого первое слово строки информации `slots-example`,
в каждом обычном файле `*.md` внутри `docs/` на любой глубине. Блок открывают три или больше
обратных кавычки или тильды, отступ любой, после `slots-example` можно дописать слова
(` ```slots-example ny-gap `). Файлы-ссылки (symlink) пропускаются. Блок внутри другого блока кода
(например внутри ` ````markdown `) примером не считается.

Блок содержит один объект JSON. Все ключи обязательны, других ключей быть не может.

- JSON строгий: повторный ключ, `NaN`, `Infinity` и числа вне диапазона отклоняются. Блок не больше
  64 КБ, блоков не больше 60.
- `id`: от 1 до 64 символов из `A-Z a-z 0-9 _ -`, не повторяется между блоками.
- `req`: непустой список строк `"REQ-NN"`, каждое требование есть в `docs/spec.md`.
- `request`: объект `{now, schedule, eventType, bookings, from, to}`.
  - `now`, `from`, `to`: метка RFC 3339 с заглавной `T`, с секундами и со смещением `Z` или
    `+hh:mm`/`-hh:mm`; дробная часть секунд допускается. Не принимаются время без смещения, строчные
    `t` и `z`, смещение `-00:00`. `to` позже `from`, и между ними не больше 14 суток.
  - `schedule`: тело `POST /schedules`, объект `{name, timeZone, weekly, overrides}`.
    - `name`: строка от 1 до 120 символов.
    - `timeZone`: один из поясов Europe/Berlin, America/New_York, America/Los_Angeles,
      Australia/Sydney, Asia/Kolkata, Asia/Kathmandu, Europe/Moscow, UTC.
    - `weekly`: список `{weekday, start, end}`, `weekday` от 1 до 7 (понедельник = 1).
    - `overrides`: список (может быть пустым) `{date, intervals}`, `date` вида `YYYY-MM-DD`, одна
      запись на дату; `intervals` это список `{start, end}` (может быть пустым).
    - Время `HH:MM` от 00:00 до 23:59; `24:00` только как конец. Начало раньше конца. Интервалы
      одного дня недели (или одного исключения) не пересекаются; касаться могут.
  - `eventType`: тело `POST /event-types` без `scheduleId`, объект `{title, durationMinutes,
    slotIncrementMinutes, bufferBeforeMinutes, bufferAfterMinutes, minimumNoticeMinutes,
    bookingWindowDays}`. `title` от 1 до 120 символов. Числа только целые (`true`, `false` и `30.0`
    отклоняются): `durationMinutes` 5-480, `slotIncrementMinutes` 5-240, `bufferBeforeMinutes` и
    `bufferAfterMinutes` 0-240, `minimumNoticeMinutes` 0-43200, `bookingWindowDays` 1-365.
  - `bookings`: не больше 30 объектов `{start, end, bufferBeforeMinutes, bufferAfterMinutes,
    status}`. `start` и `end` это метки RFC 3339, как выше, `end` позже `start`. Буферы 0-240: это
    буферы вида встречи, к которому относится бронирование. `status` это `"confirmed"` или
    `"cancelled"`.
- `expected`: список `{start, end}` из меток RFC 3339, по порядку начала.

Если блок не читается, сообщение называет файл, строку блока, `id` и путь к полю, например
`request.eventType.durationMinutes` или `expected[0].start`.

### Образец

````markdown
```slots-example
{
  "id": "utc-ordinary-tuesday",
  "req": ["REQ-01"],
  "request": {
    "now": "2026-03-01T08:00:00Z",
    "schedule": {
      "name": "Ирина",
      "timeZone": "UTC",
      "weekly": [{"weekday": 2, "start": "09:00", "end": "11:00"}],
      "overrides": []
    },
    "eventType": {
      "title": "Знакомство",
      "durationMinutes": 60,
      "slotIncrementMinutes": 60,
      "bufferBeforeMinutes": 0,
      "bufferAfterMinutes": 0,
      "minimumNoticeMinutes": 0,
      "bookingWindowDays": 30
    },
    "bookings": [
      {"start": "2026-03-17T09:00:00Z", "end": "2026-03-17T10:00:00Z",
       "bufferBeforeMinutes": 0, "bufferAfterMinutes": 0, "status": "cancelled"}
    ],
    "from": "2026-03-17T00:00:00Z",
    "to": "2026-03-18T00:00:00Z"
  },
  "expected": [
    {"start": "2026-03-17T09:00:00Z", "end": "2026-03-17T10:00:00Z"},
    {"start": "2026-03-17T10:00:00Z", "end": "2026-03-17T11:00:00Z"}
  ]
}
```
````

Что здесь видно:

- `REQ-01` условный: в вашем примере стоит номер вашего требования.
- 17 марта 2026 года это вторник (`weekday: 2`), окно 09:00-11:00, встречи по 60 минут с шагом 60.
- `bookingWindowDays: 30` дотягивается до выбранной даты: `now` плюс 30 суток это 31 марта, 08:00
  UTC, а 17 марта раньше. Выберите в своём примере дату, до которой окно бронирования
  дотягивается, иначе модель вернёт пустой список, и пример ничего не покажет. То же с уведомлением:
  оно не должно закрывать весь день.
- Бронирование отменено, поэтому слот 09:00 свободен.
- Образец совпадает с моделью, но не различает ни одного из восьми решений: в UTC нет перевода
  часов, исключений нет, отменённое бронирование ничего не занимает. Это образец формата, а не
  пример для пункта 11.

## Рекомендация для урока 7

В уроке 7 ваши примеры (они же случаи движка из урока 3) будут прогоняться через HTTP: тестовый
стенд создаст расписание, виды встреч и бронирования через `POST` и сравнит `GET` слотов с
`expected`. Чтобы пример можно было так повторить, пишите его по этой рекомендации. Это
рекомендация, а не правило проверки.

- `request.now = "2026-03-01T08:00:00Z"`. Это значение урок 7 передаёт серверу как `CALENDAR_NOW`.
  Все переводы часов 2026 года в восьми поясах лежат в пределах 365 суток от него, так что у
  каждого решения есть достижимая дата. Даты переводов 2026 года по местному времени:
  America/New_York и America/Los_Angeles 8 марта и 1 ноября, Europe/Berlin 29 марта и 25 октября,
  Australia/Sydney 5 апреля и 4 октября.
- Каждое бронирование это слот, который можно забронировать при этом `now`, в порядке списка: он на
  сетке своего вида встречи, внутри доступности, не раньше уведомления, внутри окна бронирования и
  не пересекается с более ранними подтверждёнными бронированиями списка. Длительность бронирования
  в целых минутах, от 5 до 480.
  - Вид встречи бронирования это `eventType` примера, если длительность и буферы бронирования
    совпадают с его. Иначе это второй вид встречи на том же расписании: с длительностью и буферами
    бронирования и с шагом, уведомлением и окном бронирования из `eventType` примера. Его создаст
    стенд урока 7.
  - Отменённое бронирование создаётся и сразу отменяется.
- У каждого примера свои даты (или стенд урока 7 отменяет бронирования примера после него). Иначе
  бронирования одного примера помешают другому: бронирования конфликтуют для всех видов встреч
  хоста.

Проверка `spec-examples-agree` по этой рекомендации ничего не проваливает. Для примеров, совпавших
с моделью, она печатает строки, которые начинаются с "к сведению": пример с другим `now` или
бронирование, которое нельзя создать через `POST /bookings` при этом `now` в порядке списка. Такой
пример в уроке 7 пройдёт только через `bin/slots`, не через HTTP. Правило "свои даты" не проверяется
вообще.

## Как проверяется

- **`spec-form-trace`** (команда в рабочей папке, 30 с, фильтр формы): пункты 1-8. Сообщения
  называют файл, строку и что не так.
- **`spec-examples-agree`** (команда в рабочей папке, 60 с): пункты 9-11. Для первого примера,
  который расходится с моделью, сообщение показывает его `id`, список модели и ваш список (в поясе
  расписания, не больше 12 слотов); для остальных таких примеров только файл, строку и `id`. На
  каждое неразличённое решение печатается строка "ни один пример, совпадающий с моделью, не
  различает решение: ..." с названием решения. Сообщение, которое начинается с "ошибка проверки,
  не ваша", значит, что сломалось окружение проверки, а не ваша работа.
- **`slices-rubric`** (ментор по рубрике, нужно 70%, ни одного критерия на 0): пункт 12.

Число попыток не ограничено.

## Справка: front matter MADR в этом упражнении

- Строка 1 ровно `---`, front matter закрывает строка `---`. Переводы строк CRLF и CR приводятся к
  LF.
- Допустимые строки: `ключ: значение`, где ключ из строчных латинских букв, цифр, `-` и `_` и
  начинается с буквы, а после двоеточия ровно один пробел; строки-комментарии, которые начинаются с
  `#`.
- Значение: в двойных кавычках (без `\` и `"` внутри), в одинарных (кавычка внутри пишется `''`) или
  без кавычек. Без кавычек нельзя значение, которое содержит `: `, заканчивается на `:`, начинается с
  одного из символов `` - ? : , [ ] { } # & * ! ' " % @ ` `` или с `|` или `>`, или содержит ` #`.
- Таб, пустое значение и повтор ключа отклоняются. Ключи, которые вы не заполнили, удалите.
- `status` без кавычек не может быть значением, которое YAML читает как число, дату, null или
  булево. `date: 2026-11-04` без кавычек, как в шаблоне, допустимо.

## Как работать (совет, не проверяется)

- Сначала выпишите из интервью все решения, потом требования, потом примеры: на каждое из восьми
  решений о времени один маленький пример (один местный день, 1-3 слота) при `now` из рекомендации.
- Ожидаемый список можно не считать вручную до конца: проверка покажет список модели для первого
