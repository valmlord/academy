# Итоговый проект: бронирования на Go

**Твой шаг.** В эталонном плане урока 1 это серверная часть срезов 4-6: приглашённый бронирует
слот, занятый слот отклоняется (REQ-11, REQ-16), одновременные и повторные запросы создают одно
бронирование (REQ-17, REQ-18), отмена освобождает слот (REQ-10, REQ-19). Номера REQ здесь и ниже
из спецификации стартера, в своей нумерации они могут быть другими. Вертикальная команда делала бы
это в срезах 4-6 вместе с формой на странице. Здесь только API: страница придёт в уроке 6.

## Проблема

Первая версия `POST /bookings` обычно такая: под `RLock` посмотреть, свободен ли слот, отпустить
блокировку, под `Lock` записать. На ручной проверке всё верно. `sync.RWMutex` устроен так: "The lock
can be held by an arbitrary number of readers or a single writer". Два запроса на один слот вместе
проходят проверку под чтением, оба видят "свободно", оба пишут. У хоста два звонка в 10:00.

Вторая беда приходит с плохой сетью. Мобильный клиент отправил бронирование, ответ потерялся, клиент
повторил запрос. Без ключа идемпотентности это второе бронирование того же человека.

Обе ошибки не видны на одном запросе. На ноутбуке окно между проверкой и записью короткое, и гонка
проявляется редко: тесты зелёные, а двойное бронирование случается в проде.

## Идея: одна атомарная секция и память ответов

1. **Проверка и запись неделимы.** Между "слот свободен" и "бронирование записано" никакой другой
   запрос не может ни проверить, ни записать конфликтующий слот. Самая простая форма: один
   `sync.Mutex` на хоста вокруг проверки и записи.
2. **Шов задержки делает гонку видимой.** Сервер читает `CALENDAR_BOOKING_DELAY_MS` и спит столько
   миллисекунд после успешной проверки и до записи. Пока идёт задержка, конкурирующий запрос на
   этот слот не отвечает: он ждёт, пока судьба слота решится, и потом получает 409. Проще всего
   держать одну блокировку на проверку, задержку и запись. Запрос, который проверку не прошёл,
   отвечает сразу, без задержки. С задержкой 150-250 мс окно гонки широкое: в
   замерах курса сервер с проверкой под `RLock` и записью под `Lock` не прошёл ни одного из 200
   запусков проверки.
3. **Ключ идемпотентности это память.** Сервер запоминает ключ, тело и ответ. Тот же ключ с тем же
   телом получает тот же ответ, а не второе бронирование.

## 409 или 422

В контракте две "неудачи" бронирования, и у каждой своё значение:

- **422**: запрос правильный по форме, но так его не исполнить никогда. Старт вне сетки слотов, вне
  окон расписания, раньше минимального уведомления, за окном бронирования (`slot_unavailable`);
  неизвестный `eventTypeId` (`unknown_reference`); ключ с другим телом (`idempotency_mismatch`).
  Повтор не поможет.
- **409**: запрос можно исполнить в принципе, но он конфликтует с текущим состоянием: слот занят
  (`slot_taken`) или первый запрос с этим ключом ещё идёт (`idempotency_in_progress`). После отмены
  чужого бронирования тот же запрос может пройти.

Проверка доступности (422 slot_unavailable) не смотрит на бронирования. Слот, занятый другим
бронированием или его буфером, это 409 slot_taken.

Когда неверно сразу несколько вещей, ответ один, по порядку: 400, `unknown_reference`, ключ
идемпотентности (повтор, другое тело, ещё идёт), `slot_unavailable`, `slot_taken`. Старт вне сетки
поверх чужого бронирования это 422, а не 409.

Удобно считать это одним движком из урока 3, два раза. Без бронирований: старта нет среди слотов,
значит 422 `slot_unavailable`. С бронированиями хоста (подтверждёнными, с буферами их видов встреч):
старт пропал, значит 409 `slot_taken`. Бронирования любого вида встречи хоста занимают время для
всех его видов встреч (REQ-11).

## Как это выглядит в Go

Короткая программа не из нашего проекта, её можно запустить (`go run main.go`). Шесть горутин
одновременно бронируют один слот, сначала через `RWMutex`, потом через один `Mutex` вокруг
проверки, задержки и записи:

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

const delay = 200 * time.Millisecond

type racyStore struct {
	mu    sync.RWMutex
	taken map[string]bool
}

func (s *racyStore) book(slot string) bool {
	s.mu.RLock()
	busy := s.taken[slot]
	s.mu.RUnlock()
	if busy {
		return false
	}
	time.Sleep(delay)
	s.mu.Lock()
	s.taken[slot] = true
	s.mu.Unlock()
	return true
}

type atomicStore struct {
	mu    sync.Mutex
	taken map[string]bool
}

func (s *atomicStore) book(slot string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.taken[slot] {
		return false
	}
	time.Sleep(delay)
	s.taken[slot] = true
	return true
}

func winners(book func(string) bool) int {
	var wg sync.WaitGroup
	var mu sync.Mutex
	count := 0
	for range 6 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			if book("2026-03-02T09:00:00Z") {
				mu.Lock()
				count++
				mu.Unlock()
			}
		}()
	}
	wg.Wait()
	return count
}

func main() {
	fmt.Println("RWMutex:", winners((&racyStore{taken: map[string]bool{}}).book))
	fmt.Println("Mutex:", winners((&atomicStore{taken: map[string]bool{}}).book))
}
```

Первая строка покажет 6 бронирований одного слота, вторая 1. `Lock` блокирует: "If the lock is
already in use, the calling goroutine blocks until the mutex is available". Пять проигравших ждут,
потом видят занятый слот и сразу получают `false`; на сервере это 409 без задержки.

Задержка под блокировкой выстраивает все бронирования хоста в очередь. Для учебного сервера это
нормально: без переменной `CALENDAR_BOOKING_DELAY_MS` задержки нет.

## Как пробы видят, где стоит задержка

Проверка шлёт 6 одновременных запросов на попарно конфликтующие слоты и несколько запросов вокруг
них.
Правила с точными долями задержки описаны в задании, суть такая:

- **a:** запрос на уже занятый слот после раунда отвечает 409 быстрее половины задержки. Ловит
  задержку до проверки.
- **b:** список бронирований, полученный до конца задержки, не содержит бронирования раунда. Ловит
  запись до задержки, когда чтение не ждёт блокировку.
- **c:** конфликтующий запрос, отправленный посреди задержки, получает 409 примерно тогда же, когда
  победитель получает 201. Слишком рано значит, что он ответил, пока судьба слота ещё не решилась.
  Слишком поздно значит, что запрос сначала отспал свою задержку, то есть проверял слот, не
  дождавшись первого бронирования.

Курс принимает и форму с резервом: под той же блокировкой, что проверка, слот резервируется до
конца задержки, блокировка отпускается, задержка идёт вне её, потом запись. Она верна, если
конкурирующий запрос, который упёрся в резерв, ждёт, пока резерв разрешится, и только потом
получает 409. Если он ответит 409 сразу, это поймает правило c. Одна блокировка на проверку,
задержку и запись проще, и ошибиться в ней труднее.

## Ключ идемпотентности

Семантику курс берёт из Internet-Draft `draft-ietf-httpapi-idempotency-key-header-08` (22 октября
2026 года), это не RFC. Раздел 2.2: ключ "MUST NOT be reused with another request with a different
request payload". Раздел 2.7, оба правила со словом SHOULD: при повторе с другим телом "the resource
SHOULD reply with an HTTP `422` status code", а при повторе, пока первый запрос ещё выполняется,
"SHOULD reply with an HTTP `409` status code".

Синтаксис у курса свой, как в уроке 2: значение без кавычек, `^[A-Za-z0-9_-]{8,64}$`. В черновике
значение "MUST be a String (Section 3.3.3 of [RFC9651])", а такие строки по RFC 9651 "are
delimited with double quotes". Форма `"abcdefgh"` в кавычках у нас 400. Имя заголовка в любом
регистре: по RFC 9110 "Field names are case-insensitive".

Запоминать ключ стоит только у запроса, который дошёл до проверки слота. Запрос с ответом 400 или
422 `unknown_reference` ничего не бронировал, и его ключ остаётся свободным. Повтор ключа после
ответа 409 или 422 `slot_*` проверки не смотрят (список "не проверяются" в задании).

> **Go для TS-разработчика: параллельность.**
> - **Обработчики идут параллельно.** `http.Serve` принимает соединения, "creating a new service
>   goroutine for each". В JS функция "cannot be preempted and will run entirely before any other
>   code runs", и гонка возможна только между заданиями очереди. В Go обработчики двух соединений
>   выполняются одновременно, и общие данные без блокировки читаются и пишутся вперемешку.
> - **`sync.Mutex` без конструктора.** "The zero value for a Mutex is an unlocked mutex". Поле
>   `mu sync.Mutex` в структуре готово к работе. Структуру с мьютексом не копируйте: "Values
>   containing the types defined in this package should not be copied", держите `*Store`.
> - **`defer mu.Unlock()`** сразу после `Lock`: блокировка отпустится на любом `return`.
> - **Задержка:** `time.Sleep(time.Duration(ms) * time.Millisecond)`, `ms` из
>   `strconv.Atoi(os.Getenv("CALENDAR_BOOKING_DELAY_MS"))`; пустая переменная значит 0.
> - **Заголовок:** `r.Header.Get("Idempotency-Key")` не зависит от регистра имени, но "If there are
>   no values associated with the key, Get returns """: пустое значение и отсутствие не различить.
>   Пробы пустое значение не шлют.

## Частые ошибки

- `RWMutex`: проверка под `RLock`, запись под `Lock`. Два бронирования.
- Блокировка на слот (по старту) или на вид встречи: конфликт через буфер или через другой вид
  встречи того же хоста проходит.
- Задержка до проверки: занятый слот отвечает 409 только через задержку (правило a).
- Запись до задержки при чтении без блокировки (правило b).
- Проверка без блокировки, задержка, перепроверка и запись под блокировкой: двойного бронирования
  нет, но 409 приходит после собственной задержки (правило c).
- SQLite с `BEGIN` по умолчанию. Транзакция `DEFERRED` становится пишущей только на записи, и если
  другое соединение уже пишет, "the write statement will fail with SQLITE_BUSY". Это 500 вместо 409.
- 409 вместо 422 для старта вне сетки, который совпал с чужим бронированием.
- Ключ запомнен у запроса, который получил 400: следующий правильный запрос с этим ключом получит
  `idempotency_mismatch`.

## Что делать в практике

Начните с `POST /bookings` без ключа: проверка тела, `unknown_reference`, два вызова движка, запись.
Потом хранилище под одним мьютексом и шов задержки, потом ключ, потом отмена и `GET /bookings`.
Если берёте SQLite (modernc.org/sqlite), задание говорит, как обернуть транзакцию. Правила проверок
и окружение описаны в задании.
