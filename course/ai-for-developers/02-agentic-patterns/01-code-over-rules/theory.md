# Менять код, а не правила

## Проблема

Агент в третий раз передал дни вместо суммы. Добавить четвёртый восклицательный знак в CLAUDE.md или
сделать так, чтобы перепутать было нельзя?

У функции пени два целых аргумента подряд: сумма в центах и дни просрочки. Перепутать их легко, а
тест ловит перестановку не всегда: при маленькой просрочке оба порядка дают ноль. Строка "NEVER swap
them" ничего не меняет в коде. В следующей сессии агент снова увидит два `int` подряд и снова будет
угадывать.

## Идея: у каждого правила своё место

Рекомендации Claude Code (на 2026-10-30) делят инструкции на два вида. Недетерминированные (промпт, CLAUDE.md,
скилл) "Claude (the model) reads", и решает модель. Детерминированные (хук, deny-правило, управляемая
настройка) "Claude Code (the harness) *has* to execute". Эту границу для прав и хуков вы уже провели в
уроке 6 модуля 00. Здесь она опускается ниже, в сам код проекта.

Правило работает в обе стороны. Если строку в CLAUDE.md приходится подчёркивать снова и снова, а
агент её всё равно пропускает, ей место в хуке. И обратно: "if you have hooks for things that are
only preferences, delete them and let Claude decide". Почти у каждого правила стиля есть исключения,
и модель с кодом перед глазами решает их лучше, чем запрет, написанный заранее.

### Направляющие и сенсоры

Böckeler ("Harness engineering for coding agent users", 2026) называет всё, что пользователь строит
вокруг агента, внешней обвязкой и делит её на два вида:

- **guides** (feedforward) направляют агента до действия. Её примеры: файл памяти (AGENTS.md),
  скиллы, документация об архитектуре и how-to, языковой сервер и CLI, инструмент с рецептами
  codemod (OpenRewrite);
- **sensors** (feedback) наблюдают после действия и помогают агенту исправиться: тесты, линтеры,
  проверка типов, ревью ИИ.

И те и другие бывают **computational** (детерминированные и быстрые, их выполняет обычная программа)
и **inferential** (решает модель, например ревью ИИ; медленнее, дороже и менее детерминированы).
Ещё одно её понятие, harnessability: не любой код одинаково поддаётся обвязке. Строгие типы делают
проверку типов сенсором, чёткие границы модулей делают возможными правила архитектуры.

В терминах этого модуля: память и код это направляющие (сигнатура функции и понятное имя тоже
направляют агента, это наше расширение её списка), проверки и хуки это вычислительный контроль.

### Почему не просто ещё одна строка

- Gloaguen et al. (v3, 2026) нашли, что инструкции из файлов контекста агенты исполняют хорошо. Это
  палка о двух концах: неверное или лишнее правило агент выполнит добросовестно и потратит на него
  шаги. Как отбирать содержимое памяти, разобрано в уроке 5 модуля 00.
- OpenAI (Lopopolo, 2026) описывает, как у них не сработал один большой AGENTS.md: он вытесняет из
  контекста задачу, "too much guidance becomes non-guidance", устаревает, и механически его не
  проверить. Их AGENTS.md около 100 строк, это карта к каталогу `docs/`, где лежат подробности. Когда
  документации не хватает, "we promote the rule into code". И ещё одно наблюдение: агенты копируют
  паттерны, которые уже есть в репозитории, в том числе плохие.
- Hashimoto ("Engineer the Harness", 2026) советует каждую ошибку агента исправлять так, чтобы она не
  повторилась. Форм у исправления две: строка в AGENTS.md о повторяющейся неверной команде или API и
  "actual, programmed tools", то есть скрипты, которыми агент проверяет свою работу. Строка в памяти
  здесь законный первый шаг, а не ошибка.

Hashimoto считает строки памяти исправлениями, а Claude Code и Böckeler тянут обязательные правила в
хуки и сенсоры. Противоречия нет: память для подсказок, код и хуки для того, что должно выполняться
всегда.

### Poka-yoke: сделать ошибку невозможной

Anthropic в "Building effective agents" переносит на инструменты агента принцип poka-yoke (защита от
ошибки): "Change the arguments so that it is harder to make mistakes". Их пример: агент путался в
относительных путях, и инструмент стал требовать абсолютные. Для кода проекта это значит:

- сигнатура, в которой ошибку нельзя написать;
- удалённый мёртвый модуль, который больше некому скопировать;
- одна точка входа вместо трёх похожих.

Пример с аргументами только по имени (всё после `*`):

```python
def discount(*, price_cents: int, percent: int) -> int:
    return price_cents * percent // 100


print(discount(price_cents=1000, percent=15))  # 150
print(discount(1000, 15))  # TypeError: discount() takes 0 positional arguments but 2 were given
```

Теперь вызов без имён не запускается, а перестановка видна глазами: `percent=price` читается как
ошибка.

## Лестница размещения

Это словарь всего модуля: уроки 3 и 5 пользуются им же. Семь вопросов об одной строке файла памяти,
по порядку; решает первый ответ "да", дальше не спрашивают. "Код" здесь это исходники Python в
`src/` или `scripts/`; файлы данных, Makefile, документация и настройки кодом не считаются. `hook`
это всё, что останавливает агента в момент хода: PreToolUse- или Stop-хук и правило
`permissions.deny` в настройках; Stop-хук, который запускает `make check`, тоже `hook`. `check` это
программа, которая находит нарушение после факта: тест, линтер, проверка в `make check`.

1. Строка это команда, которой агент собирает, тестирует или проверяет весь проект? -> `memory`.
   Команда для одной части (например, перегенерировать один каталог) к этому шагу не относится.
2. Строку уже обеспечивает хук или проверка, которые есть в репозитории (`.claude/settings.json`,
   Makefile, тесты)? -> этот слой, `hook` или `check`. Гарантия живёт там, а из памяти строка уходит в
   любом случае.
3. Агент, который проигнорирует строку, всё равно сделает правильно, потому что строка только
   описывает то, что видно в репозитории, или выражает предпочтение с законными исключениями? ->
   `delete`.
4. Может ли изменение кода сделать ошибку невозможной или убрать то, что вводит в заблуждение
   (сигнатура, удаление мёртвого модуля, одна точка входа), не нарушив контракт, задокументированный
   в репозитории? -> `code`. "Да" только тогда, когда изменение предотвращает ошибку именно этой
   строки. Удаление мёртвого модуля исправляет строку об этом модуле, но не правило, которое
   запрещает импорт: любой другой файл по-прежнему может его написать.
5. Нужно ли остановить агента в определённый момент хода, до вызова инструмента или до конца хода,
   потому что найти нарушение позже уже поздно? -> `hook`.
6. Может ли детерминированная программа найти нарушение после факта (тест, линтер, структурный
   тест)? -> `check`.
7. Иначе (факт, который репозиторий показать не может, суждение, причина) -> `memory`.

Порядок важен. Шаг 1 стоит первым, потому что команда проверки, по словам рекомендаций Claude Code,
"the single most useful line in your CLAUDE.md". Шаг 3 стоит до шагов 4-6: строку, которая ничего не
защищает, не надо превращать в код. Шаг 4 стоит до хука и проверки: ошибку, которую нельзя написать,
не нужно ловить.

### Два прохода по лестнице

Строка "В `src/` не читай `os.environ` напрямую, только через `config.settings`" в проекте, где
нет ни линтера, ни подходящего хука:

1. нет, это правило, а не команда;
2. нет, ничего в репозитории его не обеспечивает;
3. нет, агент, который её проигнорирует, обойдёт настройки;
4. нет, изменением исходников нельзя запретить импорт `os`;
5. нет, найденное после хода чинится одной правкой, ничего необратимого не случилось;
6. да, программа найдёт `os.environ` в `src/` по дереву разбора. Ответ: `check`.

Строка "`discount` принимает сначала цену, потом процент" в проекте с позиционной сигнатурой: шаги
1-3 дают "нет" (это правило, ничто его не обеспечивает, перестановка и есть вред), шаг 4 даёт "да":
сигнатура выше делает перестановку невозможной. Ответ: `code`, и строка из памяти уходит.

## Частые ошибки

- Добавлять IMPORTANT и восклицательные знаки. Рекомендации Claude Code: нагромождение акцентов
  "mostly makes Claude over-apply the rule".
- Перевести позиционные вызовы на имена по позиции: `f(days, amount)` превращается в
  `f(amount_cents=days, days_late=amount)`. Перестановка осталась, но теперь её видно в диффе.
  Читайте дифф, прежде чем принять.
- Унести правило в другой файл памяти или подключить его импортом и считать, что в памяти его больше
  нет.
- Оставить строку в CLAUDE.md, когда её уже обеспечивает хук: гарантия в хуке, строка только тратит
  контекст.
- Принять команду для одной части проекта за команду проверки всего проекта.
- Ставить хук на предпочтение: исключения есть почти у каждого правила стиля.

## Что делать в практике

Вы разложите 12 правил раздутого CLAUDE.md по пяти ступеням, уберёте из него всё, что ушло на
другие ступени, сделаете аргументы `late_fee` только именованными, исправите вызовы и удалите
мёртвый модуль. Начните с того, что уже есть в репозитории: для шага 2 нужно знать его хуки и цели
Makefile. Как устроены PreToolUse-хук и deny-правила, разобрано в уроке 6 модуля 00, Stop-хук в
уроке 1 модуля 01.
