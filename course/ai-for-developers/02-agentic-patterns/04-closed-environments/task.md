# Задание: закрытый контур

Время: около 60 минут, из них около 35 практика:

- теория: около 25 минут;
- бриф в список требований: около 4 минут;
- найти расхождения (файл, ключ и действующее значение по каждому требованию): около 13 минут;
- исправить: около 10 минут;
- прогоны проверки и доводка: около 8 минут.

## Что в рабочей папке

Репозиторий `invoice-service` в состоянии после урока 3, без `failure-log.json`, `incidents/` и без
каталога `.git`. Кроме того:

- `docs/contour-brief.md`: бриф банка (вымышленный). Это главный документ задания: что разрешено, что
  запрещено, какие адреса и файлы есть в контуре.
- `launcher.env`: профиль банка, который загружают лаунчер и каждая login-оболочка.
- `.claude/settings.json`: настройки проекта, в том числе хуки из прошлых уроков.
- `home/.claude/settings.json`: стоит на месте вашего `~/.claude/settings.json` (пользовательские
  настройки).
- `.claude/settings.local.json` нет, его можно создать.

В стартовом состоянии каждое из требований G1-G7 ниже нарушено, а N1-N4 выполнены, и их нельзя
сломать.

## Осторожно: это живые настройки

`.claude/settings.json` (и `.claude/settings.local.json`, если вы его создадите) это настоящие
настройки Claude Code, а не текст. Сессия Claude Code, открытая в этой папке, после того как вы
примете доверие к папке, применит их `env`, адрес шлюза и `apiKeyHelper`. Ключ шлюза важнее вашего
сохранённого входа, так что сессия перестанет работать с вашей учётной записью. Работайте одним из
способов:

- правьте файлы руками в редакторе;
- запустите агента вне этой папки и дайте ему путь к файлам;
- запустите Claude Code в этой папке как `claude --setting-sources user`: тогда загружаются только
  пользовательские настройки, а проектные и локальные нет.

## Готово, когда

Для сессии Claude Code в терминале в доверенной папке (Desktop-приложение и self-hosted раннер
строят своё окружение запуска, а проектные и локальные `env` и `apiKeyHelper` в интерактивной сессии
ждут доверия к папке; эти случаи вне задания):

- **G1**: каждый запрос Claude Code идёт в шлюз из брифа.
- **G2**: токены выдаёт только программа банка для токенов, и ни в одном файле рабочей папки не
  осталось статического токена.
- **G3**: необязательный трафик Claude Code выключен.
- **G4**: uv в терминалах команды ставит пакеты только из зеркала из брифа.
- **G5**: uv в терминалах команды доверяет корневому CA банка.
- **G6**: у агента нет веб-инструментов, а инструменты для файлов и оболочки остались.
- **G7**: команды в песочнице достают до зеркала и ни до какого другого хоста, и никакой запрос
  разрешения этого не расширит.
- **N1**: Claude Code по-прежнему доверяет корневому CA банка.
- **N2**: ни один запрос не уходит к другому провайдеру в обход шлюза.
- **N3**: лаунчер может прочитать свой профиль (формат строк из брифа).
- **N4**: файлы настроек разбираются, а хуки проекта остаются на месте и включены, и скрипты хуков
  не изменены.

Общее правило для всех пунктов:

- Проверка читает `launcher.env`, `.claude/settings.json`, `.claude/settings.local.json`, если он
  есть, и `home/.claude/settings.json` (он стоит на месте `~/.claude/settings.json`). Чтобы найти
  оставшийся токен, она читает каждый файл рабочей папки.
- Действующее значение переменной: первое, что её задаёт, среди `env` локальных, затем проектных,
  затем пользовательских настроек, затем `launcher.env`. Так получается, потому что настройки
  действуют поверх оболочки, а между собой идут по порядку старшинства. Действующее значение
  настройки: первое из локальных, проектных и пользовательских, кроме случаев, где документация
  говорит иначе: `sandbox.network.strictAllowlist` из трёх файлов упражнения действует только из
  пользовательских настроек, а
  `false` для `sandbox.allowUnsandboxedCommands` в пользовательских настройках держится, даже если
  проект или локальные настройки ставят `true`.
- Проходит любая форма, которой документация Claude Code или uv даёт нужный эффект, там, где по
  документации она действует. Форма, у которой по документации нет эффекта или эффект другой, не
  проходит.
- Ограничения брифа сужают формы:
  - терминалы команды читают только `launcher.env`;
  - файлы настроек uv (`pyproject.toml`, `uv.toml` на уровне проекта, пользователя или системы) на
    машинах команды не учитываются;
  - командам Bash нужно только зеркало, поэтому `sandbox.excludedCommands` в любом файле настроек
    остаётся пустым: перечисленные там команды идут в обход песочницы;
  - пакеты только из зеркала, порт 443; источник пакетов для uv это не только индекс, но и
    `UV_FIND_LINKS` с адресом;
  - токены печатает только программа банка для токенов; статический токен это любой ключ, записанный
    в файл, в том числе заголовок с ключом (`Authorization`, `x-api-key`) в `ANTHROPIC_CUSTOM_HEADERS`;
  - лаунчер читает строки `KEY=VALUE` как есть.
- Проверка называет каждое невыполненное требование по его id. Файл, ключ и значение она не
  называет. Число попыток не ограничено.

Квиз: не меньше 5 верных из 6.

## Как проверяется

**`contour-config`** (команда в рабочей папке). Проверка ничего не запускает и не ходит в сеть: она
читает файлы из общего правила и вычисляет действующие значения. На каждое невыполненное требование
она печатает одну строку, которая начинается с "не выполнено:", затем id и формулировку из "Готово,
когда", например:

```text
не выполнено: G5: uv в терминалах команды доверяет корневому CA банка
```

Проверка пройдена, когда таких строк нет.

**`closed-environments-quiz`** (квиз): 6 вопросов-сценариев, нужно 5 верных. В вопросах с пометкой
"выберите все верные" засчитывается только точный набор ответов.

## Как работать (совет, не проверяется)

- Первый шаг: перепишите строки брифа в список требований.
- Для каждого требования найдите файл и ключ, которые должны его обеспечивать сейчас, а для каждой
  переменной запишите, значение из какого файла побеждает (действующее значение из общего правила).
  Найденные расхождения и есть задание.
- Потом исправьте их и запустите проверку: она назовёт требования, которые ещё нарушены, каждое
  строкой "не выполнено:".

## Попытки и подсказки

- `contour-config`: число попыток не ограничено; после 5 неудачных интерфейс предложит ментора.
- Квиз: не больше 3 попыток. После неудачи показывается только общий балл. Ответы и пояснения
  открываются после прохождения или после 3-й неудачной попытки, и тогда квиз закрывается как "не
  пройдено" с разбором у ментора.
- Ментор между попытками задаёт вопросы и подсказывает направление. Он может обсуждать требование,
  которое проверка уже назвала, но не называет файл, ключ или значение. По квизу он не говорит, какой
  вопрос неверен.
