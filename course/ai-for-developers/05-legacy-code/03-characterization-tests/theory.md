# Characterization-тесты: зафиксировать то, что код делает

## Проблема

Агент написал первый тест на этикетку parcel-desk. Тест сравнивает дату отправки с `date.today()` плюс один день и зелёный у вас в Москве. Ночью CI на сервере в часовом поясе Pacific/Kiritimati (UTC+14) падает: в Москве ещё 23:30 9 марта, а там уже 10:30 10 марта, и "завтра" у теста и у кода разное. Утром тест снова зелёный. Команда решает, что тест "иногда флапает", и перестаёт ему верить.

Тест был не про код, а про часы машины. Он не фиксировал поведение, он его угадывал.

## Идея: сначала записать, что код делает

Майкл Фезерс в книге "Working Effectively with Legacy Code" (2004) даёт legacy-коду короткое определение. Николас Карло в разборе книги приводит его так: "Legacy Code is code without tests". Менять такой код страшно, потому что не видно, что сломаешь. Ответ Фезерса, в том же разборе: characterization-тест, "a test that characterizes the actual behavior of a piece of code". Он фиксирует то, что код делает сейчас, а не то, что должен. Странное поведение тоже фиксируется: если манифест округляет рубли не так, как вы ожидали, тест записывает именно это округление. Решать, ошибка ли это, вы будете потом, отдельным изменением.

Порядок работы с legacy-кодом по Фезерсу, как его даёт Карло ("Identify change points (Seams)", "Break dependencies", "Write the tests", "Make your changes", "Refactor"):

1. Найти точки изменения (швы).
2. Разорвать зависимости.
3. Написать тесты.
4. Внести изменения.
5. Отрефакторить.

В этом уроке вы проходите шаги 1-3. Шаги 4 и 5 в следующем уроке.

## Шов: как подменить часы, не правя код

Шаги 1 и 2 держатся на понятии шва. Фаулер цитирует Фезерса: шов это "a place where you can alter behavior in your program without editing in that place". В Python самый частый шов это имя, которое модуль ищет у себя во время вызова. Документация `unittest.mock`: "you patch where an object is looked up, which is not necessarily the same place as where it is defined".

В legacy-коде обычно четыре вида скрытых входов, и у каждого свой шов:

- часы (`datetime.now()`, `date.today()`): подменить имя в модуле, который их вызывает;
- случайность (`random`): подменить функцию или зафиксировать результат;
- состояние модуля (кэш, счётчик, настройка, прочитанная при импорте): подменить на время теста и вернуть;
- файлы: направить запись во временный каталог.

Пример. Модуль `stamp.py`:

```python
from datetime import datetime


def stamp_line(name: str) -> str:
    return f"{name} {datetime.now():%Y-%m-%d}"
```

Тест `test_stamp.py` рядом с ним замораживает часы через шов `stamp.datetime`:

```python
import datetime
import unittest
from unittest import mock

import stamp


class FrozenDatetime(datetime.datetime):
    @classmethod
    def now(cls, tz=None):
        return cls(2026, 3, 9, 23, 30, tzinfo=tz)


class StampLineTest(unittest.TestCase):
    def test_stamp_uses_frozen_day(self):
        with mock.patch.object(stamp, "datetime", FrozenDatetime):
            self.assertEqual(stamp.stamp_line("A"), "A 2026-03-09")
```

Запуск: `python3 -m unittest test_stamp` в каталоге с обоими файлами. Тест даёт один результат в любом часовом поясе и в любой день.

Ещё один скрытый вход это порядок. Хеши строк по умолчанию случайны в каждом процессе (документация Python, `PYTHONHASHSEED`: "a random value is used to seed the hashes of str and bytes objects"), поэтому строка, собранная обходом множества, может выходить в разном порядке от запуска к запуску. Если код так делает, тест сравнивает отсортированные части, а не строку целиком. Порядок тестов тоже не гарантирован: каждый тест сам готовит свои файлы и своё состояние.

## Golden master

Когда вывод большой (файл манифеста, словарь этикетки), его удобнее записать целиком. ApprovalTests: "Approvals work by comparing the test results to a golden master". Тест сохраняет результат в файл, человек смотрит его и одобряет, дальше тест сравнивает с одобренным. Главное правило: помощник никогда не одобряет сам. Если эталона нет или результат другой, он пишет рядом полученный файл и падает, а одобряет человек.

В рабочей среде курса нет pip, поэтому ApprovalTests (20.0.1, нужен pytest 8) и syrupy (7.0.2, плагин pytest) здесь не поставить. В стартовой папке есть свой маленький помощник на стандартной библиотеке.

## Тест должен уметь падать

Тест, который проходит на исходном коде, ещё ничего не доказал. Марк Симанн советует после зелёного теста "Sabotage the SUT so that it fails the assertion", потому что "It happens with surprising regularity that you inadvertently write a tautological assertion". Сломайте строку в коде, посмотрите, что тест покраснел, верните.

Автоматическая версия этой привычки это мутационное тестирование: инструмент вносит в код мелкие правки (мутанты) и запускает ваши тесты. Если тесты прошли, мутант "выжил": поведение, которое он изменил, ничем не зафиксировано. Выживший мутант это не ошибка кода, а дыра в тестах. Инструменты для Python: mutmut (3.8.1, нужна поддержка fork) и cosmic-ray (8.9.0). В этом уроке мутантов готовит сама проверка. Так же делает Anthropic в своей статье о миграции кода: судья проверяет исходный и новый код "on equal terms" и должен проходить на исходном и падать на нарочно сломанном.

## Ограда, а не песочница

Проверка запускает ваши тесты в копии под аудит-хуками Python и не даёт им писать и читать за пределами копии, запускать процессы и загружать исходный код в обход проверяемой версии. Документация Python про `sys.addaudithook` прямо говорит, что такие хуки "are not suitable for implementing a "sandbox"". Это ограда от случайных ошибок честного теста и от дешёвых обходов, а не защита от того, кто захочет её обойти. Такие места читает ментор.

## Частые ошибки

- Сравнивать с настоящей сегодняшней датой или текущим часом вместо замороженных часов.
- Сравнивать строку, собранную из множества, как есть.
- Писать файлы в общий каталог и полагаться на порядок тестов.
- Чинить странное поведение в тесте: тест ожидает "правильное" значение и падает на исходном коде.
- Тавтология: `assertEqual(f(x), f(x))` или golden, который переписывается при каждом запуске.
- Не проверить, что тест умеет падать.

## Что делать в практике

Вы напишете characterization-тесты для этикеток и манифеста parcel-desk. Сначала найдёте скрытые входы и швы, потом зафиксируете поведение, в том числе странное, и проверите каждый тест саботажем. Проверка запустит ваши тесты на исходном коде в пяти часовых поясах и на двенадцати скрытых изменённых версиях.
