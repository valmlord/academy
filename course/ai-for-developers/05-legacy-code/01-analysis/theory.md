# Анализ чужого проекта: проверяем выводы агента по коду

## Проблема

Возьмём выдуманный сервис библиотеки loan-desk: он выдаёт книги, считает штрафы за просрочку и рассылает напоминания. Тестов нет, README писали давно. Вы просите агента разобраться, и он уверенно отвечает: "`fines/old_rules.py` нигде не импортируется, его можно удалить". Поиск по `import old_rules` и правда ничего не находит, и файл удалён.

Через месяц три филиала перестают начислять штрафы. Модуль вызывался не через `import`: в `config/branches.csv` у каждого филиала записано строкой, каким модулем считать штраф, и код загружает модуль по этой строке. Агент искал импорт, а не имя.

Агент не соврал. Он сделал вывод по той части кода, которую прочитал. В legacy-проекте такие выводы чаще всего ошибаются там, где поведение не видно из одного файла. Этот урок про то, как проверять их по коду, прежде чем действовать.

## Идея: вывод агента это гипотеза

Каждое утверждение агента о чужом коде ("не используется", "зависит только от аргументов", "только читает", "это баг") принимайте как гипотезу, которую надо проверить по коду, данным и сборке. В первую очередь проверяйте утверждения, за которыми идёт действие: удалить файл, "исправить" поведение, записать эталон для теста, запустить команду на настоящих данных.

Best practices Claude Code называет такие места среди того, что стоит записать в память проекта: "Places where the code is misleading: an old pattern that's everywhere but that new code must not copy, or a directory that looks unused but isn't". Код, который выглядит мёртвым, но работает, это типичная ловушка legacy.

Шесть мест, где выводы ломаются чаще всего:

- Вызов по строке. Модуль, функция или команда достаются по имени из данных, конфига или Makefile (`importlib`, `getattr`, словарь обработчиков). Поиск по `import` их не видит. Ищите само имя везде: в коде, в данных, в Makefile.
- Скрытые входы. "Результат зависит только от аргументов" неверно, если функция читает часы, случайность, переменную модуля или файл, который ей не передали, или зависит от порядка обхода множества. Тогда один и тот же вызов даёт разные ответы.
- Побочные эффекты. "Функция только читает" неверно, если она пишет, переименовывает или удаляет файлы. Тогда запускать её "посмотреть" на настоящих данных нельзя.
- Поведение, на которое опираются. Закон Хайрама: "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody." Странное условие, похожее на ошибку, может быть тем, на что рассчитывает соседний модуль или внешний потребитель. Прежде чем "исправлять", найдите, кто ещё зависит от этого поведения.
- Документация против кода. README, docstring и комментарии устаревают. Когда агент пересказывает поведение по README, сверьте пересказ с кодом: решает код.
- Исследование, которое меняет состояние. Команда, запущенная "чтобы посмотреть вывод", может писать файлы или трогать внешние системы. Прочитайте, что она делает, до запуска.

## Как исследовать: от общего к частному

Рецепт "Understand new codebases" в документации Claude Code начинается с запуска `claude` из корня проекта и общего вопроса `give me an overview of this codebase`. Потом вопросы сужаются: `explain the main architecture patterns used here`, `what are the key data models?`. Совет оттуда же (рецепт "Get a quick codebase overview"): "Start with broad questions, then narrow down to specific areas". Соседний рецепт под тем же заголовком, "Find relevant code", советует говорить на языке предметной области проекта ("Use domain language from the project") и просить проследить поток выполнения, как в его примере `trace the login process from front-end to database`.

Обзор даёт карту, но не доказательства. Когда дело доходит до действия, проверьте вывод сами. Пример из того же loan-desk: агент говорит, что модуль не используется. Ищите не импорт, а имя:

```bash
grep -rn "old_rules" --exclude-dir=__pycache__ .
```

Если имя нашлось в `config/`, в файлах данных или в Makefile, модуль живой, даже если ни один `import` на него не указывает. Для "зависит только от аргументов" прочитайте тело функции и всё, что она вызывает, и ищите `now()`, `today()`, `random`, `open(` и переменные модуля. Для "только читает" ищите запись, переименование и удаление файлов.

## Инструменты исследования и что они загружают

Explore. Встроенный субагент Explore по документации это "A fast, read-only agent optimized for searching and analyzing codebases", и в строке его инструментов стоит "read-only tools; Write and Edit are denied". Поручение "найди и сразу исправь" правку ему не откроет. Важнее другое (раздел "Built-in subagents" страницы про субагентов): "Explore and Plan start without your CLAUDE.md files and the git status snapshot to keep research fast and inexpensive". Предупреждение, записанное только в корневом `CLAUDE.md`, Explore на старте не получает. То же с правилом `.claude/rules/*.md` без `paths`: в разделе "What loads at startup" правила проекта входят в иерархию CLAUDE.md, и про неё сказано "The built-in Explore and Plan agents skip this". До Explore доходят `CLAUDE.md` подкаталога и подходящие правила с `paths`: они "still load when the subagent works with files there" (раздел "What loads at startup"). Где размещать такие факты, разберём в следующем уроке.

Plan mode. Страница про режимы разрешений: "Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source. Except in interactive terminal sessions with bypass permissions available, edits stay blocked until you approve the plan." Plan mode держит правки, но не команды оболочки. Что будет с командой во время планирования, решает первый подходящий случай:

- интерактивный терминал, где доступен режим bypass permissions: "neither the classifier nor a prompt applies to planning commands";
- доступен auto mode и включена настройка `useAutoModeDuringPlan` (по умолчанию она включена): команды, кроме удалений критических путей, вместо вопроса вам просматривает классификатор; одобренные выполняются, отклонённые блокируются;
- auto mode недоступен или `useAutoModeDuringPlan` выключена: команды вне встроенного набора команд только для чтения спрашивают разрешение.

Поэтому `make purge-cache` в том же loan-desk (рецепт `rm -rf cache/*`) plan mode сам по себе не останавливает. Остановить её может вопрос вам, классификатор или правило deny ("Deny rules block in every mode, including `bypassPermissions`"), а не сам режим.

Ссылки @. `@файл` добавляет содержимое файла в разговор, если оно укладывается в лимит инструмента Read, по умолчанию 25 000 токенов; текстовый файл больше 256KB не добавляется. Ссылка на каталог устроена иначе: "Directory references show file listings, not contents". `@fines/` покажет агенту, какие там файлы, но не их код.

## Частые ошибки

- "Нигде не импортируется" принято за "не используется": имя не искали в данных и Makefile.
- "Зависит только от аргументов" принято без чтения тела функции и того, что она вызывает.
- Пересказ README принят за поведение кода.
- Странное условие "исправлено", а соседний модуль на него опирался.
- Команда запущена "посмотреть", а она пишет файлы. Plan mode от этого сам по себе не защищает.
- От `@каталог` ждут содержимого файлов.
- Факт, который нужен Explore, записан только в корневом `CLAUDE.md`.

## Что делать в практике

В рабочей папке лежат parcel-desk и `transcript.md`, запись сессии, в которой агент разбирается в этом репозитории, делает выводы и кое-что меняет. Часть выводов и действий неверна, часть верна и только похожа на ошибку. Проверьте каждое утверждение по файлам рабочей папки, определите категорию по лестнице из задания и запишите находки в `findings.json`. Потом квиз по инструментам исследования.
