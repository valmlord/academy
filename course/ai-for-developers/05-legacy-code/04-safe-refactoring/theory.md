# Рефакторинг под сетью тестов

## Проблема

Вы просите агента почистить `shipping/quote.py`. Среди прочего он находит в выборе весовой ступени сравнение `weight_grams >= row["max_grams"]` и пишет: "похоже на ошибку на единицу, исправляю на `>`". Тесты зелёные: на границу ступени их нет. Через неделю бухгалтерия перевозчика присылает расхождение. Манифест считает колонку ступени для перевозчика тем же `>=`, и рядом комментарий: перевозчик выставляет счёт по этой колонке, она должна совпадать с расчётом цены. Посылка ровно на границе теперь оценена по одной ступени, а выставлена перевозчиком по другой.

Агент не ошибся в арифметике. Он поменял поведение, на которое опирался другой код, и назвал это рефакторингом.

## Идея: рефакторинг не меняет наблюдаемое поведение

Фаулер определяет рефакторинг как "a change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behavior". И дальше: это "a series of small behavior preserving transformations", а система остаётся рабочей после каждого шага.

Отсюда два следствия.

**Исправление ошибки это не рефакторинг.** Даже если `>=` действительно ошибка, её исправление меняет поведение. Такое изменение делается отдельно, с отдельным решением и с проверкой, кто на это поведение опирается. Закон Хайрама: "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody." В legacy-коде такой "кто-то" обычно соседний модуль, файл данных или внешняя система.

**Без сети тестов это не рефакторинг, а надежда.** Сеть это characterization-тесты из прошлого урока. Но сеть бывает дырявой: тесты зелёные, а часть поведения ничем не зафиксирована. Поэтому начинают здесь не с правки кода, а с проверки сети. Мутант, который выжил, показывает дыру. Её закрывают тестом на поведение, а не на устройство кода.

Порядок работы по Фезерсу тот же, что в уроке 3 (в разборе Николаса Карло: "Identify change points (Seams)", "Break dependencies", "Write the tests", "Make your changes", "Refactor"), и теперь вы доходите до шага 5:

1. Найти точки изменения (швы).
2. Разорвать зависимости.
3. Написать тесты.
4. Внести изменения.
5. Отрефакторить.

## Как это выглядит: вынести чистую функцию

Частый шаг в legacy-коде: вынести расчёт из функции, которая сама читает часы, файлы и глобальные настройки, в чистую функцию, которая получает всё аргументами. Старая точка входа остаётся и делегирует ей.

До:

```python
import datetime

FEE_PERCENT = 12


def price(weight_grams: int) -> int:
    base = 300 if weight_grams < 1000 else 500
    if datetime.datetime.now().hour >= 15:
        base += 100
    return base + base * FEE_PERCENT // 100
```

После:

```python
import datetime

FEE_PERCENT = 12


def price_of(weight_grams: int, is_late: bool, fee_percent: int) -> int:
    base = 300 if weight_grams < 1000 else 500
    if is_late:
        base += 100
    return base + base * fee_percent // 100


def price(weight_grams: int) -> int:
    is_late = datetime.datetime.now().hour >= 15
    return price_of(weight_grams, is_late, FEE_PERCENT)
```

`price` ведёт себя как раньше, а `price_of` можно тестировать без часов и без глобальных настроек. Сравнения `<`, `>=` и целочисленное деление остались теми же, даже если хочется их "исправить".

Фезерс называет близкий приём sprout: новый код пишется отдельной функцией или классом с тестами и вызывается из старого кода в одном месте. Тот же принцип на уровне системы это strangler fig у Фаулера: новая система растёт "on top of, yet separate to the legacy code base", а старая постепенно отмирает. В этом модуле strangler fig только теория: на одном уроке систему не заменить.

## Как просить агента

Документация Claude Code, рецепт "Refactor code": сначала найти, что менять, потом попросить предложения ("Get refactoring recommendations"), потом "refactor ... while maintaining the same behavior", потом запустить тесты. Совет оттуда же: "Do refactoring in small, testable increments". На практике это значит:

- в промпте прямо сказать, что поведение должно остаться тем же, включая странное;
- один шаг за раз: вынести, прогнать сеть, посмотреть дифф, следующий шаг;
- запретить трогать тесты сети: если тест мешает, агент говорит об этом, а не правит тест.

Почему это важно. Liu и др. (arXiv:2411.04444, 2024) измерили, что 13 из 176 рефакторингов, предложенных ChatGPT, и 9 из 137 у Gemini были небезопасны: меняли поведение или ломали синтаксис. Это чат-модели, а не агенты, и работа старше 2025 года, но порядок величины понятен: каждый шаг надо проверять сетью.

Дальнейшее чтение: раздел "Overeagerness" в рекомендациях Anthropic по промптам. Там описано, что Claude Opus 4.5 и Opus 4.6 склонны делать больше, чем просили, и дан пример промпта против этого.

## Частые ошибки

- Исправлять "ошибку" во время рефакторинга.
- Начинать рефакторинг, не проверив, что сеть ловит изменения.
- Закрывать дыру тестом на устройство кода (патчем внутреннего имени), а не на поведение.
- Читать настройки, часы или файлы внутри "чистой" функции.
- Менять сигнатуру или вывод старой точки входа.
- Ослабить или удалить тест сети, чтобы стало зелёным.
- Один большой шаг вместо нескольких маленьких.

## Что делать в практике

Сначала вы закроете тестами дыры в готовой сети расчёта цены: их назовёт проверка. Потом вынесете расчёт цены из `quote_parcel` в чистую функцию `price_kopecks` в новом модуле `shipping/pricing.py`, так что `quote_parcel` будет опираться на неё, и проверите, что поведение не изменилось.

Тесты проверка запускает, как в уроке 3: во временной копии, под аудит-хуками Python. Документация Python про `sys.addaudithook` говорит, что такие хуки "are not suitable for implementing a "sandbox"", поэтому это ограда от случайных ошибок честного теста и от дешёвых обходов, а не песочница.
