# Агент в процессе команды: гейт и план внедрения

## Проблема

Команда месяц работает с агентом на legacy-репозитории. На ретро все согласны: стало быстрее. Решают дать агенту открывать пул-реквесты самому.

Что говорят измерения. В рандомизированном исследовании METR 2025 года (16 опытных разработчиков, 246 задач в зрелых проектах, которые они знали) разработчики до начала ждали, что ИИ сократит время на 24%. Измерено обратное: с ИИ время выполнения задач выросло на 19%, то есть работа шла медленнее. А после исследования те же разработчики оценили, что ИИ сократил им время на 20%. Ощущение и измерение разошлись в разные стороны.

Это не значит, что агент всегда замедляет. В обновлении 2026 года METR для вернувшихся участников оценивает ускорение: время меньше на 18%, но доверительный интервал от минус 38% до плюс 9% проходит через ноль, а сами авторы называют данные "only very weak evidence" из-за эффектов отбора: часть разработчиков не захотела работать без ИИ, часть задач участники не принесли. Вывод для команды: решать по измерениям своего процесса, а не по ощущениям.

## Идея: судья до изменения

В статье Anthropic о миграции кода есть правило: "Let scripts - a compiler, a diff, a test suite - be the referee". Судья должен быть готов до того, как агент начнёт менять код, и проверять старое и новое на равных.

Для изменений агента в существующем репозитории такой судья это гейт: детерминированный скрипт, который принимает или отклоняет патч по правилам, записанным заранее. Важно, какими тестами он проверяет. Посмотрите на патч:

```diff
--- a/billing/fees.py
+++ b/billing/fees.py
@@ -3 +3 @@
-    return days * 50
+    return days * 40
--- a/tests/test_fees.py
+++ b/tests/test_fees.py
@@ -7 +7 @@
-        self.assertEqual(late_fee(3), 150)
+        self.assertEqual(late_fee(3), 120)
```

С этим патчем все тесты зелёные: поведение изменилось вместе с ожиданием. Если гейт запускает тесты, взятые до изменения, тест падает. Поэтому гейт проверяет патч дважды: старыми тестами (поведение сохранено) и тестами после патча (новые тесты агента тоже проходят), а правку существующих тестов не пускает вовсе.

## Этапы: от меньшего риска к большему

Внедрение идёт этапами. На каждом этапе понятно, что агенту можно и чего нельзя, и есть сигнал, по которому решают, идти ли дальше.

**Ревью без права решать.** Managed Code Review от Anthropic доступен только на планах Team и Enterprise. По документации, "A review never approves or blocks the pull request": он пишет комментарии и check run "Claude Code Review", который "doesn't conclude as a failure". Ревью только читает дифф и окружающий код, "without building or running your code". Инструкции он берёт из `REVIEW.md` "from the base or default branch and never from the pull request's own changes": автор пул-реквеста не может переписать правила ревью своим же патчем. На других планах тот же этап строится на `/code-review` в своей сессии или на своём CI с `anthropics/claude-code-action@v1`. Страница этого действия говорит о режиме automation: "For a plain-text prompt, Claude has no shell or GitHub API access until you grant the tools the prompt needs" (через `--allowedTools` или `permissions.allow`), а "If you invoke a skill instead, Claude can use the tools its `allowed-tools` frontmatter grants". Пример ревью на той же странице как раз запускает skill (`/code-review:code-review --comment ...`), поэтому что может такое ревью, решает `allowed-tools` этого skill и `--allowedTools` в `claude_args`, а не одно отсутствие настроек.

**Маленькие изменения через гейт.** Агент предлагает патчи в модулях, для которых есть проверенная сеть тестов (урок 4), и только через гейт. Сеть, которую никто не проверял мутантами или саботажем, ничего не гарантирует. Лучшие практики Claude Code советуют для больших автоматических прогонов: "Try it on three files first, see what goes wrong, fix the prompt, then run the rest."

**Шире, когда есть данные.** Блог Anthropic о больших кодовых базах советует начинать с "a defined set of approved skills", обязательного ревью кода и "limited initial access, and expand as confidence builds", а настройкой Claude Code должен владеть один ответственный (DRI). Это один источник одного вендора, без метрик.

## Что мерить

Встроенная аналитика Claude Code (Team и Enterprise) считает активность: пул-реквесты и строки с участием Claude Code, долю принятых предложений. Документация называет её "deliberately conservative" и советует смотреть её "alongside DORA metrics". Активность не результат: больше строк от агента не значит лучше.

Сигнал результата это то, что команда мерила бы и без агента: доля изменений, которые пришлось откатить или чинить, время до слияния, число возвратов после ревью. У сигнала должна быть база: значение до внедрения.

DORA 2025 описывает роль ИИ так: "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses". Среди семи возможностей в модели DORA для ИИ есть работа маленькими порциями (small batches): она "amplifies the positive influence of AI on product performance". А в пункте про контроль версий сказано, что частое использование отката (rollback) улучшает результаты команд, которые работают с ИИ. Отсюда условие остановки: число, при котором этап откатывают, и человек, который это решает.

## Память агента в CI

Агент в CI запускается как `claude -p`, часто с `--bare`. По документации bare mode пропускает "auto-discovery of hooks, skills, custom commands, subagents, installed plugins, MCP servers, auto memory, and CLAUDE.md". Без `--bare` `claude -p` "discovers and loads them as an interactive session would". Значит, под `--bare` факт из корневого `CLAUDE.md` в контекст сам не попадёт. Claude по-прежнему может прочитать файл инструментом чтения, но рассчитывать на это нельзя. Текст памяти передают явно, например через `--append-system-prompt-file`. Что `--bare` делает с `.claude/rules/`, в этом списке не сказано, поэтому текст правил тоже передают явно.

Настройки проекта. В закоммиченном `.claude/settings.json` правила `deny` и `ask` действуют сразу ("`deny` and `ask` rules aren't affected, since they only restrict"), а `permissions.allow` применяются только после того, как человек принял доверие к папке. `claude -p` диалога доверия не показывает, и в папке, которой не доверяли, правила `allow` проекта "Not used", а в stderr печатается предупреждение. Запрет в закоммиченном файле работает в CI, разрешение может не работать.

## Частые ошибки

- Решать по ощущениям команды или по числу строк от агента.
- Гейт, который запускает только тесты после патча.
- Дать агенту запись сразу во весь репозиторий, без этапа ревью.
- Нет числа, при котором этап откатывают, и нет человека, который решает.
- Считать, что Code Review может заблокировать слияние.
- Считать, что CI-агент под `--bare` видит `CLAUDE.md`.

## Что делать в практике

Вы напишете правила гейта в `scripts/agent_gate.py`: функции копирования, применения патча и запуска тестов уже есть. Потом план внедрения в `docs/rollout-plan.md`, который оценит ментор по рубрике. Под конец квиз.
