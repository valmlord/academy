## Модель проверки

Модель проверки. Проверка не запускает Claude Code. Она вычисляет, что загружается, по своей модели, и эта модель состоит из правил ниже: четыре принятых места, запуск из корня репозитория, правило триггеров, таблица шаблонов, импорты (3 перехода для загрузки, 5 для запрета), комментарии, frontmatter, размер и правило термина. По модели проверки факт загружен при работе с файлом, если он есть в том, что загружается при запуске, или в том, что загружается при чтении, записи или правке этого файла. Каждое сообщение со словами "по модели проверки" значит: так получилось по этим правилам. Это не утверждение о том, что Claude Code держит в контексте.

## Уровень факта: строка охвата

Каждая заметка в `docs/team-notes.md` кончается отдельной строкой охвата, и уровень факта решает только она.

- `Applies only to: <файлы>.` (касается только этих файлов): это факт области. По модели проверки он должен загружаться при чтении, записи или правке каждого из названных файлов (правило триггеров ниже) и не загружаться при чтении, записи или правке других файлов. Проверка смотрит, что загружается в момент такого действия, а не что остаётся в контексте после него, как в новой сессии, которая работает только с этим файлом.
- `Applies to: any file, a new module included.` (касается любого файла, в том числе нового модуля): это факт сессии. По модели проверки он должен загружаться при запуске основной сессии. Подходит любое место, которое загружается при запуске: корневой `CLAUDE.md`, правило без `paths` или файл, импортированный из корневого `CLAUDE.md`.

Если факт заметки можно приложить и к другому файлу, уровень от этого не меняется.

Как ведёт себя субагент Explore: он начинает работу без ваших файлов CLAUDE.md, поэтому факт сессии в корневом `CLAUDE.md` до него не доходит. Факт области в правиле с `paths` или в `CLAUDE.md` подкаталога доходит до Explore, когда он работает с файлами, к которым относится это правило или подкаталог (документация субагентов, разделы "Built-in subagents" и "What loads at startup").

## Как проверка находит факт

Проверка ищет факт заметки по его термину. Термины такие, как они написаны в `docs/team-notes.md`: `printerd` (F1), `pickup-board` (F2), `carrier-export` (F3), `ledger-sync` (F4), `tariff-desk` (F5). Термин ищется как часть текста, без учёта регистра букв, с дефисом, как в заметке: `#tariff-desk` и `Printerd` засчитываются, `pickup board` без дефиса нет.

Засчитывается любой текст принятого места, который загружает модель проверки: абзац, заголовок, строка оглавления, код в обратных кавычках и блок кода, путь в импорте `@`, имя файла, написанное в тексте. Не засчитываются: frontmatter правила, текст, который убирает правило комментариев, и имена файлов на диске (правило `.claude/rules/printerd-labels.md`, в тексте которого термина нет, термин не несёт).

Поэтому любое упоминание термина факта области в месте, которое загружается при запуске или при работе с файлом, которого заметка не называет, проверка считает загрузкой факта там. Честные примеры, которые поэтому не проходят:

- строка оглавления в корневом `CLAUDE.md`, которая называет файл правила с термином в имени, например "Факты команды: `.claude/rules/printerd-labels.md`";
- `@docs/team-notes.md` в корневом `CLAUDE.md`: в файле заметок все пять терминов, и, по модели проверки, факты F1-F3 загружаются при запуске;
- упоминание термина F1-F3 в `CLAUDE.md` подкаталога или в правиле с широким шаблоном.

Как этого избежать: в местах, которые загружаются при запуске, не пишите термины F1-F3. Оглавление можно написать без них ("правила областей лежат в `.claude/rules/`") или назвать файлы правил без термина. Файл заметок не импортируйте, а переносите каждый факт в его место. Факт сессии, наоборот, должен нести свой термин в месте, которое загружается при запуске.

Пишите в памяти сам факт, а не только термин: проверка находит факт по термину, а ментор читает файлы.

## Правила курса

Правило курса это решение этого задания, а не утверждение о Claude Code. У каждого указана причина.

1. Принятые места. Проверка читает только их:
   - корневой `CLAUDE.md`;
   - `CLAUDE.md` в подкаталоге репозитория;
   - `.claude/rules/**/*.md` в корне репозитория, с `paths` и без;
   - файлы `.md` внутри репозитория, до которых доходит импорт `@` из файла `CLAUDE.md` (корневого или подкаталога) или из файла, до которого импорт дошёл так же. Корневой `AGENTS.md`, импортированный строкой `@AGENTS.md`, как в уроке 5 модуля 00, тоже такой файл и засчитывается.

   Правило курса: проверка в этом задании вычисляет загрузку только для этих четырёх мест, так устроена её модель. Всё остальное она не читает: другие файлы памяти (`AGENTS.md` без импорта, `CLAUDE.local.md`, `.claude/CLAUDE.md`, правила во вложенных `.claude/rules/`) и определения агентов, файлы настроек, домашний каталог и то, что Claude Code пишет сам, в том числе автопамять. Факт, который лежит только там, проверка не засчитывает как размещённый. Это не утверждение, что Claude Code его там не загрузит.

   Корневой `CLAUDE.md` удалять нельзя, даже ради того, чтобы загружался один `AGENTS.md`, как допускал урок 5 модуля 00: в этом задании в корневом `CLAUDE.md` нужны команда тестов и отметка о версии, и без него проверка ответит "нет корневого CLAUDE.md".
2. Запуск. Оценивается обычный запуск `claude` из корня репозитория `/workspace/home/work` со встроенным Explore. Флаги, переменные окружения и настройки, которые меняют загрузку памяти, проверка не читает и не учитывает. Причина: страница памяти ("How CLAUDE.md files load") считает загрузку от рабочего каталога, и только при запуске из корня корневой `CLAUDE.md` загружается как корневой.
3. Триггеры. По модели проверки загрузка с файлом считается только при чтении, записи и правке этого файла (документация памяти, разделы "How CLAUDE.md files load" и "Path-specific rules"); про Grep и Glob документация молчит. `CLAUDE.md` подкаталога по модели загружается с файлами своего каталога, правило с `paths` с файлами, которые совпадают с его шаблонами.
4. Шаблоны `paths`. Базовый каталог правил в `.claude/rules/` в корне это корень репозитория. Проверка сопоставляет шаблоны по таблице из "Path-specific rules", а не как `fnmatch` в Python:

   | Шаблон | С чем совпадает |
   |---|---|
   | `**/*.ts` | файлы `.ts` на любой глубине под базовым каталогом |
   | `src/**/*` | все файлы под `src/` базового каталога |
   | `*.md` | файлы `.md` на любой глубине под базовым каталогом |
   | `/*.md` | файлы `.md` прямо в базовом каталоге, не в подкаталогах |
   | `src/components/*.tsx` | файлы `.tsx` прямо в `src/components/` базового каталога, не в подкаталогах |

   Отсюда правила сопоставления: шаблон без `/` совпадает с именем файла на любой глубине; `/` в начале привязывает шаблон к базовому каталогу; шаблон с `/` внутри сравнивается от базового каталога по частям пути; `*` совпадает внутри одной части пути, а `**` как целая часть пути совпадает с любым числом частей, в том числе с нулём.

   Правило курса: проверка не принимает шаблоны с `{` и `[` и строку через запятую с пробелами рядом с запятой; пишите такие шаблоны списком. Причина: документация описывает раскрытие скобок и выражения в квадратных скобках, а модель проверки их не считает; обрезаются ли пробелы у шаблонов в строке через запятую, документация не говорит.
5. Импорты. Импорт засчитывается только из `CLAUDE.md` и из файлов, которые он импортирует; цель импорта должна быть файлом `.md` внутри репозитория. Для загрузки проверка считает не глубже 3 переходов, для запрета 5: документация говорит о четырёх переходах, не уточняя, считается ли сам файл; в уроке 5 модуля 00 проверка считала 5. Поэтому факт, который должен загрузиться, держите не дальше 3 переходов от `CLAUDE.md`, а термин факта области, который не должен загрузиться, не должен встречаться и на 4-м и 5-м переходе.
6. Комментарии. Для загрузки проверка не засчитывает текст внутри блочного HTML-комментария ни в каком файле и не идёт по импортам `@` внутри него. Для запрета она считает такой текст в файлах, кроме `CLAUDE.md`, обычным текстом, а по импортам `@` внутри комментария идёт в любом файле. Документация говорит, что такие комментарии вырезаются из файлов CLAUDE.md (комментарии внутри блоков кода сохраняются), и молчит про остальные файлы и про импорты внутри комментариев. Блочный комментарий здесь это `<!--` в начале строки (перед ним не больше 3 пробелов) и всё до первого `-->`. Комментарий внутри абзаца текста документация не называет, поэтому обе модели считают его текст обычным текстом, но для загрузки по импортам `@` внутри него проверка не идёт. Незакрытый `<!--` в начале строки для загрузки считается комментарием до конца файла, а для запрета обычным текстом. Блок кода распознаётся при любом отступе, в том числе внутри пункта списка.
7. Frontmatter. Frontmatter правила Claude Code убирает перед загрузкой, поэтому текст в нём не засчитывается; проверка разбирает frontmatter только в формах, перечисленных в разделе "Как проверяется" (этап 0, проверка правил).
8. Символические ссылки. Проверка читает только обычные файлы: ни принятое место, ни каталог на пути к нему (`.claude`, `.claude/rules` и ниже, подкаталог с `CLAUDE.md`, цель импорта) не должны быть символической ссылкой, а файл в принятом месте должен быть обычным файлом, не именованным каналом или устройством.
9. Размер. Файл в принятых местах длиннее 40 000 символов проверка не принимает (правило курса). Документация говорит, что при окне контекста 200K Claude получает от файла, который загружается по требованию, только первые 40 000 символов и указание дочитать остальное инструментом Read; при окне 1M предел больше. Модель проверки обрезку не считает, поэтому принимает только файлы не длиннее самого малого предела. Правило касается всех файлов в принятых местах, в том числе тех, что загружаются при запуске: проверка не знает, какое окно у вашей модели.
10. Термин. Факт ищется по термину, как написано в разделе "Как проверка находит факт". Причина: ментор читает формулировку, а проверке нужен признак, который нельзя понять двумя способами.

## Проверка версии

Привычка урока: прежде чем полагаться на загрузку памяти, проверить её по документации своей версии и записать, что проверено. Четыре шага.

1. В терминале рабочей папки выполните `claude --version`. Команда печатает номер версии и после него ` (Claude Code)`, в виде `<версия> (Claude Code)` (страница установки, "Advanced setup").
2. Откройте в браузере четыре страницы из таблицы ниже и найдите каждое утверждение под заголовком его раздела. Страницы описывают только новейший выпуск, а упоминания версий в них это обычный текст внутри абзацев.
   - На каждой странице выполните поиск по странице дважды, по одному поиску за раз. Браузер подсвечивает совпадения только текущего поиска, и новый поиск заменяет подсветку.
   - Перед первым поиском убедитесь, что браузер подсвечивает все совпадения, а не только текущее. Если нет (в Firefox может быть выключено "Highlight All"), включите в браузере подсветку всех совпадений.
   - Первый поиск: `v2.` (если ваша версия начинается с другого числа, ищите `v`, это число и точку). Просмотрите на этой странице каждый раздел из таблицы и найдите в нём подсвеченный текст.
   - Второй поиск: первые два числа вашей версии из шага 1 с точками, например `2.1.` для 2.1.311. Просмотрите те же разделы ещё раз.
   - Поиски пересекаются: каждое упоминание `v2.1.` находят оба. Поиск `2.1.` находит ещё упоминание без "v" (например "Claude Code 2.1.300"). Поиск `v2.` находит ещё упоминание с другим вторым числом (например "v2.2.0 or later").
   - В любом проходе подсвеченный текст внутри раздела считается находкой. "Внутри раздела" значит между заголовком раздела и следующим заголовком того же или более высокого уровня. Подсвеченный текст вне разделов таблицы не открывайте: он не часть этого шага.
   - Для каждой находки прочитайте, описывает предложение поведение до vX или начиная с vX, и сравните X со своей версией. Предложение о поведении начиная с vX (например "requires vX or later", "vX and later", "on vX or later"), и X больше вашей версии: в вашей версии этого поведения нет. Предложение о поведении до vX (например "Before vX", "vX or earlier"), и X больше вашей версии: ваша версия ведёт себя так, как говорит это предложение.

   Утверждения документации, на которые опирается проверка, для Claude Code 2.1.311, проверены 2026-11-16, разделы найдены 2026-11-17:

   | Утверждение | Страница и раздел | Заголовок раздела |
   |---|---|---|
   | загрузка `CLAUDE.md` из рабочего каталога и выше; `CLAUDE.md` подкаталога при чтении, записи или правке файла там; блочные HTML-комментарии | https://code.claude.com/docs/en/memory#how-claude-md-files-load | "How CLAUDE.md files load" |
   | команды Bash, которые считаются просмотром одного файла | https://code.claude.com/docs/en/tools-reference#edit-tool-behavior | "Edit tool behavior" |
   | правила без `paths` загружаются при запуске | https://code.claude.com/docs/en/memory#set-up-rules | "Set up rules" |
   | неразобранный YAML, `paths` единственное поле, frontmatter убирается; "Accepts a YAML list or a comma-separated string" | https://code.claude.com/docs/en/memory#rules-frontmatter-reference | "Rule frontmatter reference" |
   | когда загружается правило с `paths`, базовый каталог, таблица шаблонов | https://code.claude.com/docs/en/memory#path-specific-rules | "Path-specific rules" |
   | импорты `@`: синтаксис, относительные пути, четыре перехода, код не разбирается | https://code.claude.com/docs/en/memory#import-additional-files | "Import additional files" |
   | Explore "start without your CLAUDE.md files" | https://code.claude.com/docs/en/sub-agents#built-in-subagents | "Built-in subagents" |
   | у Explore `CLAUDE.md` подкаталога и правила с `paths` "still load when the subagent works with files there" | https://code.claude.com/docs/en/sub-agents#what-loads-at-startup | "What loads at startup" |
   | самая полезная строка в `CLAUDE.md` это команда проверки | https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run | "Give Claude a check to run" |

3. Откройте список изменений, https://code.claude.com/docs/en/changelog. Записи озаглавлены номером версии, новые сверху, после номера идёт дата. Страница длинная, поэтому найдите поиском по странице номер своей версии (например номер из шага 1): это заголовок её записи. Каждая запись выше него новее вашей версии. Прочитайте эти записи с поиском по словам CLAUDE.md, rules, `paths`, import, memory и Explore.
4. Запишите в корневой `CLAUDE.md` одной строкой: `<!-- memory layout checked: Claude Code <version>, docs and changelog read <YYYY-MM-DD> -->`. `<version>` это номер из шага 1 без ` (Claude Code)`, дата это день, когда вы читали.

Если страница или список изменений расходятся с процитированными утверждениями, проверка всё равно моделирует 2.1.311 так, как их передают цитаты. Размещайте по цитатам и расскажите ментору, что отличается. Три случая ожидаемы и расхождением не считаются:

- новейший выпуск на сегодня: 2.1.326 (16 ноября 2026), проверено 2026-11-17;
- упоминания версий внутри разделов таблицы, у которых X не больше 2.1.311, например "Before v2.1.211, ..." в "Set up rules" (память) и "Requires Claude Code v2.1.198 or later." в "Built-in subagents" (субагенты). Такое упоминание значит, что в вашей версии поведение такое, как его описывают цитаты;
- совпадение поиска `2.1.` внутри разделов таблицы, которое не упоминание версии, например нумерованный подпункт "2.1." или часть более длинного числа. Оно не называет версию, сравнивать нечего, и говорить о нём ментору не нужно.

## Как проверяется

`memory-layout` (команда в рабочей папке, не дольше 90 секунд). Проверка не запускает Claude Code и не ходит в сеть. Она читает только принятые места и ничего в домашнем каталоге. Сначала идёт этап 0: проверка формы. Его отказ не считается попыткой. Только если этап 0 пройден, проверка сравнивает размещение фактов, и такой результат уже считается попыткой.

Первая отправка стартовой папки как есть упирается в этап 0 (нет рабочей команды тестов) и попыткой не считается. Отправка с исправленной командой, но без отметки о версии, тоже останавливается на этапе 0.

Этап 0 идёт в таком порядке и печатает только первую найденную проблему; следующая появится после того, как вы исправите эту.

1. Файлы. Корневой `CLAUDE.md` есть и это обычный файл. Каждый файл в принятых местах читается как UTF-8. Ни принятое место, ни каталог на пути к нему не символическая ссылка и не особый файл вроде именованного канала (правило курса 8). Ни один файл в принятых местах не длиннее 40 000 символов (правило курса 9).
2. Правила в `.claude/rules/`. Каждый файл проверяется по порядку:
   1. ни один элемент `paths` и ни одно значение-строка не содержит `{` или `[`. Это проверяется до проверки формы: у блочного списка по каждому элементу, у списка в квадратных скобках по каждому элементу после разбиения (сами скобки списка шаблоном не считаются), у строки целиком. Поэтому скобка внутри элемента списка даёт сообщение про скобки;
   2. frontmatter нет совсем или он в форме, которую разбирает проверка: первая строка в точности `---`, потом закрывающая строка в точности `---`; между ними только строки `ключ: значение`, каждый ключ один раз; значение это строка, список в одной строке `[a, b]` или пустое значение, за которым идут строки `- элемент` с одинаковым отступом (в том числе без отступа); элементы можно брать в кавычки. Всё остальное не принимается. Это касается значения любого ключа, не только `paths`:
      - значение без кавычек не начинается с `-`, `?`, `:`, `,`, `[`, `]`, `{`, `}`, `#`, `&`, `*`, `!`, `|`, `>`, `'`, `"`, `%`, `@` или обратной кавычки, не содержит `: ` и ` #` и не кончается на `:`; в списке `[a, b]` элемент без кавычек не содержит ещё и запятых и скобок. Такие значения YAML читает не как обычную строку. Поэтому шаблон, который начинается с `*`, берите в кавычки: `"**/*.py"`;
      - значение в кавычках не содержит своей кавычки внутри, а в двойных кавычках ещё и обратной косой черты;
      - `paths` не пустое, не `[]`, без пустых элементов и не значение, которое YAML читает не как строку (`true`, `null`, число);
   3. `paths` это список YAML или одна строка через запятую без пробелов рядом с запятой;
   4. в файле нет импорта `@` вне кода в обратных кавычках и блоков кода.

   Другие поля frontmatter проверка игнорирует, как их игнорирует Claude Code. Причины отказа разные. YAML, который не разбирается: Claude Code проигнорировал бы frontmatter и загрузил бы правило при запуске ("Rule frontmatter reference"), и проверка оценивала бы не тот файл, который загружает Claude Code. YAML, который разбирается, но не в этих формах (блочная строка, якорь, вложенный словарь): это только правило курса, проверка разбирает только эти формы. Импорт `@` в правиле: правило курса, документация описывает импорт в файлах CLAUDE.md, проверка считает импорт только оттуда.
3. Импорты. Каждый знак `@` в корневом `CLAUDE.md`, в `CLAUDE.md` подкаталога и в импортированном файле должен вести, относительно своего файла, к существующему обычному файлу `.md` внутри репозитория. Знак `@` считается импортом, если он стоит вне кода в обратных кавычках и блоков кода (внутри HTML-комментария тоже считается) и перед ним нет буквы, цифры или одиночной обратной кавычки. Знак `@` сразу после кода в обратных кавычках тоже импорт. Поэтому `@package.json`, `@facts.txt`, `@shipping/`, `@~/x.md`, абсолютный путь, путь за пределы репозитория и несуществующий файл не принимаются, а адрес вроде `ops@example.com` не импорт. Путь импорта кончается на первом пробеле, поэтому после пути не ставьте точку, запятую или скобку: `@docs/x.md.`, `@docs/x.md)` и `@docs/x.md#part` не принимаются, путь с пробелом тоже. Причина: модель проверки считает только импорты файлов `.md` внутри репозитория. Чтобы упомянуть путь без импорта, возьмите его в обратные кавычки.
4. Команда тестов. Среди строк в обратных кавычках и в блоках кода того, что по модели проверки загружается при запуске, хотя бы одна начинается с `python3 -m unittest`, за которым пробел или конец строки. Строка с символом оболочки не запускается. Символы оболочки здесь такие:

   ```text
   ; & | < > $ ` \ ( ) { } * ? ~ ! # ' " [ ]
   ```

   - Такие строки запускаются по порядку, не больше 3, каждая не дольше 20 секунд. Проверка берёт первые 3 подходящие строки до того, как отбросить строки с символами оболочки, поэтому отброшенная строка тоже занимает одно из 3 мест.
   - Каждая запускается в свежей копии каталогов `tests/`, `shipping/`, `config/` и `data/`, как написана, из корня этой копии, без оболочки и в чистом окружении (только `PATH`, `HOME`, `TMPDIR` и `LANG`). Флага изоляции `-I`, с которым работает сама проверка, у этого запуска нет: под `-I` команда `discover -s tests` не находит пакет `shipping`. Вместо него Python запускается с `-s`, чтобы не подхватить пользовательские пакеты. Другие флаги `unittest` в строке допустимы и работают как обычно.
   - Строка принята, если она завершилась с кодом 0 и во время запуска хотя бы один тест засчитан как прошедший, а его тестовый класс определён в файле внутри `tests/` копии. Проверка считает прошедшие тесты внутри самого запуска `unittest`, а не по тексту вывода. Не засчитываются тестовые классы, определённые вне `tests/` (например модули `test.*` стандартной библиотеки), и тесты, которые были только пропущены; что тест импортирует, например `shipping`, роли не играет. Код 5 с `NO TESTS RAN` не принимается.
   - Проверка доказывает только то, что команда запускает ваши тесты, а не то, что тесты хорошие. Поэтому хватит любого честного теста, который проходит, например того, что уже есть в `tests/test_smoke.py`.
   - Если ни одна строка не принята, проверка печатает отдельное сообщение для каждой строки с символами оболочки и одно сообщение "ни одна строка" для последней запущенной строки. В конце этого сообщения стоит последняя строка stderr, а если stderr пустой, `stderr пуст`. Если строка завершилась с кодом 0, но ни один тест из `tests/` не прошёл, там стоит `код 0, не прошёл ни один тест из файлов в tests/`, а если она не уложилась в 20 секунд, `код нет, не завершилась за 20 с`.
   - Причина: best practices называет команду проверки самой полезной строкой в `CLAUDE.md`, а в репозитории есть тесты. Правило курса: строка начинается с `python3 -m unittest`, потому что pytest в рабочей среде нет.
5. Отметка о версии. В корневом `CLAUDE.md` есть строка, которая целиком состоит из HTML-комментария `<!-- ... -->` (перед ним не больше 3 пробелов, вне блока кода), и в комментарии есть версия вида `число.число.число` и дата вида `ГГГГ-ММ-ДД`: это отметка из шага 4 проверки версии. Первый комментарий стартового файла версии не содержит. Причина: привычка урока.

Сообщения этапа 0 называют только файл, строку и правило:

```text
нет корневого CLAUDE.md
<path>: не UTF-8
<path>: символическая ссылка; проверка читает только обычные файлы (правило курса)
<path>: не обычный файл; проверка читает только обычные файлы (правило курса)
<path>: больше 40 000 символов; модель проверки не считает обрезку длинных файлов (правило курса)
<rule>: шаблон с { или [ (правило курса)
<rule>: frontmatter не в той форме, которую разбирает проверка (правило курса, формы в task.md)
<rule>: пробел рядом с запятой в paths (правило курса: пишите списком)
<rule>:<line>: импорт @ в правиле (правило курса)
<file>:<line>: импорт @<target>: цель не файл .md внутри репозитория (правило курса; в обратных кавычках это не импорт)
по модели проверки в памяти при запуске нет строки `python3 -m unittest ...` в обратных кавычках или в блоке кода
<line>: символы оболочки, строка не запускалась
ни одна строка `python3 -m unittest ...`, которая по модели проверки загружается при запуске, не запускает тесты: <line> -> код <c>, <last stderr line>
ни одна строка `python3 -m unittest ...`, которая по модели проверки загружается при запуске, не запускает тесты: <line> -> код <c>, stderr пуст
ни одна строка `python3 -m unittest ...`, которая по модели проверки загружается при запуске, не запускает тесты: <line> -> код нет, не завершилась за 20 с
ни одна строка `python3 -m unittest ...`, которая по модели проверки загружается при запуске, не запускает тесты: <line> -> код 0, не прошёл ни один тест из файлов в tests/
в корневом CLAUDE.md нет однострочного комментария HTML с версией и датой (шаг 4)
```

Сравнение размещения (считается попыткой). Для F4 и F5 термин должен быть в том, что по модели проверки загружается при запуске. Для F1, F2 и F3 термин должен быть в том, что загружается с каждым файлом из строки охвата, и не должен быть в том, что загружается с файлами, которых заметка не касается. На каждый факт, который не прошёл, печатается строка, по порядку от F1 до F5; у факта области их может быть две, по одной на каждую сторону:

```text
F4: по модели проверки не загружается при запуске сессии
F1: по модели проверки не загружается хотя бы с одним файлом, который называет заметка
F1: по модели проверки загружается и при работе с файлами, которые заметка не называет: термин `printerd` найден в <file>:<line> (импортирован из <file>:<line>), <file>:<line> и ещё <k>
```

Вместо F4 и F1 стоит номер того факта, который не прошёл, и его термин. Последнее сообщение называет ваш собственный файл и первую строку в нём, где есть термин; часть в скобках есть, только если этот файл импортирован, и называет первую строку импорта из ближайшего файла, который его импортирует. Файлов называется не больше 3, остальные сокращаются до `и ещё <k>`. С каким из файлов, которых заметка не называет, совпало ваше место, сообщение не говорит.

Если все факты на месте, проверка печатает:

```text
пройдено: по модели проверки каждый факт загружается там, где нужен, команда тестов запускает тесты, отметка о версии на месте
```

Если сама проверка сломалась, она печатает `ошибка проверки: <тип>: <текст>`, и такой результат считается попыткой. Расскажите о нём ментору.

## Как работать (совет, не проверяется)

- Начните с команды тестов: пока она не работает, проверка не доходит до фактов. Запустите свою строку в терминале и посмотрите на строку `Ran ...` и на `OK` после неё.
- Для каждой заметки прочитайте только строку охвата и решите уровень. Потом выберите место: для факта области правило с `paths`, где перечислены ровно файлы из строки охвата, или `CLAUDE.md` подкаталога, если он загружается только с нужными файлами; для факта сессии любое место, которое загружается при запуске.
- Перед отправкой найдите термины поиском без учёта регистра по `CLAUDE.md` и `.claude/`: каждый термин F1-F3 должен встречаться только в своём месте.

## Попытки и подсказки

- `memory-layout`: не больше 10 оценённых попыток; после 5 неудачных интерфейс предложит ментора. Отказ этапа 0 попыткой не считается.
- Ментор спросит, какой диапазон записей changelog вы прочитали и что в документации отличалось от цитат. Он читает ваши файлы и смотрит, записан ли в каждом месте сам факт, а не только термин.
- Ментор между попытками задаёт вопросы и подсказывает направление. Он обсуждает только то, что уже назвало сообщение проверки, и не называет файлы, которых заметка не касается.
