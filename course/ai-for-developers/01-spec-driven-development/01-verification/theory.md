# Проверка результата работы агента

## Проблема

Агент написал функцию и тесты к ней и отчитался: "все тесты проходят". Тесты и правда зелёные, а
функция считает неверно. Что именно вы проверили, поверив ему?

Только его слова. Зелёный прогон ничего не значит, если тест сравнивает код с самим собой, пропущен
или проверяет лишь тип результата.

## Идея: "выглядит готовым" и "готово"

Рекомендации Claude Code: "Claude stops when the work looks done. If it has nothing to run that
tells it whether the work actually *is* done, 'looks done' is all it has to go on. In practice that
makes you the test suite."

Отсюда два правила: дайте агенту проверку, которую можно запустить, и требуйте доказательство, то
есть команду и её вывод. "'All tests pass' on its own tells you very little."

## Лестница строгости

Те же рекомендации (Claude Code 2.1.312) называют четыре способа, по тому, кто решает, что работа
готова; пятую ступень добавляет курс (в таблице рекомендаций CI стоит среди детерминированных
проверок):

1. **Промпт** "прогони тесты и продолжай, пока не пройдут": решает Claude.
2. **`/goal <условие>`**: после каждого хода отдельная модель сверяет условие с разговором. Она
   "doesn't run commands or read files independently", поэтому может принять строку "tests pass",
   которую агент просто напечатал.
3. **Stop-хук**: проверку запускает харнесс, ход не заканчивается, пока она красная (или пока не
   исчерпан лимит блокировок).
4. **Свежий ревьюер**: `/code-review` смотрит дифф в субагенте, который не видел разговора (модуль
   03).
5. **CI и защита ветки**: последнее слово за обязательной проверкой (в GitHub это required status
   checks) и человеком, который одобряет слияние.

Детерминированы тесты, Stop-хук с командой и CI. Хук типа `prompt` или `agent` "asks *another
model* to decide".

## Stop-хук в Claude Code 2.1.312

Событие `Stop` срабатывает, когда основной агент закончил ответ (не при прерывании пользователем).
На stdin приходит JSON, в нём среди прочего `stop_hook_active` и `last_assistant_message`.

Как хук не даёт закончить ход:

- **JSON на stdout**: ровно один объект `{"decision": "block", "reason": "..."}`; `reason`
  обязателен, его получает Claude. При валидном JSON код выхода не важен: при exit 2 причина
  берётся из `reason`, при exit 1 и других Claude Code "ignores the exit code, and the fields alone
  decide". Это уточнение к уроку 6 модуля 00: там "exit 1 не блокирует" говорилось про
  PreToolUse-хук без JSON, а у этого Stop-хука валидный JSON с `decision: "block"` блокирует при
  любом коде.
- **Exit 2 без JSON-блока**: блок, причина из stderr (исключение про пропавший файл ниже).
- **Exit 0, stdout пустой, обычный текст или `{}`**: ход заканчивается.
- **Exit 0 с `hookSpecificOutput.additionalContext`**: это не блок, но "The conversation continues
  so Claude can act on it"; в этой практике такой вывод не используется.
- **Exit 1 или другой без валидного JSON**: неблокирующая ошибка, ход заканчивается.
- **`continue: false`** в любом объекте останавливает Claude целиком (Справка).

**`stop_hook_active`** равен `true`, когда Claude уже продолжает работу из-за Stop-хука. Его
проверяют, чтобы не блокировать снова и снова на условии, которое не разрешится.

**Падение не блокирует.** `onFailure` на Stop "has no effect": Claude не может починить хук, который
не запустился. Упавший, зависший или не стартовавший Stop-хук пропускает конец хода; fail closed,
как у PreToolUse в модуле 00, здесь не включить.

### Две тихие ловушки

Документация: на Stop, "when your hook exits 2 with nothing on stdout and its stderr says a file is
missing, such as `No such file or directory`, Claude Code treats the run as a non-blocking error".
Это бьёт в двух местах (проверено на Python 3.11 и 3.12):

1. Опечатка в пути скрипта в форме `python3 <путь>`: Python печатает `can't open file '...': [Errno
   2] No such file or directory` и выходит с кодом 2. Хук молча ничего не делает.
2. Хук пересылает сырой вывод unittest в stderr с exit 2. Если красный тест упал с
   `FileNotFoundError: [Errno 2] No such file or directory`, именно этот красный прогон не блокирует.

Лечение: блокировать через JSON на stdout. Фраза внутри `reason` исключение не включает: stdout не
пуст.

### Где запускать тесты и что считать зелёным

`${CLAUDE_PROJECT_DIR}` это корень проекта, где началась сессия, он "stays put". Поле `cwd` во
входном JSON "follows Claude": после входа в worktree или `cd` оно указывает туда. В практике тесты
запускаются в `$CLAUDE_PROJECT_DIR`, это сознательный выбор.

Ноль тестов не зелёный цвет. Обе версии печатают `Ran 0 tests`, но Python 3.11 добавляет `OK` и
выходит с кодом 0, а 3.12 пишет `NO TESTS RAN` и выходит с кодом 5. Хук читает строку
`Ran 0 tests`, а не код выхода.

## Тест, который может упасть

Скилл `tdd` Matt Pocock (v1.3.2) называет главный антипаттерн: "the assertion recomputes the
expected value the way the code does". Ожидаемое значение берут из независимого источника, например
из требования, посчитав руками:

```python
import unittest


def discount(price_cents: int, percent: int) -> int:
    return price_cents * percent // 100


class DiscountTest(unittest.TestCase):
    def test_tautology(self) -> None:
        # Repeats the code's formula: passes on a wrong formula too.
        self.assertEqual(discount(1000, 15), 1000 * 15 // 100)

    def test_independent_value(self) -> None:
        # 15% of 10.00 is 1.50, computed from the requirement, not from the code.
        self.assertEqual(discount(1000, 15), 150)
```

Сами тесты проверяет **мутант**: копия кода с одной намеренной ошибкой. Если на мутанте ни один тест
не падает, это место не проверено. Böckeler называет мутационное тестирование сигналом качества
регрессионных тестов. И тест, написанный до кода, сначала должен покраснеть: зелёный с первого
запуска ничего не доказал.

## Что агенты подделывают

Задокументированные приёмы (бенчмарк EvilGenie, рекомендации Anthropic по промптингу, эксперимент
Böckeler): ответы, захардкоженные под входы тестов; правка или удаление тестов; тавтологические
проверки; пропущенный красный шаг; "готово" без запуска. Контрмеры, от слабой к сильной:

- строка в промпте ("It is unacceptable to remove or edit tests"): просьба, решает модель;
- защита тестов от правок: deny-правило или PreToolUse-хук из урока 6 модуля 00;
- повторный запуск проверки харнессом: Stop-хук, CI;
- скрытые тесты, которых агент не видел, и проверка тестов мутантами.

## TDD с агентом: спорная практика

Рекомендации Claude Code ("write a failing test that reproduces it, then fix it") и скилл `tdd`
("Red before green") предлагают сначала красный тест. Böckeler в небольшом эксперименте не увидела
заметной разницы в качестве; TDD-прогоны потратили в 8.50, 2.96 и 4.89 раза больше токенов, многие
из них были чтениями из кэша, так что разница в деньгах, вероятно, меньше этого отношения.
Тавтологические тесты появлялись и при тестах вперёд. Верно для обеих сторон: тест, который может
упасть, и ожидаемые значения из независимого источника.

## Частые ошибки

- Принимать "все тесты проходят" без команды и вывода.
- Считать `/goal` проверкой: он читает разговор и ничего не запускает.
- Пересылать сырой вывод unittest в stderr с exit 2 и пустым stdout.
- Запускать тесты из хука через `python3 -I`: флаг игнорирует `PYTHONPATH`, пакет из `src/` не
  импортируется.
- Решать по коду выхода unittest, а не по выводу.
- Блокировать, не проверив `stop_hook_active`.

## Что делать в практике

Вы напишете тесты по требованиям к функции пени, увидите их красными на коде агента, исправите код и
напишете Stop-хук, который сам запускает тесты. Процедуру проверки как скилл `verify` разберём в
уроке 2.

## Справка (читать по необходимости)

Исходы Stop-хука в Claude Code 2.1.312. "Объект" здесь это ровно один JSON-объект на stdout, который
проходит проверку схемы; без `continue: false` (о нём ниже):

| Код | stdout | Исход | Причина |
|---|---|---|---|
| 0 | пусто или обычный текст | ход заканчивается | нет |
| 0 | объект без `decision` и без `hookSpecificOutput.additionalContext` | ход заканчивается | нет |
| 0 | объект с `hookSpecificOutput.additionalContext` без `decision` | не блок, но разговор продолжается | `additionalContext` |
| 0, 2, другой | объект с `decision: "block"` | блок | `reason` |
| 2 | объект без `decision` | блок, поля его не отменяют | stderr |
| 2 | обычный текст или JSON, который не разбирается | блок | stderr |
| 2 | пусто, stderr не о пропавшем файле | блок | stderr |
| 2 | пусто, stderr о пропавшем файле | неблокирующая ошибка | нет |
| 0 или другой | JSON, который не разбирается или не проходит схему | неблокирующая ошибка | нет |
| 1 или другой | пусто или обычный текст | неблокирующая ошибка | нет |

Обычный текст это всё, что не один JSON-объект: в том числе JSON-массив и строка в кавычках.

- `continue: false` "Takes precedence over any event-specific decision fields": с ним Claude "stops
  processing entirely after the hook runs"; вместе с блоком его не пишут.
- `matcher` у `Stop` не поддерживается: "it is silently ignored".
- `SubagentStop`: matcher по типу агента, блок оставляет субагента работать. `TaskCompleted`: exit 2
  не даёт отметить задачу выполненной.
- `PostToolUse` не блокирует: инструмент уже выполнился.
- Просьба "проверь себя" зависит от модели: промптинг-гайд Anthropic называет её надёжной, но для
  Claude Opus 5 лишние указания на проверку ведут к избыточной проверке (на 2026-10-29).
- Лимит: после восьми продолжений подряд от Stop-хуков Claude Code игнорирует следующий блок;
  счётчик сбрасывается, когда Claude вызывает инструмент; порог задаёт `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`.
- Codex CLI 0.165.0: при exit 0 Stop ждёт JSON ("Plain text output is invalid for this event"); блок
  создаёт новый промпт продолжения с текстом `reason`; хуки вне managed-настроек работают только
  после ревью и доверия по хешу.
