## Форма артефактов, которую читает линтер

Это соглашения упражнения из уроков 3 и 4, упрощение источников.

- Глоссарий. `GLOSSARY-MAP.md` в корне: раздел `## Contexts` со списком ссылок на файлы контекстов и
  раздел `## Relationships`. Файл контекста (`docs/billing/GLOSSARY.md`, `docs/ledger/GLOSSARY.md`):
  `# <Контекст>`, необязательные строки описания, `## Language`, записи `**Term**: <определение>` и
  необязательная следующая строка `_Avoid_: word, word`. Каждое слово в `_Avoid_` одно слово из
  `[A-Za-z]+`.
- Спецификация `docs/spec.md`. Строки требований:
  `- **REQ-NN** WHEN <условие> THE SYSTEM SHALL <поведение>`, id это `REQ-` и две цифры, уникальные.
- ADR `docs/adr/NNNN-slug.md` (считаются только файлы с номером), форма Nygard: первый заголовок
  `# ADR-NNNN: <название>`, где NNNN равен номеру файла; строка
  `Status: proposed | accepted | deprecated | superseded by ADR-NNNN`; разделы `## Context`,
  `## Decision`, `## Consequences`. Номера начинаются с 0001, идут подряд и не переиспользуются.
- Задачи `docs/tasks.md`: блоки `## T-NN: <название>` со строками
  `Requirements: REQ-NN[, REQ-NN...]`, `Blocked by: none | T-NN[, ...]`, `Check:` и одна команда в
  обратных кавычках, `Status: todo | done`.

## Правила C1-C6

| Правило | Что проверяет | Файл в строке (пример) | Токен |
|---|---|---|---|
| C1 | каждое требование спецификации перечислено хотя бы в одной задаче | `docs/spec.md` | id неперечисленного требования, `REQ-NN` |
| C2 | каждое требование, на которое ссылается задача (в любой строке её блока, заголовок тоже) или метка в имени теста, есть в спецификации | `docs/tasks.md` или файл теста, например `tests/test_reminders.py` | id отсутствующего требования в виде `REQ-NN`, даже если ссылка пришла из метки `req_NN` |
| C3 | у каждого требования, которое перечисляет задача со `Status: done`, есть хотя бы одна метка в имени теста | `docs/tasks.md` | id требования без теста, `REQ-NN` |
| C4, дыра в нумерации | номера ADR идут с 0001 без пропусков | `docs/adr` | пропущенный номер, `ADR-NNNN` |
| C4, нет строки `Status:` | в ADR есть строка `Status:` | путь ADR, например `docs/adr/0003-x.md` | имя файла, например `0003-x.md` |
| C4, недопустимый статус | значение `Status:` одно из `proposed`, `accepted`, `deprecated`, `superseded by ADR-NNNN` | путь ADR | имя файла |
| C4, номер в заголовке | номер в `# ADR-NNNN:` равен номеру в имени файла | путь ADR | имя файла |
| C4, замена самого себя | `superseded by` не указывает на этот же ADR | путь ADR | имя файла |
| C4, повтор номера | ни у какого другого файла ADR нет того же номера | путь каждого из файлов с этим номером | имя этого файла |
| C4, `superseded by` в пустоту | цель `superseded by ADR-NNNN` существует | путь ADR | отсутствующий `ADR-NNNN` |
| C5 | спецификация и задачи ссылаются (`ADR-NNNN`) только на ADR, которые не заменены и не устарели (`deprecated`); заменяющий ADR может упоминать тот, который заменяет | `docs/spec.md` или `docs/tasks.md` | id процитированного ADR |
| C6 | ни одно слово из `_Avoid_` не встречается как токен в проверяемых местах | `docs/spec.md`, `docs/tasks.md` или файл теста | слово так, как оно написано в тексте, в нижнем регистре (например `clients`), а не слово из глоссария |

Проверка читает в строке находки только номер правила и токен; файл вы выбираете сами, в таблице
пример того, что пишет эталонный линтер. Например: `C4 docs/adr/0003-x.md: 0003-x.md`.

Ещё три уточнения:

- Задача со `Status: done`, которая ссылается на требование, которого нет в спецификации, и у
  которого нет теста с меткой, даёт две строки: C2 и C3 с тем же `REQ-NN`. У задачи со
  `Status: todo` будет только C2.
- C5 читает в `docs/spec.md` и `docs/tasks.md` каждую строку вне огороженных блоков кода, включая
  заголовки любого уровня (например `### ...`) и команды в строках `Check:`. Упоминание `ADR-NNNN`
  внутри блока кода не считается.
- Если два файла ADR имеют один номер, правило нарушает каждый из них: линтер пишет две строки C4,
  по одной на каждый файл, с именем этого файла как токеном (например
  `C4 docs/adr/0002-a.md: 0002-a.md` и `C4 docs/adr/0002-b.md: 0002-b.md`).

## Как читать текст: резолвер

Один набор правил для всех C1-C6:

- Токенизатор, один для текста и для имён тестов: максимальные последовательности `[A-Za-z]+`, в
  нижнем регистре. Кириллица, цифры, `_` и пунктуация это границы, поэтому `billing` один токен (не
  совпадает с `bill`), `clientId` это токен `clientid` (не совпадает с `client`), английское слово
  внутри русского предложения это токен (`клиент client` содержит `client`), русское слово `клиент`
  токенов не даёт, а имя теста `test_req_01_client2` даёт `test`, `req`, `client`.
- Совпадение: токен совпадает со словом `w` из `_Avoid_`, когда он равен `w`, `w + "s"` или
  `w + "es"` (поэтому `clients` совпадает с `client`; `billing` по-прежнему не совпадает с `bill`).
- Проверяемые места для словаря (C6): в `docs/spec.md` и `docs/tasks.md` каждая строка, кроме
  строк-заголовков (`#` в начале строки), строк `Check:` и строк внутри огороженных блоков кода, плюс
  часть каждого заголовка `## T-NN:` после первого `:` (название задачи); плюс имена тестовых
  методов. Ограждения (CommonMark): строка, у которой первый непробельный символ после не более чем
  3 пробелов начинает серию из >= 3 обратных кавычек или >= 3 тильд, открывает блок; строка из того
  же символа, не короче, закрывает его; незакрытый блок идёт до конца файла.
- Имена тестов: `ast.parse` каждого `tests/test_*.py`; имена `def` и `async def`, начинающиеся с
  `test`, на уровне модуля и прямо в теле класса уровня модуля.
- Метки требований в имени теста: регулярное выражение `(?:^|_)req_(\d{2})(?=_|$)`; не больше 2
  меток на имя (имя с 3 и более это находка: "слишком много требований в одном имени теста").
  `REQ-NN` в спецификации и задачах: регулярное выражение `\bREQ-(\d{2})\b`, только целый id,
  поэтому `REQ-1` никогда не совпадает с `REQ-10`.
- Слова `_Avoid_` это объединение по всем файлам контекстов, на которые ссылается `GLOSSARY-MAP.md`
  в `<root>`.

Среди C1-C6 нет правила для трёх меток в одном имени, поэтому линтеру сообщать о них не обязательно;
это правило проверяет `change-request-applied` (пункт 4).

Следствие для словаря: billing избегает `account`, поэтому английское `account` нельзя писать в
спецификации, задачах и именах тестов даже в смысле бухгалтерского счёта. Пишите `LedgerAccount`
(одно слово `ledgeraccount`) или по-русски.

## Готово, когда

1. `scripts/check_artifacts.py <root>` реализует C1-C6 с резолвером выше:
   - на чистом корне exit 0 и никакого вывода;
   - при находках exit 1 и ровно одна строка `<правило> <файл>: <токен>` на каждую находку в stdout,

     на который ссылается `GLOSSARY-MAP.md`);
   - на вашей рабочей папке exit 0.

   Линтер импортирует только стандартную библиотеку и модули `.py` из `scripts/` (например

   - строки REQ-01..REQ-08 не изменились;
   - добавлено ровно одно новое требование в форме WHEN...SHALL, с id, которого раньше не было
     (пропуски в номерах допустимы), и со словом `Dispute` или `disputed`;
   - его перечисляет хотя бы одна задача (правило C1), и каждая задача, которая его перечисляет,
     имеет `Status: done`;

   - ваши изменённые тесты по-прежнему проходят на каждой верной версии в любом порядке, и каждая
     сломанная версия из урока 5 по-прежнему ловится тестом с меткой своего требования;
   - изменённый код проходит скрытые приёмочные тесты;
   - ADR-0001 и ADR-0002 сохраняют свой статус.
3. Stop-хук запускает тесты, затем линтер (`scripts/check_artifacts.py` проекта с корнем
   `$CLAUDE_PROJECT_DIR`). Находка линтера (exit 1) или exit 2 линтера блокирует остановку, и в
   причине блокировки стоит вывод линтера, оба потока: находки идут в stdout, ошибки запуска и
   разбора в stderr. Всё из урока 1 по-прежнему выполняется: пункты 4 и 5 его задания (регистрация,

   при `stop_hook_active: true` хук пропускает остановку с exit 0, даже если линтер нашёл нарушение.
4. Проверки `change-request-applied` и `stop-hook-integrity` принимают каждая не больше 10

   Этап 0 `stop-hook-integrity`: правила регистрации и файла хука из урока 1 (пункт 4 там), и файл

   Проверяются в скрытых прогонах, и провал там засчитывается: скрытые приёмочные тесты; ваши тесты
   проходят на каждой верной версии в любом порядке; каждая сломанная версия из урока 5 ловится

## Как проверяется

**`artifact-linter`** (команда в рабочей папке). Проверка строит корни проекта по своему шаблону
(id, слова и имена файлов случайные при каждом запуске) и запускает на каждом свою копию вашего
линтера в отдельном процессе, в случайном порядке:

- чистые корни с похожими на нарушения, но допустимыми случаями: ожидается exit 0 без вывода;
- корни ровно с одним нарушением, по каждому правилу C1-C6: ожидается exit 1 и ровно одна строка,
  которая начинается с номера правила и содержит токен (корень с двумя ADR под одним номером: ровно
  две такие строки C4, по одной на каждый файл);
- четыре случая exit 2 из пункта 1;
- ваша рабочая папка: exit 0.

Сообщение о провале называет класс корня и правило (например "не найдено нарушение C4"), но не
содержимое корня.

**`change-request-applied`** (команда в рабочей папке): этап 0 из пункта 4, затем скрытые
приёмочные тесты на вашем коде (в отдельном процессе, через шов) и ваши тесты против нескольких
верных и нескольких намеренно сломанных версий в случайном порядке, как в уроке 5. Метку нового
требования проверка берёт из вашей спецификации.

**`stop-hook-integrity`** (команда в рабочей папке): этап 0, затем все пробы урока 1 и пробы с
линтером. В каждой пробе проверка собирает временный проект, кладёт на место
`scripts/check_artifacts.py` свою заглушку и запускает ваш хук. Заглушка либо молчит с exit 0, либо
печатает находку в stdout с exit 1, либо печатает строку `usage:` в stderr с exit 2; токены в её
выводе случайные, и они должны попасть в причину блокировки. Пробы идут в случайном порядке, каждая
не дольше 20 с.

**`integrity-quiz`** (квиз): 6 вопросов-сценариев, нужно 5 верных. В вопросах с пометкой "выберите
все верные" засчитывается только точный набор ответов.

## Как работать (совет, не проверяется)

- Пишите шесть правил test-first на маленьких корнях-примерах: каталог с минимальными
  `GLOSSARY-MAP.md`, файлом контекста, `docs/spec.md`, `docs/tasks.md`, одним ADR и одним тестом, в
  который вы вносите ровно одно нарушение. Агент может писать черновик, вы принимаете.
- Изменение требований вносите в порядке спецификация, задача, тест (сначала красный), код.
- Перед отправкой (у двух проверок есть предел) запустите линтер на корне с одним внесённым
  нарушением и запустите хук руками на этом корне, как в уроке 1: посмотрите stdout, stderr и код
  выхода.
- Запускайте линтер из хука через интерпретатор (`sys.executable` или `python3`), а не как
  исполняемый файл.

## Попытки и подсказки

- `artifact-linter`: число попыток не ограничено; после 5 неудачных интерфейс предложит ментора.
- `change-request-applied`, `stop-hook-integrity`: не больше 10 засчитанных неудачных отправок
  (пункт 4). Провал на этапе 0 не засчитывается.
- Квиз: не больше 3 попыток. После неудачи показывается только общий балл. Ответы и пояснения
  открываются после прохождения или после 3-й неудачной попытки, и тогда квиз закрывается как "не
  пройдено" с разбором у ментора.
- Ментор между попытками задаёт вопросы и подсказывает направление. По тестам он может обсуждать
  выжившего мутанта или падающий тест, которые уже назвала проверка, но не другие. По квизу он не
