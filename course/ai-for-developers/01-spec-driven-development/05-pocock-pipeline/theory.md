# Реальный кейс: конвейер скиллов Matt Pocock, реализация через TDD

## Проблема

Спецификация и задачи готовы. Агент закрывает задачи одну за другой и каждый раз пишет "тесты
зелёные". Как принять работу, не перечитывая каждую строку?

Перечитывать всё подряд не выйдет: через пять задач вы снова становитесь тестовым набором, о чём
предупреждал урок 1. Нужен процесс, в котором каждый шаг оставляет проверяемый след, и набор
проверок, которые агент не может обойти словами.

## Идея: маленькие скиллы, собранные в конвейер

Matt Pocock держит открытый набор скиллов для агентов (github.com/mattpocock/skills, лицензия MIT).
Ниже всё по версии v1.3.2: имена в этом репозитории меняются часто (по CHANGELOG `to-prd` стал
`to-spec`, `to-issues` влился в `to-tickets`, `CONTEXT.md` стал `GLOSSARY.md`), поэтому версию
всегда называйте вместе с именем.

README начинается с четырёх режимов отказа агента и лечения для каждого:

- агент сделал не то, что вы хотели (рассогласование): интервью до начала работы, `grill-me` или
  `grill-with-docs`;
- агент многословен и путает термины: общий язык, глоссарий проекта (его строит `grill-with-docs`);
- код не работает: обратная связь, то есть типы, тесты, `tdd` с циклом red-green-refactor;
- проект превращается в "большой ком грязи": регулярное внимание к дизайну.

Автор противопоставляет свой набор крупным фреймворкам вроде Spec Kit: те "владеют процессом", а эти
скиллы "маленькие, легко адаптируются и собираются вместе". Это позиция автора, а не измеренный
факт.

### Кто вызывает скилл

Скиллы делятся по тому, кто может их вызвать. User-invoked запускаются только когда вы набираете их
имя, их работа оркестровать. Model-invoked может вызвать и человек, и агент, когда задача подходит;
они держат переиспользуемую дисциплину. Правило из README: "A user-invoked skill may invoke
model-invoked skills, but never another user-invoked one".

Технически это поле из урока 2: у user-invoked скиллов в SKILL.md стоит
`disable-model-invocation: true`. В Claude Code 2.1.312 описание такого скилла не попадает в контекст,
и агент сам его не запустит. У `tdd` этого поля нет: агент может взять его сам, когда пишет код.

## Как это работает на практике

### Конвейер

В рабочей папке лежат копии четырёх SKILL.md из v1.3.2 (`vendor/mattpocock-skills/`, тег и коммит в
`UPSTREAM.md`). Это материал для чтения: они не зарегистрированы как скиллы, и Claude Code их не
загружает. Цепочка выглядит так:

1. **`grill-with-docs`** (user-invoked). Тело почти пустое: вызвать скиллы `grilling` и
   `domain-modeling`. Первый ведёт интервью по дереву решений, второй по ходу правит `GLOSSARY.md` и
   предлагает ADR. Это то, что вы делали в уроке 3.
2. **`to-spec`** (user-invoked). Без нового интервью превращает разговор в спецификацию: изучить
   репозиторий, говорить словами глоссария, учитывать ADR; набросать тестовые швы, предпочитая
   существующие, и подтвердить их с пользователем; заполнить шаблон (Problem Statement, Solution, User
   Stories, Implementation Decisions, Testing Decisions, Out of Scope, Further Notes). Это урок 4.
3. **`to-tickets`** (user-invoked). Режет спецификацию на вертикальные "трассирующие пули": узкий, но
   полный путь через все слои, размером на одно свежее окно контекста, с явными блокирующими связями.
   Разбивку показывает пользователю и правит, пока тот не одобрит. Это `docs/tasks.md` урока 4.
4. **`implement`** (user-invoked, в рабочую папку не скопирован, описан в README и в своём SKILL.md).
   Берёт задачу, пишет код через `tdd` на заранее согласованных швах, регулярно гоняет тесты, в конце
   вызывает `code-review` и делает коммит.

Сегодня ваш шаг 4: артефакты шагов 1-3 уже лежат в рабочей папке.

### Правила `tdd`

Скилл `tdd` короткий, прочитайте его целиком. Главное:

- тесты проверяют поведение через публичный интерфейс, а не детали реализации;
- тесты пишутся только на заранее согласованных швах; в спецификации урока 4 шов один:
  `plan_reminders(invoices, sent_reminders, today)`;
- сначала красный тест, потом ровно столько кода, чтобы он позеленел; один шов, один тест, одна
  минимальная реализация за цикл;
- тавтология запрещена: ожидаемое значение нельзя вычислять так же, как его вычисляет код. "Expected
  values must come from an independent source of truth": из требования, а не из формулы в коде;
- горизонтальная нарезка (все тесты, потом весь код) это антипаттерн;
- рефакторинг не часть цикла, он уходит в ревью.

Пример (выдуманное требование, не из вашей спецификации): "напоминание уходит, когда счёт просрочен
на 7 дней". Тавтология: в тесте `expected = due + timedelta(days=REMINDER_DAYS)`, та же формула и та же
константа, что в коде. Если в коде 6 вместо 7, тест посчитает 6 и останется зелёным. Независимое
значение: в тесте буквально стоит дата на 7 дней позже срока, взятая из текста требования.

Урок 1 уже говорил, что TDD с агентами спорен: в небольшом эксперименте Birgitta Böckeler явной
разницы в качестве не нашла, а прогоны с TDD тратили в 2.96-8.50 раза больше токенов (многое из этого
чтение из кэша, так что в деньгах разница, скорее всего, меньше). Что остаётся верным при
любом взгляде: тест должен уметь падать, а ожидаемые значения брать не из кода. Böckeler же называет
мутационное тестирование сигналом качества тестов, и ваши тесты сегодня проверяются именно так.

### Метка требования в имени теста

Как убедиться, что каждое требование покрыто? Свяжите тест с требованием по имени:
`test_req_03_no_reminder_before_grace_period`. Это соглашение упражнения, не стандарт Matt Pocock.
У него есть близкое правило (файл `domain.md` скилла `setup-matt-pocock-skills`): когда в заголовке
задачи или имени теста встречается понятие предметной области, брать термин из `GLOSSARY.md`.
Метка даёт трассировку: требование, задача с этим требованием, тест с его меткой. В уроке 7 вы
напишете линтер, который проверяет эту цепочку сам.

### Как принимать работу

Лестница строгости из урока 1 работает на каждой задаче:

- **команда и её вывод**: у каждой задачи в `docs/tasks.md` есть строка `Check:`. "Тесты зелёные"
  без вывода команды это заявление, а не доказательство;
- **Stop-хук** из урока 1: в Claude Code 2.1.312 он сам запускает тесты и не даёт закончить ход, пока
  они красные. На красном шаге TDD это ожидаемо: хук делает свою работу. Поле `stop_hook_active`
  во входных данных хука равно `true`, когда Claude Code "is already continuing as a result of a stop
  hook". Само поле ничего не пропускает: ваш хук урока 1 при `true` пропускает остановку, так что
  ход может закончиться красным один раз;
- **скрытые тесты**: тесты, которых агент не видел, нельзя подогнать. В бенчмарке EvilGenie скрытые
  тесты были одним из трёх способов ловить подгонку, и авторы увидели от них лишь небольшой
  выигрыш. Поэтому они одна ступень, а не замена остальным;
- **проверка ваших тестов**: тесты должны падать на сломанных версиях кода, иначе зелёный цвет
  ничего не значит.

Плагин Matt Pocock можно поставить, но не обязательно. Помните урок 2: README прямо пишет "A plugin
updates itself", то есть содержимое меняется без вашего ревью. Скопированная и прочитанная версия
предсказуемее.

## Частые ошибки

- Принять "тесты зелёные" без команды и вывода.
- Дать агенту написать код, а потом тесты: тест зелёный с первого запуска, красного шага не было.
- Вычислить ожидаемое значение той же формулой, что в коде.
- Сначала все тесты, потом весь код (горизонтально), вместо одной задачи за цикл.
- Повесить на один тест метки всех требований: такой тест не говорит, какое требование сломано.
- Поправить тест, чтобы он прошёл, вместо того чтобы спросить, кто прав: тест или код.
- Создать генерацией тесты, которых нет в исходнике как `def test_...`: их имена не видны тому, кто
  читает файл.

## Что делать в практике

Вы реализуете `plan_reminders` по задачам T-01..T-05 вместе с агентом, по одной задаче за цикл:
красный тест с меткой требования, минимальный код, зелёный прогон с выводом, отметка `Status: done`.
Проверка запустит скрытые приёмочные тесты на вашем коде и ваши тесты на верных и намеренно
сломанных версиях.
