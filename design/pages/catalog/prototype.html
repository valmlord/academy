00. Введение в разработку с ИИ

Доступен

Синхронизирующий блок. Выбор моделей и уровня ризонинга, локальные модели; ассистенты и экономика цена/качество; контекст-инжиниринг, планирование и исполнение; устройство агентов (loop, harness, tools, MCP); память и AGENTS.md; безопасность и контроль разрешений.

Чему научитесь

  • Выбирает модель, уровень ризонинга и облачный или локальный запуск под конкретную задачу и называет ограничение, которое определило выбор: качество, задержка, цена, контекст или приватность.
  • Оценивает стоимость сессии агента по логу токенов и датированному снимку цен, находит главную составляющую стоимости и рычаг её снижения.
  • Реализует минимальный цикл агента: модель выбирает инструмент, харнесс проверяет разрешение, исполняет инструмент и возвращает результат в контекст; подключает инструменты внешнего процесса по протоколу в стиле MCP.
  • Находит в транскрипте сессии ошибки управления контекстом и до начала исполнения составляет план задачи с проверяемыми шагами.
  • Пишет короткий файл инструкций для агента (AGENTS.md и подключение к своему инструменту) только из невыводимых из кода фактов и предсказывает, какие файлы инструкций загрузит конкретный инструмент при настройках по умолчанию.
  • Переносит критичные запреты из инструкций в механизмы, которые исполняет харнесс (правила разрешений, хук), и находит обходы в конфигурации разрешений.

01. Spec Driven Development

Доступен

Верификация результата работы агента; скиллы и их жизненный цикл в проекте; SDD от проектирования до реализации (ADR, PRD и другие артефакты, автоматический контроль их целостности); онтология проекта: доменная модель, сущности, связи, процессы.

Чему научитесь

  • Делает проверку работы агента детерминированной: пишет тесты, которые падают на неверной реализации, и Stop-хук, который сам запускает тесты и не даёт агенту закончить ход при красных тестах.
  • Оформляет повторяемую процедуру как скилл (SKILL.md по открытому стандарту Agent Skills, с полями Claude Code только там, где они нужны), решает, может ли модель вызывать его сама, и оставляет в постоянно загружаемой памяти проекта только то, что нужно в каждой сессии.
  • Составляет глоссарий предметной области в формате, который читает агент: термины с определениями без деталей реализации, запрещённые синонимы и связи контекстов через доменные события, разводит по контекстам слово, которое в разных частях системы значит разное, и отличает сущность от объекта-значения и границу агрегата.
  • Превращает описание фичи и протокол интервью в спецификацию с проверяемыми требованиями, один ADR для решения, которое трудно отменить, и список вертикальных задач, где каждая задача ссылается на требования и команду проверки.
  • Реализует задачи из готовой спецификации через TDD вместе с агентом так, что код проходит скрытые приёмочные тесты, а каждое требование покрыто тестом с его идентификатором, и находит в записи сессии агента подмену проверки: правку теста, тавтологичный тест, пропущенный красный шаг, заявление без вывода команды, горизонтальную задачу, действие до подтверждения решения.
  • Автоматизирует контроль целостности артефактов: пишет детерминированную проверку согласованности спецификации, задач, тестов, ADR и глоссария, подключает её к Stop-хуку и вносит изменение требований так, что проверка остаётся зелёной.

02. Паттерны агентной разработки

Доступен

Адаптация проекта под агента (менять код, а не дописывать правила); метанавыки: где и почему LLM не справляется и как улучшать обвязку; разработка в закрытых контурах; антипаттерны.

Чему научитесь

  • Раскладывает правила из файла инструкций агента по ступеням (удалить, изменить код, проверка, хук, память) по заданному порядку решения, убирает из памяти всё, что ушло на другие ступени, и меняет код так, чтобы ошибка, от которой предостерегало правило, стала невозможной.
  • Пишет детерминированную проверку архитектурных правил по AST, которая на каждое нарушение печатает правило, файл, строку и способ исправления для агента, подключает её к единой команде проверки проекта и приводит проект к зелёной проверке изменением кода, а не исключениями и не обходом правил.
  • Разбирает сбои агента по записям сессий: называет класс причины и ступень, на которой исправление предотвратит повтор, формулирует конкретное исправление и реализует одно из них как проверку зависимостей.
  • Находит и исправляет в настройках Claude Code и окружения проекта дефекты закрытого контура (адрес шлюза, секрет в репозитории, необязательный трафик, веб-инструменты, песочница со строгим списком хостов, внутренний индекс пакетов, доверие корпоративному CA для каждого инструмента) и в сценариях со слабой локальной моделью выбирает изменения процесса: чаще запускать проверки, дробить задачи, закреплять версии и документацию.
  • Находит в снимке проекта и записи сессии антипаттерны работы с агентом (раздутая память, обязательное правило только в прозе, обвязка ради предпочтения или вместо дешёвой проверки, управление сессией уговорами) и отличает их от похожих хороших практик.

03. Оркестрация субагентов и мультиагентные пайплайны

Доступен

Read-only ревьюер, который обеспечивает харнесс; контракт роли и вызов `claude -p` из Python; пайплайн Coder -> Reviewer -> Summarizer с передачей по ссылке; fan-out ревьюеров (безопасность, производительность, тесты) и synthesizer; проверки цитат на стыках против каскада галлюцинаций; журнал передач и разбор записи прогона.

Чему научитесь

  • Описывает в `.claude/agents/` ревьюера, у которого запрет менять файлы, запускать команды и делегировать обеспечивает сам Claude Code закрытым списком инструментов, а не промптом. Назначает ему модель, которая действительно запустится в заданном сценарии. Находит, какой файл определения загружается и какая настройка переопределяет модель.
  • Оформляет контракт роли (цель, формат вывода в виде JSON Schema, границы) и вызывает роль из Python через `claude -p`. Модель и лимит расходов берутся из конфигурации, структуру вывода проверяет сам Claude Code, у ролей-читателей только инструменты чтения без MCP, у кодера правка без запроса разрешения в headless-режиме без обхода разрешений. Каждый сбой вызова (код выхода, ошибка лимита, нет `structured_output`, исчерпаны попытки структурного вывода) распознаётся, а не принимается за ответ.
  • Собирает оркестратор Coder -> Reviewer -> Summarizer, в котором каждая роль получает только то, что ей нужно, прямо в промпте или по ссылке на файл: ревьюер видит изменение и критерии приёмки, но не рассуждения кодера, а Summarizer видит находки, но не стенограммы. Пайплайн останавливается на первом сбое и пишет журнал каждой передачи.
  • Запускает параллельных ревьюеров по разделам (безопасность, производительность, тесты) с общим synthesizer. Ревьюеры независимы друг от друга, synthesizer сохраняет происхождение каждой находки, а упавший раздел помечается непроверенным. Для сценария выбирает одного агента, шаблон workflow (цепочка с гейтами, маршрутизация, sectioning, voting, orchestrator-workers, evaluator-optimizer) или несколько агентов по измеренным признакам и по контексту, а не по должностям ролей.
  • Пишет детерминированную проверку на стыке. Она пропускает дальше только находки с проверяемой цитатой (существующий файл снимка, строка в диапазоне, цитата с этой строки) и итоговые находки, сводимые к принятым исходным. Ставит её так, чтобы ни одна роль и ни одно поле отчёта не получили непроверенную находку, и выбирает, где проверка исполняется в headless- и интерактивном режиме.
  • Находит в записи stream-json мультиагентного прогона стык, на котором сломалась передача: нарушение границ роли, утечку контекста, непроверенную находку, проигнорированный сбой, "проверено" без проверки. Какой агент сделал событие, определяет по `parent_tool_use_id`, в том числе через вложенные вызовы.

04. Итоговый проект: календарь звонков

Доступен

Букинг тайм-слотов по типу Calendly с разными расписаниями и видами активностей, через Design First: API-контракт на TypeSpec, backend и frontend через SDD, интеграционные и E2E тесты, CI и деплой.

Чему научитесь

  • Разбивает бриф и протокол интервью на спецификацию с требованиями REQ; исполняемые примеры, которые совпадают с моделью заказчика и различают каждое из восьми его решений о времени (несуществующее локальное время, повторяющееся локальное время, смежные встречи, буферы с обеих сторон, минимальное уведомление, окно бронирования, исключение даты вместо недельного правила, день недели в поясе хоста); один ADR; упорядоченный план вертикальных срезов, где каждый срез ссылается на требования и команду проверки.
  • Описывает API на TypeSpec так, что компиляция закреплённым компилятором без JS-расширений даёт OpenAPI, совпадающий с обязательным контрактом по операциям, параметрам, схемам и кодам ошибок. Документирует каждую операцию и модель.
  • Пишет тестовые случаи движка слотов, которые ловят каждую из двенадцати подложенных ошибок. Пишет реализацию движка за CLI-швом, которая проходит скрытые случайные пробы в восьми часовых поясах обоих полушарий.
  • Реализует HTTP-бэкенд по контракту. Бэкенд проходит пробы соответствия (problem+json, 400/404/405/409/422, отказ от лишних полей, время только со смещением, синтаксис ключа идемпотентности), не допускает двойного бронирования при параллельных запросах и повторах с ключом идемпотентности и освобождает слот при отмене.
  • Делает страницу бронирования с клиентом, сгенерированным из контракта и совпадающим с перегенерацией: страница на сервере отрисовывает слоты из API в часовом поясе приглашённого и проксирует /api/ на бэкенд; к странице есть E2E-сценарии для локального запуска (проверяются рубрикой по коду сценариев и приложенному выводу).
  • Собирает единую команду make ci, которая падает на каждой подложенной регрессии API, на контракте, изменённом без перегенерации, и на ручной правке сгенерированного клиента, и проходит на корректных реализациях и после make gen. Пишет Dockerfile и compose, проходящие статическую проверку. Доводит репозиторий до состояния, в котором видимое изменение требования проходит те же проверки, а скрытое изменение, выполненное агентом, тоже их проходит (hidden-task, исполняется после #39).

05. Работа с legacy-кодом

ДоступенГотовится

Анализ существующего проекта, погружение ИИ в структуру проекта, безопасный рефакторинг (characterization-тесты), постепенное внедрение ИИ в существующие процессы.

Чему научитесь

  • Проверяет по самому коду анализ незнакомого legacy-репозитория, сделанный агентом, и находит неверные утверждения и действия: "мёртвый" код, который вызывается по строке из данных; "зависит только от аргументов" у функции, которая читает часы, случайность, состояние модуля или файлы; "без побочных эффектов" у функции, которая пишет файлы; "исправление" поведения, на которое опирается другой модуль; факт из README вопреки коду; команду, которая во время исследования меняет файлы. Выбирает инструмент исследования (субагент Explore, plan mode, ссылки @) по тому, что он загружает и что блокирует.
  • Размещает факты команды о legacy-проекте в местах памяти, которые принимает курс, по строке охвата в конце каждой заметки. Факт области: заметка называет файлы, которых касается, например внешний потребитель файлов, которые пишет один модуль, выгрузка, которая заменяет один файл данных, или внешнее расписание, под которое выставлена одна настройка; такой факт размещается так, что по модели проверки он загружается при работе с каждым названным файлом и не загружается при работе с другими, в том числе у субагента Explore. Факт сессии: заметка касается любого файла, в том числе нового модуля, например согласование любого изменения цены или форма, в которой внешняя система читает суммы из любого модуля; такой факт размещается так, что по модели проверки он загружается при запуске основной сессии. Записывает версию Claude Code и дату, по которым проверил загрузку в документации и в списке изменений. Указывает при запуске команду проверки, которая действительно запускает тесты этого репозитория.
  • Пишет characterization-тесты для кода без тестов, которые фиксируют текущее поведение, в том числе странное, и не зависят от часов, часового пояса, случайности, порядка хеширования, состояния модуля и порядка тестов: набор проходит на исходном коде и падает на каждой скрытой изменённой версии.
  • Рефакторит под защитой сети тестов: закрывает тестами дыры готового набора, которые называет проверка, затем выносит расчёт цены в чистую функцию без часов, файлов и глобальных настроек, на которую опирается старая точка входа, и сохраняет наблюдаемое поведение на заданных и случайных входах проверки.
  • Вводит агента в процесс команды поэтапно: пишет правила гейта, который принимает изменение агента, только если оно применяется, не трогает существующие тесты и защищённые файлы, мало, и тесты, взятые до изменения, и тесты после него проходят. Пишет план внедрения с этапами, областью, измеряемыми сигналами результата, условием остановки и ответственным. Выбирает следующий шаг по измерениям (METR, DORA, семантика Code Review), а не по ощущениям.
