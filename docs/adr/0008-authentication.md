# ADR-0008: Authentication

- Status: Proposed
- Date: 2026-10-30
- Issue: #29

## Context
The platform has one learner, who is also its operator, on a stack published only on loopback
(`127.0.0.1`, plain HTTP; `docker-compose.yml`). ADR-0003 chose Better Auth with email and password;
ADR-0007 item 2 made `users` Better Auth's user table and left #29 three checks. The designs
(`design/flows/auth.md`, `design/pages/sign-in`, `design/pages/dashboard`) have no sign-up and no password
reset: a seed creates the only user. Facts, with sources: the #29 research notes and section 0 of the
#29 design (PR #81; Better Auth 1.7.14 source, file:line), working notes that are not published.

- Better Auth's rate limiter runs only on its HTTP router (`dist/api/index.mjs:173`); server-side
  `auth.api.*` calls are never limited. It is off by default outside `NODE_ENV=production`.
- Its origin check also needs a `Request` and is skipped by default under `NODE_ENV=test`.
- `betterAuth()` builds its context eagerly; `next build` imports route modules without secrets.
- Better Auth uses its public default secret silently outside production, and an env variable
  `BETTER_AUTH_SECRETS` replaces the configured `secret` with only a warning
  (`dist/context/create-context.mjs:70-76`).
- Drizzle 0.45's `DrizzleQueryError` message carries query parameters (session tokens, password hashes),
  and Better Auth's logger passes raw errors as arguments.
- Next 16 keeps a client-sent `X-Forwarded-For`; Better Auth trusts a single value when no proxy is
  configured.

## Decision
1. **Library and scope.** `better-auth` 1.7.14, pinned exactly (the seed uses `$context`, a semi-internal
   API). Email and password only, `disableSignUp: true`, the only plugin `nextCookies()`. No password reset,
   email verification, OAuth or sign-up. Telemetry off explicitly.
2. **Tables.** `sessions`, `accounts`, `verifications` with `usePlural: true`, next to `users`, in ADR-0007
   style: explicit snake_case, `timestamptz`, `text` ids generated by the app (Better Auth's default
   generator, no DB default), every constraint and index named, FKs `sessions_user_id_fk` and
   `accounts_user_id_fk` `ON DELETE CASCADE` (ADR-0007 item 6), plus `sessions_token_unique` and
   `accounts_provider_account_unique (provider_id, account_id)`. Migration `0001_auth`, generated.
3. **ADR-0007 item 2 answered.** Property keys equal Better Auth's field names, so the Drizzle adapter maps
   them without `fields` overrides (proved by Better Auth's own schema check in an integration test; `npx
   auth generate` agrees on keys and differs only in timestamp type, names and checks, so no additive
   migration). The default id generator stays. Better Auth lowercases every email it writes or looks up,
   so `users_email_unique` stays case-sensitive.
4. **Sessions.** Database sessions, 7 days, extended after 1 day of use, no cookie cache. Server renders
   read the session with `disableRefresh` (an RSC cannot set the cookie it would extend); the extension
   happens in a route handler call (`GET /api/auth/get-session`) on each protected page load. One render
   reads the session once (React `cache()`).
5. **Transport.** Sign-in posts from the browser to Better Auth's handler (`POST /api/auth/sign-in/email`),
   so the rate limiter and the origin / Fetch-Metadata checks apply. Sign-out is a server action
   (`auth.api.signOut`), guarded by Next's server-action origin check, invoked from the user menu item
   "Выйти" (the prototype's `a.dropdown-item` whose `href` is the signed-out sign-in page; activation is
   intercepted and calls the action, so no GET ever signs out). The action passes the request headers, so
   Better Auth sees the session cookie, deletes the session row and deletes the cookie. Better Auth catches
   a failure of that row delete itself: it logs it, still deletes the cookie and reports success
   (`dist/api/routes/sign-out.mjs:42-54`), so the row stays valid until it expires (residual below). When
   the call itself throws (for example the base URL cannot be resolved from `Host`), the action logs the
   error name and code and deletes the cookies. Either way it then shows "Вы вышли" via
   `/sign-in?signed-out=1`. The e2e test proves revocation on the server: the token saved before sign-out
   is rejected by `get-session` afterwards. A `Host` outside the allowed list makes the handler
   throw before the router; Next answers 500 and the form shows its "server unreachable" message.
6. **Hosts and cookies.** Dynamic base URL with `allowedHosts` `localhost:*`, `127.0.0.1:*`, `[::1]:*` and
   `protocol: "http"`: any loopback port works, any other `Host` is refused (DNS rebinding).
   `useSecureCookies: false` (plain HTTP); cookies stay `HttpOnly`, `SameSite=Lax`.
   `disableOriginCheck: false` explicitly, so tests run with the check. If the wildcard origin match is
   disproved, an explicit list from `AUTH_ALLOWED_HOSTS` replaces the patterns (design 6.3).
7. **Rate limit.** Always on (also in `pnpm dev` and tests), memory storage, Better Auth's defaults:
   3 requests per 10 s per IP and path on `/sign-in*`.
8. **Route protection.** Default deny: `proxy.ts` redirects every path except `/sign-in` and `/api/auth/*`
   (and static assets) to `/sign-in?next=<path>` when no session cookie is present; this is an optimistic
   redirect only. Its `Location` is absolute and keeps the request's own `Host` (Next's middleware adapter
   parses it with `new URL`, and `NextRequest` rewrites `127.0.0.1` to `localhost`, where the browser has
   no cookie); a `Host` that is not a plain host and port falls back to the request URL's origin. Authorization is a data access layer (`requireSession` / `getSession`) that reads the
   session from the database in every protected page, server action and route handler. A unit test walks
   all of `apps/web` (except `node_modules` and `.next` at any depth, `e2e` and `test` only at the package
   root, so a route segment of that name is still checked, and test files), reads `.ts`, `.tsx`, `.js`,
   `.jsx`, `.mjs` and `.cjs` (`allowJs` is on and Next serves JavaScript pages), and checks every page
   and route handler file under `app/` and every module whose first statement is `"use server"`. It rejects inline
   `"use server"` functions and any export of a route handler or server-action module that is not a
   recognised function form, and it fails when an entry point neither calls the DAL nor sits on an
   explicit allowlist with a reason. Allowlist entries name the export (`<file>#<export>`), so another
   export in the same file is checked like any other; only a page or a route handler file may be listed
   as a whole. #29's allowlist: the sign-in page; `app/sign-in/actions.ts#needsSeedHint` (a public server
   action that reveals only whether any user exists, by one existence query,
   `SELECT 1 FROM users LIMIT 1` through `getDb()`; it is the one database read outside the DAL); the Better Auth route handler (it
   authenticates itself); `app/(app)/actions.ts#signOutAction` (it needs no session). `next` is accepted only as a same-origin path, checked on the server.
   Modules that create the auth instance or read the request session import `server-only`; the testable
   logic sits in marker-free modules with injected dependencies.
9. **Secret.** `BETTER_AUTH_SECRET` only, from env (compose requires it). The app refuses, in every
   environment and at startup before migrating, a missing secret, Better Auth's public default, any value
   shorter than 32 characters, and any non-empty `BETTER_AUTH_SECRETS` (Better Auth would sign with that
   value instead and only warn, and its parser echoes a malformed entry into its error message). Error
   messages name the variable and the rule, never the value. CI generates the secret per run and masks it
   in the log; no usable secret is committed. `AUTH_SECRET` is not used.
10. **Seed.** `pnpm seed` (host side, `tsx`, a turbo task that builds the workspace packages first) creates
    the single user from `SEED_EMAIL` / `SEED_PASSWORD` through Better Auth's internal adapter and password
    hash, or re-keys that user's password when it exists (the only recovery path), and refuses when a
    different user exists. Every rerun converges: a user without its credential account gets one linked.
    Re-keying (or linking) deletes every session of the user, so a leaked password's sessions die with it.
    It does not migrate. It is a one-shot operator command of the `apps/web` package, which ADR-0007 item 8
    (amended by #29) counts as `apps/web`. The password is passed through the git-ignored `.env` or an
    exported variable read without echo, never typed on a command line.
11. **Logging rule for database and auth errors** (ADR-0007 Consequences). Log the error name, the SQLSTATE
    and the constraint name, never a Drizzle message, its params, the query, the stack, the cause or the
    object. Better Auth's `logger.log` keeps only the first line of a message, drops its arguments and
    withholds Drizzle-formatted messages. Errors from session reads are rethrown without `cause`. Pool
    errors log the code only. The seed never prints the email, the password or the URL.
12. **Account deletion** (ADR-0007 item 6: collect `attempts.transcript_path`, delete the user, then the
    transcript files) is not part of #29: it moved to #78, blocked by #29 and #38 (the transcript store's
    delete operation); ADR-0007 is amended accordingly. #29 ships only the cascade of item 2.

## Alternatives considered
- **Sign-in as a server action**: no Better Auth rate limit; we would write our own limiter
  (security-shaped code). Rejected.
- **A fixed `BETTER_AUTH_URL`**: one origin; `127.0.0.1:3080`, `localhost:3080` and `localhost:3000` would
  get 403 from each other. Rejected.
- **The Better Auth browser client**: a dependency surface for one POST. Rejected.
- **Singular table names with `user.modelName = "users"`**: two conventions in one schema, permanently.
  Rejected.
- **Rate limit off in e2e or a test-only rule**: AC7 untestable, or a production config weakened through
  env. Rejected; e2e isolates tests by a distinct `X-Forwarded-For` per test.
- **A committed development secret**: every fresh clone would run with a known secret. Rejected.
- **Supporting `BETTER_AUTH_SECRETS` (secret rotation)**: a second secret source with weaker validation,
  for a single-user loopback stack that never rotates. Rejected; a rotation need reopens this item.
- **A seed via a second Better Auth instance with sign-up enabled**: cannot re-key a password. **Raw SQL
  with a copied hash format**: couples to Better Auth internals more than `$context`. Rejected.
- **A flash cookie for "Вы вышли"**: set and consume across a redirect for a note on a public page.
  Rejected.
- **A `button` inside a `form` for "Выйти"**: correct without JavaScript, but the menu itself needs
  JavaScript, and it would deviate from the prototype's link item. Rejected.
- **`Secure` / `__Secure-` cookies**: unverified over `http://127.0.0.1`; the stack has no TLS. Rejected
  until TLS.

## Consequences
- Every new page calls `requireSession`; every new route handler calls `getSession` and returns 401; every
  new server action calls the DAL; every route that takes an attempt id checks `attempts.user_id` against
  the session user (ADR-0007 item 8). The guard test fails otherwise, unless the entry is allowlisted with
  a reason.
- `.env` must carry `BETTER_AUTH_SECRET` for compose (every command that interpolates the file, including
  `docker compose up -d --wait db`) and for `pnpm dev`; a fresh clone fails fast with the variable's name.
- Residual risks, accepted for a loopback-only single-user stack:
  - `X-Forwarded-For` can be forged to dodge the limiter (the e2e suite relies on it to isolate buckets; a
    reverse proxy that rewrites the header would close it and turn those tests red; the design names the
    serial fallback).
  - Rate-limit state lives in memory and resets on restart (one web process, ADR-0007).
  - The session token is returned in the JSON of sign-in and `get-session` (Better Auth's core `token`
    field is not hidden), so a script running on the origin can read it; `HttpOnly` protects the cookie,
    not the token. An XSS on the origin is a full compromise either way.
  - Better Auth's adapter factory logs a failed fallback user lookup with a direct `console.error(error)`
    (`@better-auth/core` `db/adapter/factory.mjs:391-396`), bypassing the logger; its parameters are the
    user id, not a token or hash.
  - A Better Auth log message in a format the logger does not recognise could still carry data in its
    first line.
  - If the database fails while signing out, Better Auth swallows the failed session delete and still
    clears the cookie (`sign-out.mjs:49-54`): the browser is signed out, but the session row, and so a
    copied token, stays valid until it expires (at most 7 days). The only trace is the log line
    `better-auth error: Failed to delete session from database`; re-keying with `pnpm seed` ends every
    session of the user.
  - The guard test is a regex scan: a DAL call is attributed to the export whose source segment contains
    it, so a non-exported helper placed between two exports counts for the earlier one. Code review
    covers that layout.
  - Endpoints #29 does not use (`/change-password`, `/update-user`, `/list-sessions`, ...) stay reachable
    and authenticate themselves; `disabledPaths` could close them later.
  - Playwright traces of a failed CI run hold that run's seed password (the `fill()` value and the body of
    `POST /api/auth/sign-in/email`) and its session cookies, and the HTML report in `playwright-report`
    embeds the same traces; both are uploaded as the `e2e-report` artifact. Accepted, and `test-results`
    stays uploaded: the password is random per run (`openssl rand -hex 24`), the user and its sessions live
    only in the job's database, which `docker compose down -v` destroys at the end of the job, the
    repository is private, the artifact is uploaded only on failure and kept 7 days, and the traces are the
    main evidence for debugging a failed e2e run. `BETTER_AUTH_SECRET` never reaches a trace (it stays on
    the server). A local trace can hold the typed seed password too (`test-results/` is git-ignored).
- Enabling TLS later flips `useSecureCookies` and the base URL protocol; that is an update of this ADR.
- Upgrading Better Auth is its own task: re-run the seed and schema-check integration tests and re-read
  the limiter, origin-check, session-refresh and secret call sites cited in the design.
- Multi-user features (#50 excludes them) would need sign-up or an admin path and a review of items 7,
  9 and 10.
