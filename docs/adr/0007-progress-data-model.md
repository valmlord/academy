# ADR-0007: Database schema and progress data model

- Status: Accepted
- Date: 2026-10-29
- Issue: #28

## Context
The platform needs to store learners, enrollments, lesson progress, attempts, check results and mentor
reviews (#28, `backlog/02-db-schema.md`). Forces, with sources:

- Lessons live in git, not in the database (ADR-0001). Lesson ids are unique only per course
  (`packages/lesson-schema/src/validate.ts`); check ids are unique per lesson; the validator does not check
  course ids for uniqueness.
- Better Auth arrives in #30. Its core `user` model is id, name, email (unique), emailVerified, image,
  createdAt, updatedAt, and its default id is a 32-character string generated by the application.
- Drizzle 0.45 runtime migrator: all pending migrations run in one transaction; an entry is applied only if
  its `when` timestamp is newer than the newest applied one (an out-of-order merge is skipped silently); the
  stored file hash is never compared; there is no lock, so concurrent migrators are not serialized.
- drizzle-kit 0.31 without a TTY: an ambiguous change (a rename) prints `Interactive prompts require a TTY
  terminal`, writes nothing and exits 0.
- A Postgres enum value added with `ALTER TYPE ... ADD VALUE` cannot be used in the same transaction, and
  a value can never be dropped.
- `docs/architecture.md`: Postgres lives under `apps/web`; the workspace service is the only Docker client.

Sources: `plans/28-db-schema-research.md`, `plans/28-db-schema-design.md` (revision 3), the operations
reviews `plans/28-db-schema-design-review-1-operations.md` and `-2-operations.md`.

## Decision
Each item can be accepted or overturned on its own.

1. **Drizzle 0.45 / drizzle-kit 0.31**, not the 1.0 release candidate. Every column has an explicit
   snake_case SQL name; there is no `casing` option and no relations (no relational query API). Upgrade
   trigger: 1.0.0 on npm's `latest` tag. Upgrade path, as its own task: bump both packages and run
   `drizzle-kit up` (1.0 refuses the old `_journal.json`); check whether the 1.0 migrator adopts an existing
   0.x `drizzle.__drizzle_migrations` table; replace the journal-order unit test with a check of the new
   folder layout; keep the append-only step (1.0 still does not detect edited files); re-check the drift
   step's output literal; adjust any `db.execute` result handling. This ADR is updated then.
2. **`users` is Better Auth's user table.** Every user id and user FK is `text`, never empty
   (`users_id_check`), with no DB default: the application generates ids. #30 must check: that the Drizzle
   adapter maps Better Auth's field names to our property keys (and that `npx auth generate` agrees; if
   not, an additive migration); that it keeps the default id generator, or, for `generateId: "uuid"`,
   whether a DB default `gen_random_uuid()::text` is then needed; whether Better Auth lowercases email,
   because `users_email_unique` is case-sensitive (if not, a unique index on `lower(email)` replaces it).
3. **Lessons are referenced by `(course_id, lesson_id)`**, both `text` and non-empty, not validated by the
   database against `course/` and without a second copy of the slug grammar. Writers take both ids from
   objects parsed by `@academy/lesson-schema`. Lesson ids become permanent once a learner has progress.
4. **Status vocabularies** are `text` columns with a named `CHECK (... IN (...))`, built from one exported
   `as const` array per vocabulary, typed in TypeScript; no `pgEnum`. One helper builds every `IN` list and
   refuses (`InvalidVocabularyValueError`, at schema load) any value that is not `^[a-z][a-z0-9-]*$`.

   | Vocabulary | Values | Meaning |
   |---|---|---|
   | `LESSON_PROGRESS_STATUSES` | `in-progress`, `completed` | No row means not started. |
   | `ATTEMPT_STATUSES` | `running`, `passed`, `failed`, `error` | Over the attempt's own checks only. `passed`: every result passed. `failed`: the learner's work missed the bar (any `failed` or `timeout`, no `error`). `error`: the platform could not grade (any `error`, or the stream ended without a result); it does not count against the learner. |
   | `CHECK_RESULT_STATUSES` | `passed`, `failed`, `timeout`, `error` | `timeout` is its own outcome; `error` means the grader's infrastructure failed. |
   | `MENTOR_REVIEW_STATUSES` | `pending`, `completed`, `error` | |
   | `CHECK_KINDS` | derived from lesson-schema's `Check` union | Never retyped in `packages/db`. |

   The attempt status above is the aggregation rule over its check results; it is a writer rule, not a
   constraint, because it spans rows.
5. **Progress semantics.** Every writer (backlog 08, 10, 11, 13) and the reader (backlog 09) follow these
   rules.
   - *Attempt scope.* An attempt is one grading run started by one learner action over a non-empty subset
     of the lesson's current checks; its `check_results` are exactly that subset, one per check id. A
     lesson with `checks: []` has no attempts.
   - *Atomic finish.* Inserting the results, setting the attempt's final status and `finished_at`, and
     evaluating completion happen in one transaction.
   - *Isolation and order in the finish transaction.* READ COMMITTED, never REPEATABLE READ or
     SERIALIZABLE. (1) Insert the results and set the attempt final; (2) `SELECT ... FROM lesson_progress
     WHERE <pk> FOR NO KEY UPDATE`; (3) the completion query, as a separate statement issued after (2)
     returns; (4) the update to `completed` if the rule holds. Under READ COMMITTED every statement takes a
     new snapshot, so (3) sees results a concurrent finisher committed while (2) waited. A single statement
     that locks and aggregates (a CTE) or a higher isolation level evaluates a snapshot from before the
     wait and loses those results. `FOR NO KEY UPDATE` conflicts with itself, so finishers of one lesson
     are serialized, but not with the `FOR KEY SHARE` an attempt insert takes through its FK check, so
     starting an attempt never waits for a finisher.
   - *Row creation.* The `lesson_progress` row (`in-progress`) is upserted when the learner first opens the
     lesson page, at the latest together with the first attempt.
   - *Completion.* A lesson is complete when every check id in its current `lesson.yaml` has at least one
     `passed` result over all of this user's finished attempts (status not `running`) for that
     `(course_id, lesson_id)`. A passed check counts even if its attempt as a whole is `failed` or `error`.
     Results for check ids no longer in the lesson are ignored. Completing sets `status = 'completed'`,
     `completed_at = now()`, `updated_at = now()`.
   - *Theory lessons* (`checks: []`) are completed only by an explicit "mark as done" action, refused for a
     lesson that has checks.
   - *Sticky.* `completed` never returns to `in-progress`, and `completed_at` stays the first completion
     time. A lesson still `in-progress` is evaluated against its current checks.
   - *One writer function* in `apps/web` implements the rule; no writer sets `completed` any other way.
   - *Dashboard.* Lesson status comes from `lesson_progress.status` alone (no row = not started). Counted
     lessons are the lessons with status `ready` currently in the course tree; progress rows for other
     lesson ids count in neither numerator nor denominator. Course percentage = completed counted lessons /
     counted lessons; a course with 0 counted lessons shows no percentage (never `0/0`, `NaN` or `0%`).
     Module status over its counted lessons: `completed` when it has at least one and all are completed;
     `in-progress` when any of them has a progress row and the module is not completed; otherwise
     `not started`. A module with 0 counted lessons has no status and no percentage.
   - *No grader secrets in `check_results.details`*: no verify-script source, expected outputs, hidden test
     names or contents of `checks/`.
6. **Tables, keys and cascade.** Six tables on one FK chain `users -> enrollments -> lesson_progress ->
   attempts -> {check_results, mentor_reviews}`, every FK `ON DELETE CASCADE`. Natural composite keys
   (`enrollments (user_id, course_id)`, `lesson_progress (user_id, course_id, lesson_id)`, `check_results
   (attempt_id, check_id)`), uuid keys for the event rows (`attempts`, `mentor_reviews`). Every constraint
   and index is named. The cascade covers **Postgres rows in these six tables only**: account deletion
   first collects every `attempts.transcript_path` of the user, then deletes the user, then deletes those
   transcript files (#30 owns the flow, backlog 12 the store's delete operation). #30's `session` and
   `account` FKs to `users` are `ON DELETE CASCADE`.
7. **Transcript reference** = `attempts.transcript_path`, a path relative to the transcript store root,
   NULL when there is none, constrained by the allowlist
   `^[A-Za-z0-9][A-Za-z0-9._-]*(/[A-Za-z0-9][A-Za-z0-9._-]*)*/?$` (every segment starts with a letter or
   digit, so no `.` or `..` segment anywhere; both anchors are load-bearing). The constraint is defence in
   depth: the reader (backlog 12) still resolves `realpath(root + path)` and refuses anything outside the
   root. No length cap; a `char_length` CHECK is additive later.
8. **Database clients.** `apps/web` is the only process that connects to Postgres and the only writer. It
   calls `migrateDatabase` at startup and exits non-zero if it rejects. Every route or API that takes an
   attempt id checks `attempts.user_id` against the session user. Requirement on the workspace API
   (backlog 05): it returns per-check results, mentor output and cost, and the transcript path to
   `apps/web`, and the stream the browser sees ends in, or is relayed by, `apps/web`. `architecture.md`
   does not draw that relay yet; this ADR is where it is required. A service writing to the database
   directly needs the workspace-API ADR and an update of this one first.
9. **Migration and package rules.**
   - Migrations are only generated by drizzle-kit (`db:generate`); merged migration files are never
     edited, deleted or renamed.
   - CI job `db`: step "applied migrations are append-only" (`packages/db/scripts/check-append-only.sh`,
     on the PR merge commit), step "migrations match the schema" (`packages/db/scripts/check-drift.sh`,
     green only with drizzle-kit's literal `No schema changes, nothing to migrate` and a clean
     `packages/db/drizzle`), and the unit test of journal order (U1).
   - `migrateDatabase` runs on one connection under `pg_advisory_lock(MIGRATION_LOCK_KEY)`, with
     `lock_timeout` set via `set_config` and a bind parameter, validated to an integer from 1 to
     2147483647 (`InvalidLockTimeoutError`).
   - Failures are `MigrationError` with a stage: `connect`, `lock` or `apply`. The "another
     migrateDatabase may hold it" hint appears only for SQLSTATE 55P03.
   - A bundled consumer passes an absolute `migrationsFolder`; a relative one is
     `InvalidMigrationsFolderError`.
   - No connection string, or any part of its userinfo, in any error message, `cause` or log line the
     package builds; option errors never serialize caller data.
10. **Change procedure.** Any schema change is a dev task with a generated migration. Changing items 2-9
    updates this ADR and needs Stepan's approval.

## Alternatives considered
- **Drizzle 1.0 RC** (item 1): fixes out-of-order merges by design and its kit has no dependencies, but
  the API was still moving between RCs (`casing` removed from config, RQB v2, `db.execute` result type).
- **`pgEnum` for statuses** (item 4): adding a value and using it in one migrate run fails, and values
  can never be dropped. **Lookup tables** cost joins and seed data for four tiny fixed lists. **No
  constraint** lets a writer typo persist silently.
- **A unit test comparing the snapshot's CHECK lists with the vocabularies** (item 4): the drift step
  already regenerates a changed CHECK on every PR, and the test would couple to the 0.x snapshot format.
- **Own `users` table plus Better Auth's `user`, 1:1** (item 2): two identities for one person and a join
  on every request. **`uuid` user ids**: they need #30 configuration. **Integer ids**: Better Auth's string
  ids would not fit.
- **`lesson_id` alone** (item 3) collides across courses. **A DB check that the lesson exists** cannot see
  git and breaks history on removal. **A slug `CHECK`** would duplicate the id grammar and not catch the
  likely writer bug.
- **Storing transcripts in Postgres** (item 7): large logs written by the service would bloat the rows.
  **A denylist CHECK** (`<> ''`, no leading `/`, no `..`) still admits backslashes, control characters and
  `%2e%2e`.
- **`SET lock_timeout = <n>`** (item 9) takes no bind parameter, so the value would be interpolated.
- **The workspace service writing attempts directly** (item 8) contradicts `architecture.md` and needs a
  second DB client.
- **`postgres` (postgres.js) driver**: `pg` is the only driver in Better Auth's peers, and its `Pool` is
  what Better Auth accepts. **`casing: "snake_case"`**: must match in two places and is removed in 1.0.

## Consequences
- Writers upsert `enrollments` and `lesson_progress` (`ON CONFLICT DO NOTHING`) before inserting an
  attempt.
- Renaming a lesson id needs a data migration; until then the dashboard ignores the orphaned rows.
- Removing a check kind from lesson-schema makes the generated migration narrow the CHECK; on a database
  with rows of that kind it fails and rolls back, and the app does not start until a data decision is made.
- `apps/web` marks an attempt `error` with `finished_at` when the service stream for it ends without a
  final result, and at startup marks every attempt still `running` as `error` (one web process assumed; a
  multi-instance deployment needs an owner or heartbeat column first).
- Bundled consumers (Next.js) list `@academy/db`, `drizzle-orm` and `pg` in `serverExternalPackages` or
  pass an absolute `migrationsFolder`; every image ships `packages/db/drizzle`; #1 tests `migrateDatabase`
  inside the built image.
- drizzle-kit 0.31 pulls `esbuild@0.18.20` (moderate GHSA-67mh-4wv8-2f99, exploitable only while
  `esbuild serve` runs, which nothing here does). Accepted until the 1.0 upgrade.
- Transcripts survive the database cascade; the account-deletion flow deletes them.
- Drizzle 0.45's `DrizzleQueryError` message embeds the query parameters. Before credential tables exist,
  #30 states its own rule for logging DB errors (for example: the SQLSTATE and the constraint name, never
  the Drizzle error message or object).
- Residual risks of the append-only guard: a direct push to `main` bypasses it (no branch protection,
  ADR-0004); an edited `when` of an existing `_journal.json` entry is unguarded (U1 only checks that the
  values increase); a migration applied locally before it was merged may later differ, so Stepan resets
  his local database (`docker compose down -v`) in that case.

### Follow-ups for backlog 08 (the finish transaction and the stale-attempt sweep)
- If two web processes overlap (a dev restart), the new process's startup sweep can mark the old
  process's in-flight attempt `error` before the old process finishes it. Decide whether the finish
  update overwrites `error` (the more accurate outcome) or is guarded by `status = 'running'`. Either
  way, its passed results still count toward completion.
- Write step (4) as `UPDATE ... WHERE status = 'in-progress'`, or skip it when the row read in step (2) is
  already `completed`, so stickiness and the first `completed_at` follow from the statement itself.
- Pass `isolationLevel: "read committed"` to `db.transaction` explicitly, so a changed
  `default_transaction_isolation` on the server cannot break the finish rule.
